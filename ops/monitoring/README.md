# Monitoring and alerting for itlearning.tech

← [Home](../../README.md) · [Moodle blueprint](../../lms/moodle/BLUEPRINT.md) · [CodeRunner and Jobe](../../lms/moodle/CODERUNNER.md)

Prometheus, Grafana and five exporters run on the Moodle server (the "Moodle VPS") and watch both servers. Everything listens on `127.0.0.1` only, so the stack opens no ports and the firewall is unchanged.

| Component | What it measures |
| --- | --- |
| Prometheus v3.15 | Stores the metrics (30 days, at most 5 GB) |
| Grafana 12.4 | Dashboards and alerting |
| node-exporter v1.12 | CPU, memory, disk and network of the Moodle VPS. A second copy on the Jobe VPS is read through `https://jobe.itlearning.tech/node-metrics/` (Caddy, Moodle server's IP only). |
| cAdvisor v0.60 | CPU and memory of each container on the Moodle VPS (Moodle, the database, mail, Ollama, …). Uses `ghcr.io/google/cadvisor`, limited to CPU, memory and network every 60 s: the defaults spiked to 80% of a CPU on this 2-CPU server. |
| blackbox-exporter v0.29 | From outside: `https://itlearning.tech`, the Jobe API, mail ports 25, 587 and 993, and certificate expiry |
| prometheus-nginxlog-exporter v1.11 | **Real itlearning.tech response times**, from a timing log added to Nginx Proxy Manager ([`npm-custom/`](npm-custom/)). Each request gets a `kind`: `page` (PHP pages), `quizsubmit` (quiz submissions, including CodeRunner checks), `ajax` or `asset`. |
| Caddy on the Jobe VPS | **Code-check time**: request timings at `https://jobe.itlearning.tech/caddy-metrics` (Moodle server only; Caddy's admin API stays local). POST requests are code checks. |

Together they used about 0.2 GB of RAM after start-up (each container has a memory limit).

## Open Grafana and Prometheus

Both listen on the Moodle server's `127.0.0.1` only. Open an SSH tunnel for both:

```bash
ssh -L 3000:127.0.0.1:3000 -L 9090:127.0.0.1:9090 itlearning
```

While it's open:

- **Grafana:** <http://localhost:3000>, user `admin`. The password was generated on the first install and is only on the server: `ssh itlearning grep GRAFANA /opt/monitoring/.env`.
- **Prometheus:** <http://localhost:9090>. It has no login of its own, which is why it stays behind the tunnel. *Query* runs PromQL, and *Status → Targets* lists the 11 scrape targets. The alert rules live in Grafana (*Alerting → Alert rules*), not in Prometheus.

Dashboards are in the **ITLearning** folder:

- **ITLearning status:**
  - websites and mail ports up or down, response times, certificate days left;
  - CPU, memory and disk per server, and per container;
  - page-load percentiles (p50, p90, p99) and p90 by kind of request;
  - code-check time on Jobe;
  - requests per minute and 5xx errors;
  - CPU and memory p90 over the last hour.

  It's generated by [`grafana/make_dashboard.py`](grafana/make_dashboard.py).
- **Node Exporter Full:** every host metric in detail. It's the community dashboard 1860 by rfmoz (revision 45, LGPL-3.0); choose the server with the *Host* drop-down.

### Useful queries

| Question | PromQL |
| --- | --- |
| p90 page load, last 15 min | `histogram_quantile(0.9, sum by (le) (rate(moodle_http_response_time_seconds_hist_bucket{kind="page"}[15m])))` |
| p90 by kind of request | `histogram_quantile(0.9, sum by (le, kind) (rate(moodle_http_response_time_seconds_hist_bucket[15m])))` |
| p90 code-check time | `histogram_quantile(0.9, sum by (le) (rate(caddy_http_request_duration_seconds_bucket{instance="jobe-vps", method="POST"}[15m])))` |
| p90 outside check, 30 min | `quantile_over_time(0.9, probe_duration_seconds{job="blackbox-http"}[30m])` |
| p90 CPU over 1 h | `quantile_over_time(0.9, (100 * (1 - avg by (instance) (rate(node_cpu_seconds_total{mode="idle"}[5m]))))[1h:1m])` |

For p99 or p50, change the `0.9`. Caddy's largest timing bucket is 10 s, so a code-check percentile of 10 means "10 s or more".

## Alerts

| Alert | Fires when | Severity |
| --- | --- | --- |
| Monitoring target down | Prometheus can't scrape a server or exporter for 5 min | critical |
| Website down | itlearning.tech or the Jobe API isn't answering 200 for 3 min | critical |
| Mail port down | Port 25, 587 or 993 refuses connections for 5 min | warning |
| TLS certificate expires soon | Under 14 days left, for 1 h | warning |
| Disk almost full | Root disk over 85% for 15 min | warning |
| Memory almost exhausted | Over 90% in use for 10 min | warning |
| CPU busy (p90 over 1 h) | p90 of CPU use over the last hour above 85%, for 10 min | warning |
| Memory under sustained pressure (p90 over 1 h) | p90 of memory use over the last hour above 85%, for 10 min | warning |
| Moodle page loads slow (p90) | p90 of real page loads over 15 min above 2 s, for 5 min, with at least 20 page requests | warning |
| Code checks slow (p90) | p90 of Jobe code checks over 15 min at least 10 s, for 5 min, with at least 5 checks | warning |
| Website checks slow (p90 over 30 min) | p90 of the outside check above 3 s, for 5 min | warning |

The latency rules need a minimum of traffic, so a single slow request at night can't fire them. The rules are in [`grafana/provisioning/alerting/alerting.yml`](grafana/provisioning/alerting/alerting.yml); change them there and re-run the installer, so the server and the repository stay in step.

### Where alerts go

Alerts always go to **admin@itlearning.tech**. Grafana sends them through this server's own mail server: port 25, no login, local delivery. It greets the mail server as `itlearning.tech`, because Postfix rejects the bare server name. A test alert was delivered on 28 October 2026. Alerts are grouped by alert and repeat every 4 hours while firing.

More destinations come from `/opt/monitoring/.env` (see [`env.example`](env.example)). The installer turns them into `contactpoints.yml` on the server, readable only by Grafana, so addresses and tokens never enter the repository:

- `ALERT_EMAILS=you@example.com,other@example.com` adds email addresses.
- `TELEGRAM_BOT_TOKEN` and `TELEGRAM_CHAT_ID` add Telegram:
  1. In Telegram, talk to **@BotFather**, send `/newbot` and copy the token.
  2. Send your new bot any message.
  3. Open `https://api.telegram.org/bot<token>/getUpdates`; your chat id is the number after `"chat":{"id":`.
  4. Add both lines to the `.env` with `ssh itlearning nano /opt/monitoring/.env`, then re-run the installer.

Monitoring runs on the Moodle VPS, so if that whole server goes down, nothing on it can send an alert. A free external uptime checker on `https://itlearning.tech` (for example UptimeRobot) covers that case.

## Install or update

```bash
scp -r ops/monitoring itlearning:/tmp/ && ssh itlearning sh /tmp/monitoring/setup-monitoring.sh
```

The script:

1. copies the files to `/opt/monitoring`, keeping the existing `.env`;
2. writes the contact points;
3. installs the Nginx Proxy Manager timing log (tested with `nginx -t`, and removed again if nginx rejects it);
4. starts the containers and restarts Prometheus and Grafana so they reread their configuration;
5. checks that every scrape target is up and the alert rules and dashboards are loaded.

The Jobe side (node-exporter, Caddy metrics and their routes) is part of [`scripts/moodle/jobe/setup-jobe.sh`](../../scripts/moodle/jobe/setup-jobe.sh).
