# Lab 3.D: Query tuning, from slow query to indexed query

← [Module 3](../../phases/01-foundations/03-databases-sql-nosql/README.md)

A deliberately under-indexed banking database (only primary keys) and five slow queries modelled on real workloads: a statement page, a dormant-accounts report, a monthly merchant-category summary, a narration search and a reconciliation join.

## Set up

```bash
docker run -d --name tuning -e POSTGRES_PASSWORD=devpass -p 5433:5432 postgres:17-alpine
psql -h localhost -p 5433 -U postgres -v rows=2000000 -f seed.sql     # start with 2M rows; try 20M later
psql -h localhost -p 5433 -U postgres
```

(No local `psql`? Use `docker exec -i tuning psql -U postgres -v rows=2000000 < seed.sql`.)

All data is synthetic, generated by `seed.sql`.

## Your task

For each query in `queries.sql`:

1. Run it with `EXPLAIN (ANALYZE, BUFFERS)` and save the plan.
2. In one paragraph, explain why it's slow: which node dominates, how many rows are read versus returned, and why the planner chose that plan.
3. Fix it with an index, a query rewrite, or both (topic 3.3). Some queries need a rewrite before any index can help. Watch for functions applied to columns, leading wildcards and range-before-equality column order.
4. Re-run and save the new plan and time.
5. Note what each index costs: size (`pg_relation_size`) and its effect on inserts.

Deliver `TUNING.md` with a before/after table (query, time before, time after, rows read before/after, fix, index size). Then rerun the seed at 20M rows and check whether your fixes still hold.

Hints are in topic 3.3. No solution is published; mentors review `TUNING.md`.
