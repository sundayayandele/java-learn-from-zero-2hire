# Capstone 1: Core banking ledger

**Required for every learner.** Weeks 5–12. Modules used: 1, 2, 3, 4.

## Business context

Every bank, wallet and payment company sits on a **ledger**: the record of who owns how much, and every movement that changed it. Tier-1 Nigerian banks, mobile-money operators and fintech wallets all run some version of a double-entry ledger. When it is wrong, customers lose money, regulators fine the institution, and finance teams spend nights reconciling. When it is right, it is invisible.

You will build the ledger service for a small digital bank, **ITL Bank**: customer wallet accounts, internal general-ledger (GL) accounts, deposits, transfers with fees, reversals, statements and a trial balance, correct under concurrent load and safe against duplicate requests.

## What you'll build

A Spring Boot 4 REST service backed by PostgreSQL.

### Accounts

- **Customer accounts** (type `LIABILITY` from the bank's point of view): 10-digit account number generated by the service, holder name, currency (NGN by default; must be a valid `java.util.Currency`), status `ACTIVE` / `FROZEN` / `CLOSED`, daily transfer limit.
- **Internal GL accounts** created by a migration: `CASH` (asset, the source of deposits), `FEE_INCOME` (income), `SUSPENSE` (for reversals and unmatched items).

### Double-entry journals

Every business event is a **journal** with two or more **postings**. Each posting debits or credits one account. **The postings of every journal sum to zero per currency.** Balances are derived from postings, and also stored on the account row (updated in the same transaction) for fast reads. A consistency check endpoint proves the two agree.

| Event | Postings |
| --- | --- |
| Deposit ₦50,000 into A | Debit CASH 50,000; Credit A 50,000 |
| Transfer ₦20,000 from A to B with ₦26.88 fee | Debit A 20,026.88; Credit B 20,000; Credit FEE_INCOME 26.88 |
| Reversal of that transfer | The exact opposite postings, as a new journal that references the original |

Postings are **never updated or deleted**. Mistakes are corrected with reversing journals, which is how real ledgers stay auditable.

### API (suggested)

| Method and path | Purpose | Notes |
| --- | --- | --- |
| `POST /api/v1/accounts` | Open an account | 201 + `Location` |
| `GET /api/v1/accounts/{number}` | Account details and balance | 404 Problem Detail if unknown |
| `POST /api/v1/accounts/{number}/freeze` and `/unfreeze` | Change status | 204 |
| `POST /api/v1/deposits` | Deposit from CASH | Requires `reference` |
| `POST /api/v1/transfers` | Transfer between customer accounts | Requires `reference`; fee applied |
| `POST /api/v1/transfers/{reference}/reversal` | Reverse a transfer | Once only |
| `GET /api/v1/accounts/{number}/statement?from=&to=&page=` | Statement with opening balance, running balance and closing balance | Paged |
| `GET /api/v1/ledger/trial-balance` | Every account's balance; total of debits equals total of credits | |
| `GET /api/v1/ledger/consistency` | Compares stored balances with posting sums | Should always report zero differences |

### Business rules

1. Amounts are positive, at most 2 decimal places (validate with `@Digits`), in the account's currency.
2. A customer account can never go below zero (no overdrafts in this capstone).
3. `FROZEN` and `CLOSED` accounts can neither send nor receive.
4. Transfers to the same account are rejected.
5. **Fees** follow tiers configured in `application.yaml` via `@ConfigurationProperties` (example: up to ₦5,000 → ₦10.75; up to ₦50,000 → ₦26.88; above → ₦53.75; the fee counts towards the balance check).
6. **Daily limit**: the sum of a customer's outgoing transfers (amount + fee) on the current business day (Africa/Lagos time) may not exceed the account's limit.
7. **Idempotency**: `reference` is unique per journal. Repeating a request with the same reference and the same payload returns the original result (HTTP 200) without posting again. The same reference with a different payload is a 409 Conflict.
8. A transfer can be reversed only once, and only if the receiving account still has the funds (otherwise 422).

### Errors

All errors are RFC 9457 Problem Details with stable `type` URIs: `account-not-found` (404), `validation-failed` (400), `insufficient-funds` (422), `daily-limit-exceeded` (422), `account-not-active` (422), `duplicate-reference` (409), `already-reversed` (409).

## Data

No external dataset: the ledger's data is what your API creates. Write a small **load generator** (a test helper or a separate `main`) that opens 1,000 accounts and runs 100,000 random deposits and transfers, so you can test performance and statements at realistic volume. Generated data is yours; publish it under CC0 if you share it. Currency rules come from `java.util.Currency`.

## Acceptance criteria

Your CI must run tests that prove:

- [ ] Deposit then transfer produces the expected balances and postings, and every journal sums to zero.
- [ ] A transfer that would overdraw the account returns 422 and changes nothing.
- [ ] The fee tier boundaries (exactly ₦5,000.00, ₦5,000.01, ₦50,000.00, ₦50,000.01) give the right fees.
- [ ] Repeating a transfer with the same reference returns the original result and creates no new postings; a different payload with the same reference returns 409.
- [ ] **Concurrency:** 50 transfers fired in parallel between 10 accounts leave the sum of all customer balances plus fee income unchanged, no balance negative, and `/ledger/consistency` reports zero differences.
- [ ] Reversal restores both balances; a second reversal returns 409.
- [ ] Frozen accounts can't send or receive.
- [ ] The statement's closing balance equals the opening balance plus credits minus debits for the period.
- [ ] The trial balance's debits equal its credits.

## Infrastructure and deployment

- **Local:** `docker compose up --build` from the starter.
- **Sizing:** app 0.5 vCPU / 1 GB RAM (`-XX:MaxRAMPercentage=75`); PostgreSQL 1 vCPU / 1 GB / 10 GB storage is ample for the load generator. A single 2 vCPU / 4 GB VPS runs both.
- **CI/CD:** GitHub Actions (primary) and GitLab CI (secondary) come with the starter.
- **Deploy:** follow the [deployment guide](../../deploy/README.md) for a VPS, AWS, Azure or GCP. Use a managed PostgreSQL on the cloud platforms; enable automated backups (a ledger without backups is not a ledger).
