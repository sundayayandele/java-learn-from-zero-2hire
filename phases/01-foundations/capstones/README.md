# Phase 1 capstones

← [Phase 1](../README.md) · [Data sources and licences](../../../docs/data-sources.md) · [Deployment and CI/CD guide](../deploy/README.md)

Ten capstones built on the problems Nigerian and international financial institutions actually hire Java engineers to solve. Each uses only public data that is free for commercial and non-commercial use (licences recorded in each brief and in [docs/data-sources.md](../../../docs/data-sources.md)), or synthetic data generated by your own code.

**Every capstone starts with its architecture and system design**: five views (solution, logical, technical, infrastructure and cloud) as Mermaid, draw.io, SVG and PNG, plus architecture decision records, in its `architecture/` folder. Study them before you code, adapt them to what you build, and use them in interviews. The goal is system thinking: how the service fits its users, data, integrations and platform.

**Every capstone has a step-by-step build guide** (`GUIDE.md`, linked at the top of each brief): setup from the starter, data download commands, build steps that each end with a "done when" check, then CI, deployment, architecture pack, README and submission.

**Complete at least three by the end of week 13: Capstone 1 plus any two others**, then defend them in a 20-minute [capstone defence](../../../docs/assessments/capstone-defence.md) (demo, code questions and a live change). Pick the two that best match the jobs you will apply for (see "Good for" below). Capstones 1 and 2 come with complete reference solutions; look at them only after you have built your own version.

## What every capstone must have

These are the same standards hiring managers look for. They are also the rubric.

1. **A public GitHub repository** created from the capstone's `starter/` folder (or the [Spring Boot service starter](../../../templates/spring-boot-service-starter/README.md)), with a meaningful commit history: small commits, clear messages.
2. **Java 21 and Spring Boot 4.1**, Maven wrapper, PostgreSQL via Flyway migrations, `ddl-auto=validate`.
3. **Money as `BigDecimal` (or `long` minor units) everywhere**, with a written rounding policy.
4. **Tests**: unit tests for every business rule, `@WebMvcTest` tests for validation and errors, and at least one Testcontainers integration test of the main flow. `./mvnw verify` green.
5. **CI**: GitHub Actions green on `main` (primary). The `.gitlab-ci.yml` from the starter should also pass if you mirror the repo to gitlab.com (secondary, recommended).
6. **Operability**: Actuator health/readiness, Prometheus metrics including at least two business metrics, Problem Details errors, no secrets in the repository.
7. **Deployment**: running on at least one target from the [deployment guide](../deploy/README.md) (a VPS is cheapest), with the health endpoint URL in your README. Tear down cloud resources when you're done to avoid charges.
8. **Architecture pack** in your repository: the five diagrams updated to match what you built, and at least three ADRs of your own.
9. **README** that a hiring manager can read in three minutes: the business problem, architecture diagram, how to run it, API examples, data source and licence attribution, design decisions and trade-offs, what you'd do next.
10. **Data licence compliance**: attribution lines copied from the brief; raw datasets downloaded by script, not committed.

## Rubric

Each criterion is scored 1–4. **A capstone passes at 14/20 with no criterion below 2.**

| Criterion | 1: Not yet | 2: Developing | 3: Hireable | 4: Standout |
| --- | --- | --- | --- | --- |
| Correctness and domain rules | Core flows broken or money handled with floating point | Main flows work; some rules or edge cases missing | All rules implemented and tested, including boundaries and failures | Invariants enforced at several layers (DB constraints, domain, tests under concurrency) |
| Engineering quality | Runs only on the author's machine | Builds from README with effort; little structure | Clean layers, small classes, validation, Problem Details, CI green | Code reads like the business rules; thoughtful abstractions; measured performance |
| Data and persistence | Ad-hoc schema, no migrations | Migrations exist; some missing constraints or indexes | 3NF schema, constraints, indexes justified by query plans, idempotent imports | Proven query performance at realistic volume, documented tuning |
| Delivery and operations | Not deployed | Runs in Docker locally | Deployed with health checks, metrics and no secrets in Git | Automated deployment from CI, dashboard, runbook |
| Communication | Code only | README describes *what* | README explains *why*, trade-offs and data licences | Architecture decision records and a 3-minute demo video |

## Infrastructure sizing at a glance

All Phase 1 capstones are small services. Detailed sizing and step-by-step deployment for each platform are in the [deployment guide](../deploy/README.md).

| Environment | App | Database | Typical cost |
| --- | --- | --- | --- |
| Laptop | Docker Desktop, 8 GB RAM minimum (16 GB recommended) | PostgreSQL container | Free |
| VPS (e.g. SSDNodes) | One VM, 2 vCPU / 4 GB RAM / 40 GB SSD runs app + PostgreSQL in Docker Compose | Same VM | Lowest |
| AWS | ECS Express Mode (Fargate) 0.5 vCPU / 1 GB | RDS PostgreSQL db.t4g.micro, 20 GB | Free tier eligible for 12 months, then low |
| Azure | Container Apps 0.5 vCPU / 1 GiB | Azure Database for PostgreSQL Flexible Server B1ms | Free account credit, then low |
| GCP | Cloud Run 1 vCPU / 512 MiB–1 GiB | Cloud SQL PostgreSQL db-f1-micro or shared-core | Free trial credit, then low |

Capstones 5, 8 and 9 load millions of rows: give the database at least 2 vCPU / 4 GB RAM and 20–50 GB storage during imports, or work with a filtered subset (each brief says how).
