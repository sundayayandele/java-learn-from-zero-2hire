Week 12 · Module 4: Spring Boot 4 Fundamentals

What you will be able to do

  • Map entities, IDs, columns, enums, embedded values and relationships with Jakarta Persistence (JPA) annotations.
  • Explain the persistence context, entity states and dirty checking, and how they produce SQL.
  • Use Spring Data JPA repositories: derived queries, @Query, projections, pagination and sorting.
  • Detect and fix the N+1 select problem with fetch joins, entity graphs and DTO projections.
  • Use @Transactional correctly, and add optimistic locking with @Version.

Why this matters in a bank or fintech

JPA with Hibernate is the default persistence stack in enterprise Java, and also the most common source of performance incidents in it. A statement page that silently runs 501 queries, a "harmless" toString() that loads a customer's entire transaction history, or a @Transactional annotation that never applied, all pass tests on a laptop and fall over in production. This topic teaches you to use JPA productively and to see the SQL it generates, which is exactly what interviewers probe with "what's the N+1 problem?".

1. JPA, Hibernate and Spring Data

  • Jakarta Persistence (JPA) is a specification: annotations and the EntityManager API (jakarta.persistence). Spring Boot 4 uses Jakarta Persistence 3.2.
  • Hibernate (version 7 in Boot 4) is the implementation that turns entity operations into SQL.
  • Spring Data JPA adds repository interfaces on top, generating common queries for you.

All three sit on JDBC and the HikariCP pool from topic 3.5.

spring.datasource.url=jdbc:postgresql://localhost:5432/bank
spring.datasource.username=bank_app
spring.datasource.password=${DB_PASSWORD}
spring.jpa.hibernate.ddl-auto=validate        # Flyway owns the schema; Hibernate only checks it
spring.jpa.open-in-view=false                  # see section 7
spring.jpa.show-sql=false                      # use logging instead (below)
logging.level.org.hibernate.SQL=debug          # print every SQL statement during development
logging.level.org.hibernate.orm.jdbc.bind=trace   # and the bound parameter values

Never use ddl-auto=update or create against a shared database. Schemas are managed by Flyway migrations (topic 3.4); validate makes startup fail if entities and schema disagree.

2. Mapping entities

@Entity
@Table(name = "account")
public class Account {

    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)     // matches GENERATED ALWAYS AS IDENTITY
    private Long id;

    @Column(nullable = false, unique = true, length = 10)
    private String number;

    @Enumerated(EnumType.STRING)                            // store 'SAVINGS', never the ordinal 0/1/2
    @Column(nullable = false)
    private Product product;

    @Column(nullable = false, precision = 19, scale = 2)
    private BigDecimal balance = BigDecimal.ZERO;

    @Column(nullable = false, length = 3)
    private String currency;

    @ManyToOne(fetch = FetchType.LAZY, optional = false)
    @JoinColumn(name = "customer_id")
    private Customer customer;

    @Version
    private long version;                                    // optimistic locking (section 6)

    protected Account() { }                                  // JPA needs a no-arg constructor

    public Account(String number, Product product, String currency, Customer customer) {
        this.number = number; this.product = product; this.currency = currency; this.customer = customer;
    }

    public void debit(BigDecimal amount) {                   // behaviour, not just setters (topic 1.4)
        if (balance.compareTo(amount) < 0) throw new InsufficientFundsException(number, amount, balance);
        balance = balance.subtract(amount);
    }

    public void credit(BigDecimal amount) { balance = balance.add(amount); }

    public Long getId() { return id; }
    public String getNumber() { return number; }
    public BigDecimal getBalance() { return balance; }
    // ...
}

Rules for entities:

  • They need a no-arg constructor (it can be protected) and must not be final, because Hibernate creates proxies (subclasses) for lazy loading. That is why records are not entities (topic 1.8).
  • Map enums with EnumType.STRING. The default ORDINAL stores 0, 1, 2 and corrupts data the day someone reorders the enum.
  • Keep equals/hashCode simple: base them on a business key (number) or on id with care for unsaved entities. Never include lazy associations.
  • Don't put associations in toString(): printing an account would load its customer, and printing a customer could load every account.

Value objects with @Embeddable

@Embeddable
public record Money(@Column(name = "amount", precision = 19, scale = 2) BigDecimal amount,
                    @Column(name = "currency", length = 3) String currency) { }

@Entity
public class LedgerPosting {
    @Id @GeneratedValue(strategy = GenerationType.IDENTITY) private Long id;
    @Embedded private Money money;          // stored as two columns in the posting table
}

Records can be @Embeddable (Hibernate 6.2+), which is a neat way to keep Money immutable inside a mutable entity.

Relationships

Annotation Example Default fetch
@ManyToOne many transactions → one account EAGER (change it to LAZY)
@OneToMany(mappedBy = ...) one account → many transactions LAZY
@OneToOne customer → KYC profile EAGER (change it to LAZY)
@ManyToMany customers ↔︎ joint accounts LAZY (often better as an explicit join entity)

Make every association LAZY. EAGER is a performance trap: it loads related data on every query, whether you need it or not, and cannot be switched off per query.

Bidirectional relationships have an owning side (the side with the foreign key, @ManyToOne/@JoinColumn) and an inverse side (mappedBy). Only the owning side's changes are written to the database. Think twice before mapping @OneToMany collections that can be huge: an account's transactions should be queried (paged), not loaded as a collection.

3. The persistence context

The EntityManager (and the Hibernate Session underneath) keeps a persistence context: a first-level cache of the entities loaded in the current transaction.

Entity states:

  • Transient: new Account(...), not known to JPA.
  • Managed: loaded or saved in the current persistence context. Changes are tracked.
  • Detached: was managed, but the context closed (e.g. after the transaction).
  • Removed: scheduled for deletion.

Dirty checking: at flush time (usually commit), Hibernate compares each managed entity with its snapshot and issues UPDATEs for whatever changed. You don't call save() after modifying a managed entity:

@Transactional
public void applyMonthlyFee(String number) {
    Account acc = accounts.findByNumber(number).orElseThrow();
    acc.debit(new BigDecimal("50.00"));      // no save() needed: UPDATE is issued at commit
}

The persistence context also guarantees one Java object per row per transaction: loading the same account twice returns the same instance and runs one query.

4. Spring Data JPA repositories

public interface AccountRepository extends JpaRepository<Account, Long> {

    Optional<Account> findByNumber(String number);                     // derived query

    List<Account> findByCustomerIdAndStatus(Long customerId, Status status);

    boolean existsByNumber(String number);

    @Query("""
           select a from Account a
           where a.status = :status and a.balance < :threshold
           """)
    Page<Account> findLowBalance(@Param("status") Status status,
                                 @Param("threshold") BigDecimal threshold,
                                 Pageable pageable);                   // pagination + sorting

    @Query(value = "select * from account where lower(number) = lower(:n)", nativeQuery = true)
    Optional<Account> findByNumberNative(@Param("n") String n);       // plain SQL when you need it
}
  • JpaRepository gives you save, findById, findAll, deleteById, count, paging and more.
  • Derived queries parse the method name: findBy...And...OrderBy...Desc. Great for simple lookups; switch to @Query when names get long.
  • @Query uses JPQL, which queries entities and fields (Account, a.balance), not tables and columns. nativeQuery = true runs plain SQL.
  • Pagination: PageRequest.of(page, size, Sort.by("postedAt").descending()). Page also runs a count query; Slice skips it when you only need "is there a next page?".

Projections: read only what you need

For read-only screens, don't load full entities. Project straight into a DTO:

public record StatementLine(LocalDate valueDate, String reference, String direction,
                            BigDecimal amount, String narration) { }

@Query("""
       select new ng.itlearning.bank.statement.StatementLine(t.valueDate, t.reference, t.direction, t.amount, t.narration)
       from Txn t
       where t.account.number = :number and t.valueDate between :from and :to
       order by t.postedAt
       """)
List<StatementLine> statement(String number, LocalDate from, LocalDate to);

Projections select only the needed columns, never trigger lazy loading, and produce no managed entities (no dirty-checking overhead). Interface-based and record-based projections in derived queries work too.

5. The N+1 select problem

List<Account> accounts = accountRepository.findByStatus(Status.ACTIVE);   // 1 query: 500 accounts
for (Account a : accounts) {
    System.out.println(a.getCustomer().getFullName());                     // +1 query per account
}

With customer mapped LAZY, each getCustomer().getFullName() triggers a separate SELECT from customer: 1 + 500 queries. With EAGER it's no better: Hibernate often loads each customer with its own query anyway. Each query is fast; 501 round trips are not. In logs it looks like the same select ... from customer where id=? repeated hundreds of times.

Fixes:

  1. Fetch join in JPQL: load accounts and their customers in one query.

    @Query("select a from Account a join fetch a.customer where a.status = :status")
List<Account> findActiveWithCustomer(Status status);

  2. Entity graph on a repository method:

    @EntityGraph(attributePaths = "customer")
List<Account> findByStatus(Status status);

  3. DTO projection (section 4): select exactly the columns needed, joined in SQL.

  4. Batch fetching as a safety net: spring.jpa.properties.hibernate.default_batch_fetch_size=50 makes Hibernate load lazy associations in batches (where id in (?, ?, ...)), turning N+1 into 1 + N/50.

Caveat: fetch-joining a collection (join fetch c.accounts) together with pagination makes Hibernate paginate in memory (it warns: HHH90003004: firstResult/maxResults specified with collection fetch). Page the parent IDs first, then fetch their children in a second query.

How to catch N+1 before production: enable SQL logging in development, look at the statement count per request (Hibernate statistics: spring.jpa.properties.hibernate.generate_statistics=true), and write tests that assert the number of queries for key endpoints.

6. Transactions with @Transactional

@Service
public class TransferService {
    private final AccountRepository accounts;
    private final LedgerRepository ledger;

    @Transactional
    public TransferReceipt transfer(TransferRequest r) {
        Account from = accounts.findByNumberForUpdate(r.fromAccount()).orElseThrow(...);
        Account to = accounts.findByNumberForUpdate(r.toAccount()).orElseThrow(...);
        from.debit(r.amount());
        to.credit(r.amount());
        ledger.save(LedgerEntry.debit(r.clientReference(), from, r.amount()));
        ledger.save(LedgerEntry.credit(r.clientReference(), to, r.amount()));
        return new TransferReceipt(r.clientReference(), Instant.now());
    }   // commit: dirty checking flushes the two balance UPDATEs and the INSERTs
}

Spring wraps the bean in a proxy that begins a transaction before the method, commits after it, and rolls back on unchecked exceptions (RuntimeException, Error). The JDBC code from topic 3.5 is what it does underneath.

What trips people up:

  • Self-invocation: calling a @Transactional method from another method in the same class bypasses the proxy, so no transaction starts. Put it in a separate bean, or make the outer method transactional.
  • Checked exceptions don't roll back by default. Use unchecked domain exceptions, or @Transactional(rollbackFor = Exception.class).
  • Only public methods called through the proxy are transactional.
  • @Transactional(readOnly = true) on read methods lets Hibernate skip dirty checking and may route to a read replica.
  • Keep transactions short: no HTTP calls to partners inside them (topic 3.2).
  • Use jakarta.transaction.Transactional or org.springframework.transaction.annotation.Transactional; prefer Spring's, which has more options.

Locking with JPA

Optimistic: the @Version field above. Every update runs UPDATE ... SET ..., version = version + 1 WHERE id = ? AND version = ?; if another transaction changed the row first, Hibernate throws ObjectOptimisticLockingFailureException, which you map to HTTP 409 or retry.

Pessimistic: lock the row for the rest of the transaction (SELECT ... FOR UPDATE), matching topic 3.2:

@Lock(LockModeType.PESSIMISTIC_WRITE)
@Query("select a from Account a where a.number = :number")
Optional<Account> findByNumberForUpdate(String number);

For transfers, lock both accounts in a consistent order (by number or id) to avoid deadlocks.

7. Open Session in View: switch it off

By default Spring Boot keeps the persistence context open for the whole web request (spring.jpa.open-in-view=true, with a startup warning), so lazy loading works even in controllers and JSON serialisation. That hides N+1 problems and holds database connections for the entire request, including JSON writing. Set it to false, load what each use case needs in the service (fetch joins, projections), and return DTOs. A LazyInitializationException after that change tells you exactly where data was being loaded by accident.

Worked example: a statement endpoint that runs two queries, not 500

@Transactional(readOnly = true)
public StatementResponse statement(String number, LocalDate from, LocalDate to, int page) {
    AccountHeader header = accounts.findHeader(number)                         // 1: projection with customer name
            .orElseThrow(() -> new AccountNotFoundException(number));
    Slice<StatementLine> lines = txns.statementPage(number, from, to,
            PageRequest.of(page, 50, Sort.by("postedAt", "id")));             // 2: projection, paged
    return new StatementResponse(header, lines.getContent(), lines.hasNext());
}

Two SQL statements regardless of statement length, no entities loaded, no lazy-loading surprises, and the transaction is read-only. Compare that with returning account.getTransactions() from the entity: one query for the account, one for the customer, and a collection load of every transaction the account ever had.

Common mistakes

  • ddl-auto=update in shared environments.
  • EnumType.ORDINAL.
  • EAGER associations, or entities in toString()/JSON.
  • Mapping unbounded @OneToMany collections and loading them.
  • N+1 queries hidden by Open Session in View.
  • Calling a @Transactional method from the same class.
  • Expecting checked exceptions to roll back.
  • save() calls everywhere "just in case", or saveAll in loops without batching (hibernate.jdbc.batch_size).

Practice

  1. Map Customer, Account and Txn to your Flyway schema from topic 3.4 with ddl-auto=validate. Make startup fail by renaming a column in a migration, read the error, and fix it.
  2. Write an endpoint listing 200 active accounts with customer names. Turn on SQL logging, count the queries, then fix the N+1 three ways (fetch join, entity graph, projection) and compare the SQL.
  3. Implement transfer with @Transactional and pessimistic locking. Write a test that runs 20 concurrent transfers and asserts the total balance is unchanged.
  4. Add @Version to Customer, update the same customer from two threads, and map the resulting exception to a 409 Problem Detail.
