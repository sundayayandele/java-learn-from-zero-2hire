Week 23 · Module 8: Git, Docker & CI/CD

What you will be able to do

  • Deploy a containerised Spring Boot service to a VPS, AWS (ECS Express Mode / Fargate), Azure Container Apps and Google Cloud Run, from CI.
  • Configure health checks, graceful shutdown and readiness so deployments cause no failed requests.
  • Choose a deployment strategy: rolling, blue-green, canary, and know how to roll back fast.
  • Run database migrations safely alongside deployments (expand and contract).
  • Manage configuration and secrets per environment, and keep costs under control.

Why this matters in a bank or fintech

"It works in CI" is not the end; customers only benefit when the change is running safely in production. Banks care about deployment as much as code: a failed release during month-end salary payments is a serious incident. Zero-downtime deployments, fast rollback and safe migrations are what let teams release often without fear, and they are standard system-design and DevOps interview topics.

1. What a deployable service needs

Before choosing a platform, make the service easy to run anywhere:

  • Immutable image tagged with the commit SHA (topic 8.2).
  • Configuration from the environment (SPRING_DATASOURCE_URL, SPRING_PROFILES_ACTIVE), secrets from the platform's secret store (topic 6.5).
  • Health endpoints: liveness (/actuator/health/liveness) answers "is the process alive?"; readiness (/actuator/health/readiness) answers "can it take traffic now?" (database reachable, warmed up). Enable them with management.endpoint.health.probes.enabled=true (on by default on Kubernetes).
  • Graceful shutdown: on SIGTERM, stop accepting new requests and finish in-flight ones:
server.shutdown=graceful
spring.lifecycle.timeout-per-shutdown-phase=30s
  • Stateless instances: no local session state or local files that matter, so any instance can serve any request and instances can be replaced freely.
  • Logs to stdout in a structured format (Spring Boot: logging.structured.format.console=ecs or logstash), collected by the platform.

The Phase 1 deployment guide has sizing and the full commands for each platform; this lesson focuses on doing it safely and repeatably from CI.

VPS from CI

# deploy/vps-deploy.sh, run by the pipeline with an SSH deploy key stored in the production environment
ssh deploy@wallet.example.ng "
  cd /srv/wallet &&
  export APP_IMAGE=ghcr.io/acme/wallet-api:$GIT_SHA &&
  docker compose pull app &&
  docker compose up -d app &&
  docker image prune -f"
curl --fail --retry 10 --retry-delay 5 https://wallet.example.ng/actuator/health/readiness

A single VPS has a short gap while the container restarts; run two app containers behind Caddy (or use a blue-green pair, section 3) to avoid it.

Azure Container Apps (CLI from a pipeline)

az containerapp update --name wallet-api --resource-group rg-wallet-prod \
  --image ghcr.io/acme/wallet-api:$GIT_SHA \
  --revision-suffix ${GIT_SHA:0:7}

Container Apps creates a new revision; with multiple-revision mode you can split traffic between revisions for canary releases and switch back instantly.

Google Cloud Run

gcloud run deploy wallet-api --image europe-west1-docker.pkg.dev/acme/apps/wallet-api:$GIT_SHA \
  --region europe-west1 --no-traffic --tag canary
gcloud run services update-traffic wallet-api --region europe-west1 --to-tags canary=10

Deploying with --no-traffic and a tag gives the new revision its own URL for smoke tests before it receives real traffic.

AWS ECS (Express Mode or a classic service)

The pipeline registers a new task definition revision with the new image and updates the service; ECS performs a rolling deployment, using the load balancer's health checks, and the deployment circuit breaker (deploymentCircuitBreaker: {enable: true, rollback: true}) rolls back automatically if new tasks fail to become healthy.

3. Deployment strategies

Strategy How Pros Cons
Recreate Stop old, start new Simple Downtime
Rolling Replace instances a few at a time, each checked for readiness No downtime, default on most platforms Old and new versions run together briefly
Blue-green Run the new version alongside the old; switch all traffic at once Instant switch and instant rollback Double capacity during the switch
Canary Send a small share of traffic (1–10%) to the new version, watch metrics, then increase Limits blast radius; real-traffic validation Needs good metrics and traffic splitting

During rolling, blue-green and canary releases, two versions run at the same time, so they must both work with the same database schema and the same message formats. That leads to the most important rule of deploying data-backed services.

4. Database migrations without downtime: expand and contract

Flyway runs migrations when the new version starts. If version N+1 renames a column, version N (still running) breaks. Split breaking schema changes across releases:

  1. Expand: add the new column/table (nullable or with a default); version N ignores it. Deploy code that writes both old and new.
  2. Migrate: backfill existing rows (in batches, outside peak hours for big tables).
  3. Switch: deploy code that reads the new column.
  4. Contract: in a later release, stop writing the old column, then drop it.

Other rules: never edit an applied migration; avoid long locks on large tables (add indexes with CREATE INDEX CONCURRENTLY in a migration with -- flyway:executeInTransaction=false); test migrations against a copy of production-sized data; take a backup or snapshot before risky changes.

5. Rolling back

  • Application rollback should take one command or one click: redeploy the previous image SHA, switch traffic back to the previous revision, or let the platform's circuit breaker do it.
  • Because of expand and contract, the previous version still works with the current schema, so rollback does not need a database rollback. Forward-fix schema problems with a new migration rather than undoing applied ones.
  • Use feature flags to switch off a risky feature without redeploying.
  • Decide rollback criteria in advance: error rate above X%, p95 latency above Y ms, failed smoke tests.

6. After deployment

  • Smoke tests against the new version (topic 7.3) as a pipeline step.
  • Watch the dashboards (error rate, latency, saturation; Phase 3 builds them properly).
  • Record the deployment: which SHA, when, by whom, approved by whom. Many banks link it to a change ticket automatically from the pipeline.

7. Cost and environments

  • Separate staging and production (separate cloud accounts, subscriptions or projects where possible), with production data never copied to lower environments unmasked.
  • Scale non-production to zero or tear it down after use; set budget alerts on every cloud account.
  • Right-size containers from real metrics (Phase 1 sizing table is a starting point).

Common mistakes

  • No readiness probe, so traffic hits instances that are still starting.
  • Abrupt shutdown that kills in-flight payments during deploys.
  • Renaming or dropping a column in the same release as the code change.
  • Rollback that requires a database restore.
  • Deploying latest, or not knowing which commit is in production.
  • Manual production deployments from a laptop.
  • Forgetting to delete a test environment and receiving a cloud bill.

Practice

  1. Enable liveness and readiness probes and graceful shutdown in your capstone; prove with a load test (hey or k6) that a redeploy causes no failed requests.
  2. Deploy the capstone from CI to one managed platform (Container Apps, Cloud Run or ECS) and to a VPS, using the commit SHA as the tag.
  3. Perform a canary release (traffic split) and a rollback to the previous revision; time the rollback.
  4. Rename a column using expand and contract across three releases, and write the plan as an ADR.
