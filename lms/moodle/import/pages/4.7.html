Week 13 · Module 4: Spring Boot 4 Fundamentals

Why this topic is here. Like topic 1.9, this is an addition to the ITLearning programme page. Spring Boot treats Kotlin as a first-class language, and many fintechs build new services in it. After this topic you can build the same kind of service from topics 4.1–4.5 in Kotlin, and review a Kotlin Spring pull request with confidence.

What you will be able to do

  • Generate and build a Spring Boot 4 project in Kotlin with Maven, and explain the Kotlin-specific compiler plugins it needs.
  • Write controllers, services, configuration properties and validation in idiomatic Kotlin.
  • Map JPA entities from Kotlin safely, and know when to prefer Spring Data JDBC or plain SQL.
  • Use Spring's Kotlin extensions and null-safety integration, and test Kotlin Spring code.

Why this matters in a bank or fintech

A Kotlin Spring Boot service is still a Spring Boot service: same starters, same Actuator, same PostgreSQL, same deployment. Teams choose Kotlin for concise, null-safe code; the cost is a few framework details you must know, mainly around proxies, JPA and Jackson. Knowing those details is the difference between "I've done a Kotlin tutorial" and "I can work on our Kotlin services".

1. Creating the project

On start.spring.io choose Language: Kotlin, Project: Maven, Spring Boot 4.1.x, Java 21, and the same dependencies as topic 4.1 (Spring Web, Validation, Spring Data JPA, Flyway, PostgreSQL, Actuator).

The generated pom.xml adds Kotlin-specific pieces:

<properties>
  <java.version>21</java.version>
  <kotlin.version>2.4.21</kotlin.version>          <!-- Boot manages a compatible default; override only if needed -->
</properties>

<dependencies>
  <dependency><groupId>org.jetbrains.kotlin</groupId><artifactId>kotlin-reflect</artifactId></dependency>
  <dependency><groupId>org.jetbrains.kotlin</groupId><artifactId>kotlin-stdlib</artifactId></dependency>
  <dependency><groupId>tools.jackson.module</groupId><artifactId>jackson-module-kotlin</artifactId></dependency>
  <!-- ...the usual starters... -->
</dependencies>

<build>
  <sourceDirectory>${project.basedir}/src/main/kotlin</sourceDirectory>
  <testSourceDirectory>${project.basedir}/src/test/kotlin</testSourceDirectory>
  <plugins>
    <plugin>
      <groupId>org.springframework.boot</groupId>
      <artifactId>spring-boot-maven-plugin</artifactId>
    </plugin>
    <plugin>
      <groupId>org.jetbrains.kotlin</groupId>
      <artifactId>kotlin-maven-plugin</artifactId>
      <configuration>
        <args><arg>-Xjsr305=strict</arg></args>          <!-- trust Java nullability annotations -->
        <compilerPlugins>
          <plugin>spring</plugin>                         <!-- all-open for Spring-annotated classes -->
          <plugin>jpa</plugin>                            <!-- no-arg constructors for @Entity -->
        </compilerPlugins>
      </configuration>
      <dependencies>
        <dependency><groupId>org.jetbrains.kotlin</groupId><artifactId>kotlin-maven-allopen</artifactId><version>${kotlin.version}</version></dependency>
        <dependency><groupId>org.jetbrains.kotlin</groupId><artifactId>kotlin-maven-noarg</artifactId><version>${kotlin.version}</version></dependency>
      </dependencies>
    </plugin>
  </plugins>
</build>

What each piece is for:

  • kotlin-reflect: Spring uses Kotlin reflection to understand constructors, default values and nullability.
  • jackson-module-kotlin (Jackson 3 coordinates tools.jackson.module): lets Jackson construct Kotlin classes with default and non-null parameters. Spring Boot registers it automatically.
  • spring compiler plugin (all-open): Kotlin classes are final by default, but Spring creates proxies (subclasses) for @Configuration, @Transactional, @Async and similar. The plugin opens classes annotated with Spring stereotypes automatically, so you don't scatter open everywhere.
  • jpa compiler plugin (no-arg): generates the no-argument constructor JPA needs for @Entity, @Embeddable and @MappedSuperclass classes.
  • -Xjsr305=strict: makes Kotlin treat Spring's nullability annotations as real nullability. Spring Framework 7 annotates its APIs with JSpecify, which Kotlin 2.x understands, so Spring APIs appear with correct ? types in Kotlin.

Spring Boot 4 requires Kotlin 2.2 or later. Spring Boot also supports Gradle with the Kotlin DSL, which many Kotlin teams prefer; the concepts are identical.

2. The application, controllers and services

@SpringBootApplication
@ConfigurationPropertiesScan
class BankApplication

fun main(args: Array<String>) {
    runApplication<BankApplication>(*args)          // Kotlin extension from Spring Boot
}
data class TransferRequest(
    @field:NotBlank @field:Pattern(regexp = "\\d{10}") val fromAccount: String,
    @field:NotBlank @field:Pattern(regexp = "\\d{10}") val toAccount: String,
    @field:NotNull @field:DecimalMin("1.00") @field:Digits(integer = 13, fraction = 2) val amount: BigDecimal,
    @field:NotBlank @field:Size(max = 100) val narration: String,
    @field:NotBlank @field:Size(max = 64) val clientReference: String,
)

data class TransferResponse(val reference: String, val status: String, val postedAt: Instant)

@RestController
@RequestMapping("/api/v1/transfers")
class TransferController(private val transfers: TransferService) {      // constructor injection, no @Autowired

    @PostMapping
    fun create(@Valid @RequestBody request: TransferRequest): ResponseEntity<TransferResponse> {
        val receipt = transfers.transfer(request)
        return ResponseEntity.created(URI.create("/api/v1/transfers/${receipt.reference}"))
            .body(TransferResponse(receipt.reference, "COMPLETED", receipt.postedAt))
    }

    @GetMapping("/{reference}")
    fun get(@PathVariable reference: String): TransferResponse =
        transfers.find(reference) ?: throw TransferNotFoundException(reference)
}

Two Kotlin specifics here:

  • Annotation use-site targets. A Kotlin constructor property is a parameter, a field and a getter at once. Bean Validation annotations must target the field (@field:NotBlank), or they may be placed on the constructor parameter and ignored. (Recent Kotlin versions apply annotations to both parameter and field by default, but explicit @field: remains the safe, readable choice and you will see it in most codebases.)
  • Null safety meets HTTP. A request missing a non-null field like narration fails during JSON deserialisation (HTTP 400) before validation even runs. Make fields nullable (String?) only when they're genuinely optional.

Services look like Java, with less ceremony:

@Service
class TransferService(
    private val accounts: AccountRepository,
    private val ledger: LedgerRepository,
    private val clock: Clock,
) {
    @Transactional
    fun transfer(r: TransferRequest): TransferReceipt {
        val (first, second) = listOf(r.fromAccount, r.toAccount).sorted()      // consistent lock order
        val locked = listOf(first, second).associateWith {
            accounts.findByNumberForUpdate(it) ?: throw AccountNotFoundException(it)
        }
        val from = locked.getValue(r.fromAccount)
        val to = locked.getValue(r.toAccount)
        from.debit(r.amount)
        to.credit(r.amount)
        ledger.saveAll(LedgerEntry.pair(r.clientReference, from, to, r.amount))
        return TransferReceipt(r.clientReference, Instant.now(clock))
    }

    @Transactional(readOnly = true)
    fun find(reference: String): TransferResponse? = ledger.findTransfer(reference)
}

Spring Data repositories can return nullable types instead of Optional:

interface AccountRepository : JpaRepository<Account, Long> {
    fun findByNumber(number: String): Account?          // null when absent: idiomatic Kotlin

    @Lock(LockModeType.PESSIMISTIC_WRITE)
    @Query("select a from Account a where a.number = :number")
    fun findByNumberForUpdate(number: String): Account?
}

3. Configuration properties

Kotlin data classes bind naturally with constructor binding:

@ConfigurationProperties(prefix = "bank.transfer")
@Validated
data class TransferProperties(
    @field:DecimalMin("0.01") val dailyLimit: BigDecimal,
    @field:DecimalMin("0.01") val singleLimit: BigDecimal,
    val feeCap: BigDecimal = BigDecimal("2000.00"),          // Kotlin default values work as property defaults
    val lockTimeout: Duration = Duration.ofSeconds(2),
)

A missing non-null property without a default fails startup, which is the behaviour topic 4.4 asked for.

4. JPA entities in Kotlin: be careful

JPA's model (mutable objects, no-arg constructors, proxies, identity semantics) fits Kotlin less well than plain data. Guidelines that keep you out of trouble:

@Entity
@Table(name = "account")
class Account(                                             // a regular class, NOT a data class
    @Column(nullable = false, unique = true, length = 10)
    val number: String,

    @Enumerated(EnumType.STRING)
    @Column(nullable = false)
    val product: Product,

    @ManyToOne(fetch = FetchType.LAZY, optional = false)
    @JoinColumn(name = "customer_id")
    val customer: Customer,
) {
    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    var id: Long? = null                                   // null until persisted

    @Column(nullable = false, precision = 19, scale = 2)
    var balance: BigDecimal = BigDecimal.ZERO
        protected set                                      // only the entity changes its balance

    @Version
    var version: Long = 0

    fun debit(amount: BigDecimal) {
        check(balance >= amount) { "Insufficient funds" }
        balance -= amount
    }

    fun credit(amount: BigDecimal) { balance += amount }

    override fun equals(other: Any?) = other is Account && number == other.number
    override fun hashCode() = number.hashCode()
    override fun toString() = "Account(number=$number)"   // never include lazy associations
}
  • Don't use data class for entities. Generated equals/hashCode/toString include every property, including lazy associations (triggering queries or LazyInitializationException) and the mutable id.
  • Rely on the jpa plugin for the no-arg constructor and the all-open configuration for @Entity classes (start.spring.io configures allOpen annotations for jakarta.persistence.Entity, Embeddable and MappedSuperclass in Gradle; in Maven add them via <option>all-open:annotation=jakarta.persistence.Entity</option> if lazy-loading proxies are needed).
  • Keep the database ID nullable (Long?) because it is assigned on insert.

Because of this friction, many Kotlin teams use Spring Data JDBC or Spring's JdbcClient (topic 3.5) with immutable data classes for simpler aggregates, and reserve JPA for complex domains. Both are valid; be consistent within a service.

5. Kotlin extensions in Spring

Spring ships Kotlin-friendly APIs:

  • runApplication<App>(*args) instead of SpringApplication.run(...).
  • Bean definition DSL (beans { bean<FeeService>() }) as an alternative to @Bean methods.
  • Router DSL for functional endpoints: router { GET("/health-check") { ok().body("UP") } }.
  • Reified generics: restClient.get().uri("/rates").retrieve().body<List<Rate>>() instead of ParameterizedTypeReference.
  • JdbcClient and RestClient extensions, and coroutine support (suspend controller functions) for WebFlux applications.

6. Testing

@WebMvcTest(TransferController::class)
class TransferControllerTest(@Autowired val mvc: MockMvc) {

    @MockitoBean
    lateinit var transfers: TransferService

    @Test
    fun `rejects a negative amount`() {                    // backtick names read like specifications
        mvc.post("/api/v1/transfers") {                    // Spring's Kotlin MockMvc DSL
            contentType = MediaType.APPLICATION_JSON
            content = """
                {"fromAccount":"0123456789","toAccount":"9876543210","amount":-5,
                 "narration":"rent","clientReference":"r-1"}
            """.trimIndent()
        }.andExpect {
            status { isBadRequest() }
        }
    }
}

Many Kotlin teams use MockK (a Kotlin-native mocking library, with springmockk for Spring integration) instead of Mockito, and Kotest or JUnit 5 for tests. JUnit 5 with Mockito, as above, works perfectly well and keeps one toolset across Java and Kotlin services.

Worked example: the same service, two languages

Take the transfer service you built in Java in topics 4.1–4.5 and port it:

Java Kotlin
Record DTOs with Bean Validation Data classes with @field: annotations
Optional<Account> from repositories Account?
@ConfigurationProperties record @ConfigurationProperties data class with defaults
Entity class with getters Class with val/var properties and protected set
SpringApplication.run runApplication<...>()
MockMvc builder MockMvc Kotlin DSL

Same Flyway migrations, same PostgreSQL, same Actuator endpoints, same Docker image and deployment. Usually 30–40% fewer lines. The behaviour, and the tests that prove it, should be identical.

Common mistakes

  • Forgetting the spring (all-open) plugin, so @Transactional or @Configuration proxies fail on final classes.
  • data class JPA entities.
  • Validation annotations without @field:, silently not validated.
  • Using !! on values from Spring APIs instead of handling null.
  • Missing jackson-module-kotlin, so request bodies fail to deserialise.
  • Mixing Java and Kotlin styles randomly in one codebase.

Practice

  1. Generate a Kotlin Spring Boot 4.1 project with Maven and build the account and transfer endpoints from topic 4.2, including the Problem Details advice.
  2. Remove the spring compiler plugin and observe what fails, then restore it. Write two sentences explaining why.
  3. Map Account as a regular Kotlin class with the jpa plugin. Then try it as a data class with a lazy customer association, call toString() outside a transaction, and explain the error.
  4. Write @WebMvcTest tests with the Kotlin MockMvc DSL for a valid transfer, a validation failure and an insufficient-funds error.
