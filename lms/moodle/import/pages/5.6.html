Week 17 · Module 5: API Design & Integration

What you will be able to do

  • Run a 30–45 minute junior system design conversation: clarify requirements, estimate load, sketch components, design the API and data model, and discuss failures and trade-offs.
  • Explain the building blocks every backend uses: load balancers, stateless services, caches, queues, read replicas, object storage and CDNs.
  • Make back-of-the-envelope estimates (requests per second, storage per year) and use them to justify a design.
  • Discuss consistency, availability and idempotency in money-moving systems, and present your own capstone's architecture views confidently.

Why this matters in a bank or fintech

Junior interviews increasingly include a light design round: "design a transfer API", "design a URL shortener", "design a notification service", "how would your capstone handle ten times the traffic?". Nobody expects a junior to design a global payment network. Interviewers want to see that you ask questions before drawing boxes, that your numbers are roughly right, that you know what a cache or a queue is for, and that you think about failure and money correctness. Your capstones already have solution, logical, technical, infrastructure and cloud views; this lesson teaches you to talk through them, which is exactly what a design round is. Phase 3 goes deeper into distributed systems.

1. A repeatable structure for the conversation

Step (time) What you do Example for "design a bank transfer API"
1. Requirements (5 min) Functional: what it must do. Non-functional: scale, latency, availability, consistency, security, compliance Intra-bank and inter-bank transfers, statements; 99.9% availability; never lose or duplicate money; audit trail
2. Estimates (5 min) Users, requests per second, data size, growth 2M active customers × 3 transfers/day ≈ 6M/day ≈ 70/s average, ~10× at peak ≈ 700/s
3. API (5 min) Main endpoints and their contracts POST /transfers with Idempotency-Key, GET /accounts/{id}/statement?cursor=
4. Data model (5 min) Tables and keys, what must be unique and consistent Double-entry journal/posting (Phase 1 Capstone 1), unique reference
5. High-level design (10 min) Boxes and arrows for the happy path Load balancer → stateless API instances → PostgreSQL primary; NIP adapter; notifications via a queue
6. Deep dive and failures (10 min) Bottlenecks, failure modes, trade-offs Row locks on hot accounts, provider timeouts (pending + status query), replica lag on statements
7. Wrap-up (2 min) Summarise, list what you'd do next Monitoring, rate limits, partitioning postings by month

Say your assumptions out loud ("I'll assume 2 million active customers; tell me if that's wrong"). Interviewers reward structure and reasoning more than the "right" architecture.

2. Back-of-the-envelope estimates

Useful numbers:

  • 1 day ≈ 86,400 s ≈ 10⁵ s. So 1 million requests per day ≈ 12 per second on average; assume peaks of 5–10× the average.
  • One PostgreSQL row of a transaction with indexes ≈ 200–500 bytes. 6M transfers/day × 2 postings × 300 B ≈ 3.6 GB/day ≈ 1.3 TB/year: plan partitioning and archiving.
  • A well-tuned Spring Boot instance serves hundreds to a few thousand simple requests per second; the database is usually the first bottleneck.
  • Rough latencies: memory ~100 ns; SSD read ~100 µs; same-datacentre network round trip ~0.5 ms; a cross-region round trip ~50–150 ms; a payment provider call often 200 ms–2 s.

Estimates decide the design: 70 requests per second fits comfortably on two application instances and one database; 50,000 per second needs sharding and a very different conversation.

3. Building blocks

Load balancer. Spreads requests across instances, removes unhealthy ones using health checks (your Actuator readiness probe) and terminates TLS. Requires stateless application instances: no in-memory sessions or caches that must be consistent; state lives in the database, Redis or the token.

Horizontal scaling. Add instances behind the load balancer. Works for stateless services; it doesn't scale the database, and it breaks in-memory assumptions (local locks, in-memory rate limits, @Scheduled jobs on every instance, topic 4.8).

Cache. Keeps hot, read-mostly data close (Redis, topic 3.6; or an in-process cache such as Caffeine). Common patterns: cache-aside (read cache, on miss load from the database and populate) and write-through. Every cache needs an expiry (TTL) and an invalidation story. Never cache balances used for authorising debits; cache FX reference rates, product catalogues, bank lists and name-enquiry results for minutes.

Message queue or log (RabbitMQ, Kafka). Decouples a fast request from slow follow-up work: the API commits the transfer and publishes TransferCompleted; SMS, email, fraud scoring and analytics consume it at their own pace and retry independently. Gives buffering for spikes. Costs: eventual consistency, duplicate deliveries (consumers must be idempotent), and more operations (Phase 3).

Read replicas. Copies of the database that serve reads (statements, reports) to take load off the primary. Replication is usually asynchronous, so a replica can be seconds behind: never read a balance from a replica to authorise a payment, and be careful with "read your own writes" (a customer who just transferred expects to see it).

Partitioning and sharding. Partitioning splits a big table inside one database (for example postings by month) for faster queries and archiving. Sharding splits data across databases by a key (customer id); powerful but complex. Mention it as a later step, with the reason.

Object storage and CDN. Statements as PDFs, KYC documents and exports go to S3/Blob/GCS, not database rows; a CDN serves static assets near users.

Rate limiting and API gateway. Protect services from abuse and noisy partners (topic 5.3); gateways centralise authentication, rate limits and routing.

4. Consistency, availability and money

  • Strong consistency for money: a debit and its credit commit together or not at all (one database transaction, or a saga with compensations across services in Phase 3).
  • CAP in one sentence: when the network between parts of a system fails, you must choose between refusing some requests (consistency) and possibly serving stale or conflicting data (availability). Payment authorisation chooses consistency; a product catalogue can choose availability.
  • Idempotency everywhere (topic 5.3): clients retry, queues redeliver, providers resend webhooks.
  • Unknown outcomes: a timeout from a provider is not a failure; record PENDING and resolve with status queries (Phase 2 Capstones 7 and 8).
  • Auditability: append-only journals and event logs make it possible to explain every balance.

5. Worked example: a notification service

Requirements: send SMS and email for transfers and logins; 5M notifications/day (≈ 60/s average, ~600/s peak); must not delay transfers; tolerate provider outages; no duplicate OTPs.

Design: the transfer service writes TransferCompleted to an outbox table in its transaction; a relay publishes it to a queue; a notification service consumes, renders the template, looks up preferences (cached), and calls an SMS provider through an adapter with timeouts, retries with backoff and a circuit breaker; failed messages go to a dead-letter queue for retry or inspection; a notification table with a unique (event_id, channel) prevents duplicates. Trade-offs to mention: SMS can arrive seconds later (acceptable); OTPs need a separate fast path with short expiry; the provider is the bottleneck, so throttle to its rate limit.

6. Talking through your capstone

Use your capstone's architecture pack as a script:

  1. Solution view: who uses it and what it integrates with (30 seconds).
  2. Logical view: the capabilities and data, and the invariant you protect (for example "postings always balance").
  3. Technical view: how a request flows through controller, service and repository, and where transactions and security apply.
  4. Infrastructure and cloud views: how it runs, scales and recovers.
  5. What breaks first at 10× load, and what you'd change: for example, the fee-income row becomes a hot lock; statements move to a replica; postings get partitioned by month.

Common mistakes

  • Drawing boxes before asking a single question.
  • Adding Kafka, Kubernetes and microservices to a problem that fits on two instances and one database.
  • Caching data that must be exactly current (balances, limits).
  • Ignoring failure: what happens when the provider times out, the queue redelivers, or the replica lags?
  • Never stating numbers, or stating impossible ones.
  • Forgetting security and audit in a banking design.

Practice

  1. Do the seven-step structure for "design a bill payments API" in 35 minutes, out loud, with a timer; record yourself and review.
  2. Estimate requests per second and storage per year for your capstone at 1 million customers.
  3. Add a "What breaks first at 10× load" section to your capstone README with three bottlenecks and the fix for each.
  4. Redraw the notification-service example as a Mermaid diagram and add the failure paths.
  5. Pair with a peer: one interviews, one designs "a URL shortener for payment links"; swap roles.
