Why this matters in a bank or fintech

A typical payments service spends 90% of each request waiting: on the database, the card switch, a fraud API, a notification provider. With classic thread-per-request servers, each waiting request holds an expensive operating-system thread, so a server tops out at a few hundred concurrent requests and teams reach for complex reactive frameworks to go further. Java 21's virtual threads let the same simple, blocking code handle tens of thousands of concurrent requests. Lagos fintech job ads now mention them by name, and Spring Boot turns them on with one property.

1. The problem virtual threads solve

A platform thread is a thin wrapper around an operating-system thread. OS threads are expensive: each reserves a large stack (often around 1 MB), is scheduled by the OS kernel, and costs microseconds to switch. A server can comfortably run a few thousand at most.

In a thread-per-request server, a request that waits 200 ms for the database still occupies its thread for those 200 ms. With a pool of 200 threads, the 201st concurrent request waits in a queue even though the CPU is idle. Teams worked around this in two ways: bigger pools (more memory, more context switching) or reactive programming (WebFlux, CompletableFuture chains), which avoids blocking but makes code harder to write, read, debug and profile.

2. What a virtual thread is

A virtual thread (JEP 444, final in Java 21) is a java.lang.Thread managed by the JVM rather than the OS. Many virtual threads are scheduled onto a small pool of platform threads called carrier threads (a ForkJoinPool with about one carrier per core).

When a virtual thread performs a blocking operation (socket read, Thread.sleep, a BlockingQueue.take, a JDBC call over the network), the JVM unmounts it: its stack is saved to the heap and the carrier is freed to run another virtual thread. When the I/O completes, the virtual thread is mounted again, possibly on a different carrier, and continues as if nothing happened.

Platform thread Virtual thread
Managed by Operating system JVM
Memory ~1 MB reserved stack Small; stack grows on the heap as needed
Creation cost High Very low (like creating an object)
Practical count per JVM Thousands Millions
Blocking I/O Holds the OS thread Releases the carrier
Best for CPU-bound work, long-running background loops Many concurrent, mostly-waiting tasks
Pool them? Yes No: create one per task

Your code does not change: it still blocks, still uses try/catch, still reads top to bottom, and stack traces and debuggers work normally. That is the point.

3. Creating virtual threads

Thread vt = Thread.ofVirtual().name("payment-", 0).start(() -> processPayment(p));
Thread.startVirtualThread(() -> sendSms(msg));

try (ExecutorService executor = Executors.newVirtualThreadPerTaskExecutor()) {
    for (Payment p : payments) {
        executor.submit(() -> processPayment(p));     // one new virtual thread per task
    }
}   // close() waits for all submitted tasks to finish

A classic demonstration:

try (var executor = Executors.newVirtualThreadPerTaskExecutor()) {
    IntStream.range(0, 100_000).forEach(i ->
            executor.submit(() -> {
                Thread.sleep(Duration.ofSeconds(1));   // simulate a 1 s downstream call
                return i;
            }));
}
// Finishes in about 1 second. With a 200-thread platform pool it would take about 500 seconds.

In Spring Boot

One property switches Tomcat's request handling, @Async tasks and several other executors to virtual threads:

spring.threads.virtual.enabled=true

You will turn it on in Module 4 and measure the difference.

4. When virtual threads help, and when they don't

Virtual threads increase throughput for workloads with many concurrent tasks that spend most of their time blocked. They do not make any single task faster, and they do nothing for CPU-bound work: if 10,000 virtual threads all calculate interest, they still share the same 8 cores.

Downstream limits still apply. Ten thousand virtual threads calling a database with a connection pool of 20 will still have only 20 queries running; the rest wait for a connection. That is fine (waiting is now cheap), but it means:

  • Do not use the thread count to limit concurrency to a downstream system. Use a Semaphore (topic 2.2) or the connection pool.
  • Size connection pools for what the database can handle, not for the number of threads.

5. Things that change in how you write code

Don't pool virtual threads

Pools exist because platform threads are expensive. Virtual threads are cheap, so create one per task and let it die. A "pool of virtual threads" adds nothing but complexity.

Pinning

In some situations a virtual thread cannot unmount while blocked and keeps its carrier busy; this is called pinning. In Java 21, the main cause was blocking inside a synchronized block or method. With only a handful of carriers, a few pinned threads could stall the whole application. Since Java 24 (JEP 491), synchronized no longer pins, so on Java 25 this is largely solved. Blocking inside native code (JNI) still pins.

What this means in practice:

  • On Java 21, prefer ReentrantLock over synchronized around blocking I/O in hot paths, and upgrade drivers and libraries to versions that already do this. You can detect pinning with JDK Flight Recorder (jdk.VirtualThreadPinned events).
  • On Java 24+, synchronized is fine again.

ThreadLocal with care

ThreadLocal gives each thread its own copy of a value. With platform-thread pools it was often used as a per-thread cache (for example, a SimpleDateFormat per thread). With millions of short-lived virtual threads, such caches are recreated constantly and waste memory. Use immutable shared objects instead (such as DateTimeFormatter), and keep ThreadLocal for genuine per-request context. For that use case, scoped values are the modern replacement.

Scoped values

A ScopedValue (final in Java 25, preview in 21–24) carries an immutable value through a call chain, visible to everything called within a scope and automatically gone afterwards:

static final ScopedValue<String> CORRELATION_ID = ScopedValue.newInstance();

ScopedValue.where(CORRELATION_ID, request.header("X-Correlation-Id"))
        .run(() -> transferService.transfer(request));   // any code inside can read CORRELATION_ID.get()

Unlike ThreadLocal, it cannot be modified by the code that reads it, cannot leak past the scope, and is cheap to inherit by child tasks.

6. Structured concurrency

With ExecutorService and CompletableFuture, subtasks are not tied to the code that started them. If one of three parallel calls fails, the other two keep running (wasting resources), and if the parent is cancelled, its children may never find out. Errors and cancellation are easy to get wrong.

Structured concurrency applies the idea of structured programming to concurrency: subtasks started in a block must finish before the block exits, just as a method call finishes before the next line runs. Failures and cancellation propagate automatically.

Java's API is StructuredTaskScope. It has been a preview API since Java 21 and was redesigned in Java 25 (JEP 505); at the time of writing it is still in preview, so you must compile and run with --enable-preview, and the API may change before it becomes final. Read it to understand the idea; check the JEP for your JDK version before using it in production.

Java 25 style:

// compile/run with: --release 25 --enable-preview
Dashboard load(String customerId) throws InterruptedException {
    try (var scope = StructuredTaskScope.open()) {            // default: all must succeed
        Subtask<Account> account = scope.fork(() -> core.account(customerId));
        Subtask<Integer> score   = scope.fork(() -> fraud.score(customerId));
        Subtask<Integer> points  = scope.fork(() -> loyalty.points(customerId));

        scope.join();     // waits for all; if any fails, cancels the others and throws
        return new Dashboard(account.get(), score.get(), points.get());
    }
}

Java 21 style (the first preview, which you will still meet in articles and code):

try (var scope = new StructuredTaskScope.ShutdownOnFailure()) {
    Subtask<Account> account = scope.fork(() -> core.account(customerId));
    Subtask<Integer> score = scope.fork(() -> fraud.score(customerId));
    scope.join().throwIfFailed();
    return new Dashboard(account.get(), score.get());
}

Each fork runs in its own virtual thread. Compared with the CompletableFuture version in topic 2.1, the code is sequential-looking, failures cancel sibling tasks, nothing outlives the block, and thread dumps show the parent–child relationship. Other policies ("return the first successful result", for example to query two FX-rate providers and use whichever answers first) are available as joiners in Java 25.

Until it is final, the production-ready options on Java 21 are CompletableFuture with a virtual-thread executor, or a virtual-thread-per-task executor with invokeAll.

Worked example: a webhook dispatcher

A payment processor must notify 5,000 merchants of settlement results. Each webhook call takes 100 ms to 3 s, and some merchants are down.

public DispatchReport dispatch(List<Webhook> hooks) {
    var limiter = new Semaphore(500);                  // protect our outbound network and partners
    var ok = new LongAdder();
    var failed = new ConcurrentLinkedQueue<String>();

    try (var executor = Executors.newVirtualThreadPerTaskExecutor()) {
        for (Webhook hook : hooks) {
            executor.submit(() -> {
                limiter.acquire();
                try {
                    http.post(hook.url(), hook.payload(), Duration.ofSeconds(5));   // plain blocking call
                    ok.increment();
                } catch (Exception e) {
                    failed.add(hook.merchantId());
                } finally {
                    limiter.release();
                }
                return null;
            });
        }
    }
    return new DispatchReport(ok.sum(), List.copyOf(failed));
}

Simple blocking code, 5,000 concurrent tasks, at most 500 in flight, no thread pool tuning, and failures collected for a retry run. With a 50-thread platform pool, the same job would take minutes longer.

Common mistakes

  • Expecting virtual threads to speed up CPU-bound work.
  • Pooling virtual threads, or limiting concurrency by pool size instead of a semaphore.
  • Long blocking calls inside synchronized on Java 21 (pinning).
  • Per-thread caches in ThreadLocal.
  • Using preview APIs (structured concurrency) in production without --enable-preview awareness and a plan for API changes.
  • Raising the database connection pool to thousands because "threads are cheap now".
