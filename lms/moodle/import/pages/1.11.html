Week 5 · Module 1: Modern Java & OOP Foundations

What you will be able to do

  • Recognise the design patterns interviewers ask about most (Strategy, Factory, Builder, Template Method, Proxy, Decorator, Observer, Adapter and Singleton) and implement each in modern Java.
  • Explain where Spring itself uses each pattern, so you can answer "which patterns does Spring use?" with examples from your own code.
  • Choose a pattern because it removes a real problem (a growing if/switch, duplicated algorithms, an awkward third-party API), not to decorate code.
  • Spot pattern misuse: needless interfaces, singletons holding mutable state, inheritance where composition is simpler.

Why this matters in a bank or fintech

Financial code changes constantly for business reasons: the regulator adds a levy, a new payment provider is onboarded, fees change for a promotion. Patterns are the shared vocabulary for keeping such changes small. "Each fee rule is a Strategy", "providers sit behind an Adapter", "auditing is a Decorator", "@Transactional works through a Proxy" are sentences you will hear in design reviews and interviews. Interviewers also use patterns to test whether you understand object-oriented design (topic 1.4) beyond definitions: they will ask you to refactor a switch into a Strategy, or explain why a Singleton bean must not keep per-request state.

1. Strategy: one interface, interchangeable algorithms

Problem: a fee calculation grows a new case for every product.

// Before: every new product edits this method (violates the open/closed principle)
BigDecimal fee(Transfer t) {
    return switch (t.channel()) {
        case NIP -> t.amount().compareTo(new BigDecimal("5000")) <= 0 ? new BigDecimal("10.75") : new BigDecimal("26.88");
        case USSD -> new BigDecimal("6.98");
        case INTERNAL -> BigDecimal.ZERO;
    };
}
// After: each rule is a Strategy; adding a channel adds a class, not an edit
public interface FeeRule {
    Channel channel();
    BigDecimal feeFor(Transfer t);
}

@Component
class NipFeeRule implements FeeRule {
    public Channel channel() { return Channel.NIP; }
    public BigDecimal feeFor(Transfer t) {
        return t.amount().compareTo(new BigDecimal("5000")) <= 0 ? new BigDecimal("10.75") : new BigDecimal("26.88");
    }
}

@Service
class FeeCalculator {
    private final Map<Channel, FeeRule> rules;

    FeeCalculator(List<FeeRule> rules) {                       // Spring injects every FeeRule bean
        this.rules = rules.stream().collect(Collectors.toMap(FeeRule::channel, r -> r));
    }

    BigDecimal fee(Transfer t) {
        FeeRule rule = rules.get(t.channel());
        if (rule == null) throw new IllegalStateException("No fee rule for " + t.channel());
        return rule.feeFor(t);
    }
}

With lambdas, a Strategy can be a Function<Transfer, BigDecimal> or a functional interface, which is often enough. Sealed interfaces (topic 1.8) plus switch pattern matching are a legitimate alternative when the set of cases is closed and owned by one team: the compiler then forces you to handle every case. Choose Strategy when new cases arrive often or come from other modules.

In Spring: PasswordEncoder implementations, HandlerMethodArgumentResolver, RetryPolicy, Spring Security's AuthenticationProvider list.

2. Factory: hide which class gets created

A static factory method is the most common form in modern Java: List.of(...), Optional.of(...), Currency.getInstance("NGN"), Money.of("1500.00", "NGN"). Advantages over constructors: a meaningful name, the ability to return a cached instance or a subtype, and validation in one place.

public record Money(BigDecimal amount, Currency currency) {
    public static Money of(String amount, String currency) {
        Currency c = Currency.getInstance(currency);
        return new Money(new BigDecimal(amount).setScale(c.getDefaultFractionDigits(), RoundingMode.UNNECESSARY), c);
    }
}

A factory object chooses an implementation at run time, for example PaymentProviderFactory.forCurrency("GHS"). In Spring, the container is the factory: @Bean methods are factory methods, FactoryBean builds complex objects, and ObjectProvider<T> lets you ask for beans lazily.

3. Builder: readable construction of many optional parts

Use a Builder when an object has many optional fields or must be assembled in steps. Records with more than about five components, especially several of the same type, are hard to call correctly: new Transfer("0123", "0456", amount, null, null, true).

Transfer t = Transfer.builder()
        .from("0123456789").to("0987654321")
        .amount(Money.of("25000.00", "NGN"))
        .narration("Rent October")
        .build();                                             // validate everything here

You will meet Builders constantly in libraries: HttpRequest.newBuilder(), RestClient.builder(), ResponseEntity.status(...).body(...), MockMvcRequestBuilders, test data builders (topic 7.1). Lombok's @Builder generates them (see the Lombok section in topic 1.8).

4. Template Method: fixed algorithm, variable steps

A base class (or a method taking callbacks) fixes the order of steps and lets subclasses or lambdas fill in the variable ones. Every statement import in a bank follows the same skeleton: open the file, validate the header, parse lines, persist in batches, report. Only parsing differs per partner.

abstract class StatementImporter {
    public final ImportReport importFile(Path file) {          // final: the algorithm can't be changed
        try (var lines = Files.lines(file)) {
            validateHeader(file);
            List<Entry> entries = lines.skip(1).map(this::parseLine).toList();
            return persist(entries);
        } catch (IOException e) {
            throw new UncheckedIOException(e);
        }
    }
    protected abstract Entry parseLine(String line);          // the step each partner supplies
    protected void validateHeader(Path file) { /* default rules */ }
    private ImportReport persist(List<Entry> entries) { /* batch insert */ return new ImportReport(entries.size()); }
}

In Spring: JdbcTemplate, TransactionTemplate, RestTemplate (legacy) and RetryTemplate are the callback flavour: Spring runs the fixed steps (get a connection, handle exceptions, release resources) and calls your lambda for the variable part. Prefer callbacks over inheritance in new code.

5. Proxy: the pattern behind most Spring "magic"

A Proxy stands in for an object and adds behaviour around calls: transactions, security checks, caching, retries, metrics. Spring creates proxies around beans annotated with @Transactional, @PreAuthorize, @Cacheable, @Async or @Retryable. Your controller calls the proxy; the proxy starts the transaction, calls your real method, then commits or rolls back.

// Roughly what Spring generates for a @Transactional service
class TransferServiceProxy extends TransferService {
    private final TransferService target;
    private final PlatformTransactionManager tm;
    @Override public Receipt transfer(TransferRequest r) {
        TransactionStatus tx = tm.getTransaction(new DefaultTransactionDefinition());
        try {
            Receipt result = target.transfer(r);
            tm.commit(tx);
            return result;
        } catch (RuntimeException e) {
            tm.rollback(tx);
            throw e;
        }
    }
}

This explains the most common interview question about Spring: a @Transactional method called from another method in the same class runs without a transaction, because the call never goes through the proxy. Topic 4.8 covers proxies in depth.

6. Decorator: add behaviour by wrapping

A Decorator implements the same interface as the object it wraps and adds behaviour, like a Proxy, but you compose it explicitly. Java's I/O classes are the classic example: new BufferedReader(new InputStreamReader(new FileInputStream(f), UTF_8)).

class AuditingProvider implements PaymentProvider {
    private final PaymentProvider delegate;
    private final AuditLog audit;
    AuditingProvider(PaymentProvider delegate, AuditLog audit) { this.delegate = delegate; this.audit = audit; }

    @Override public InitResult initialise(InitRequest r) {
        audit.record("initialise", r.reference());
        return delegate.initialise(r);
    }
    // ...other methods delegate the same way
}

Decorators stack (auditing, then metrics, then retries) without touching the provider code. In Spring: ClientHttpRequestInterceptor chains, servlet filters, BeanPostProcessors that wrap beans.

7. Observer: publish events instead of calling everyone

When a transfer completes, several things must happen: send an SMS, update the fraud model, notify the ledger. Calling each service directly couples the transfer code to all of them. The Observer pattern lets the transfer service publish an event and lets listeners react.

public record TransferCompleted(String reference, Money amount, String customerId) { }

@Service
class TransferService {
    private final ApplicationEventPublisher events;
    TransferService(ApplicationEventPublisher events) { this.events = events; }

    @Transactional
    public Receipt transfer(TransferRequest r) {
        Receipt receipt = post(r);
        events.publishEvent(new TransferCompleted(receipt.reference(), r.amount(), r.customerId()));
        return receipt;
    }
}

@Component
class SmsNotifier {
    @TransactionalEventListener                        // runs only after the transaction commits
    void on(TransferCompleted e) { /* send SMS */ }
}

@TransactionalEventListener matters: a plain @EventListener runs immediately inside the transaction, so an SMS could be sent for a transfer that then rolls back. In distributed systems the same idea becomes messaging with Kafka and the transactional outbox (Phase 3).

8. Adapter: make an incompatible API fit your interface

Every payment provider, KYC vendor and core-banking system has its own API. An Adapter translates between your domain interface and theirs, so the rest of your code never sees their types.

class PaystackAdapter implements PaymentProvider {           // your interface
    private final PaystackClient client;                     // their SDK or HTTP client
    @Override public InitResult initialise(InitRequest r) {
        var res = client.initializeTransaction(r.email(), r.amountMinor(), r.reference());
        return new InitResult(res.data().authorizationUrl(), res.data().accessCode());
    }
}

Capstone 1 of Phase 2 is built entirely on this idea. In Spring: HandlerAdapter lets the DispatcherServlet call controllers of different kinds through one interface.

9. Singleton: one instance, and why "stateless" matters

The classic Singleton (a private constructor and a static getInstance()) is rarely written by hand in modern Java: it hides dependencies and is hard to test. If you need one, an enum with a single constant is the safest form (serialisation- and reflection-safe).

In Spring, beans are singletons by default (one instance per container). This is efficient, but it means a bean is shared by every request thread. A singleton bean must therefore be stateless or hold only thread-safe, effectively immutable state:

@Service
class QuoteService {
    private BigDecimal lastRate;          // BUG: shared by all requests; one user's rate leaks into another's quote
}

Keep per-request data in local variables, method parameters or request-scoped beans (topic 4.8).

10. Choosing (and not choosing) a pattern

Symptom Pattern that helps
A switch that grows with every product or provider Strategy (or sealed types if the set is closed)
Constructors with many optional or same-typed arguments Builder (or a static factory)
The same algorithm copied with small differences Template Method or callbacks
Cross-cutting behaviour: audit, retry, metrics, security Decorator, or a Spring proxy via an annotation
One action must trigger several independent reactions Observer (application events)
A third-party API leaks into your domain code Adapter

Patterns cost indirection. One implementation behind an interface "for the future" is usually speculative: introduce the abstraction when the second case arrives, and say so in code review.

Common mistakes

  • Naming everything *Manager, *Helper or *Factory without a real factory responsibility.
  • Singleton beans that store per-request or per-user data in fields.
  • Calling a @Transactional or @Cacheable method from inside the same class and expecting the annotation to work.
  • Using @EventListener for side effects that must happen only after a commit.
  • Deep inheritance hierarchies for Template Method when a lambda callback would do.
  • An interface with exactly one implementation and no test double, added "just in case".

Practice

  1. Refactor a fee switch with five channels into Strategy beans, keeping the same unit tests green (red-green-refactor).
  2. Write an AuditingProvider decorator and a MetricsProvider decorator, and compose them around a fake provider in a test.
  3. Publish a TransferCompleted event and prove with a test that an @TransactionalEventListener does not run when the transaction rolls back.
  4. In your Phase 1 Capstone 1, find three places where Spring applies a pattern (Proxy, Template Method, Factory) and explain each in your README's "Design decisions" section.
