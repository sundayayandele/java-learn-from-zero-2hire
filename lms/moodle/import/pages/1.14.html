Week 5 · Optional · Module 1: Modern Java & OOP Foundations

Why this topic is here. "Developing Applications with Localization Support" is an objective group in the Oracle OCP Java SE 21 and 25 exams, and every customer-facing banking product formats money, dates and messages for different locales. See the certification mapping.

What you will be able to do

  • Use Locale to represent language and region, and know where the default locale comes from.
  • Format and parse numbers, currency and percentages with NumberFormat, including compact forms.
  • Format and parse dates and times with DateTimeFormatter, including localised styles and time zones.
  • Build messages with MessageFormat and externalise text in ResourceBundle properties files, and explain the bundle lookup order.
  • Keep money formatting correct: format for display only, never parse display strings back into amounts.

Why this matters in a bank or fintech

A Nigerian customer expects ₦1,250,000.50; a French customer of the same remittance service expects 1 250 000,50 €. Statements, SMS alerts and receipts are generated in several languages (English, French for Francophone West Africa, and others), and dates are written differently from country to country: 03/04/2026 is 3 April in Lagos and London but 4 March in New York. Formatting mistakes are customer complaints at best, and disputes at worst.

1. Locale

Locale ng = Locale.of("en", "NG");            // Java 19+: Locale.of (constructors are deprecated)
Locale fr = Locale.FRANCE;                     // fr_FR
Locale ha = Locale.forLanguageTag("ha-NG");    // Hausa (Nigeria), from a BCP 47 tag
Locale.getDefault();                           // from the OS / JVM flags -Duser.language=... -Duser.country=...
ng.getDisplayCountry(Locale.ENGLISH);          // "Nigeria"

A locale is language plus optional region (plus script and variants). In a server, don't rely on the default locale: the JVM's default comes from the host, which differs between your laptop, the CI runner and production. Decide the locale per request (from the customer profile or the Accept-Language header) and pass it explicitly. Locale.Category.FORMAT and DISPLAY defaults can even differ.

2. Numbers, currency and percentages

BigDecimal amount = new BigDecimal("1250000.50");

NumberFormat.getCurrencyInstance(Locale.of("en", "NG")).format(amount);   // "₦1,250,000.50"
NumberFormat.getCurrencyInstance(Locale.FRANCE).format(amount);           // "1 250 000,50 €"   (narrow no-break spaces)
NumberFormat.getCurrencyInstance(Locale.US).format(amount);               // "$1,250,000.50"

NumberFormat.getNumberInstance(Locale.GERMANY).format(1234.5);            // "1.234,5"
NumberFormat.getPercentInstance(Locale.UK).format(0.185);                 // "18%"  (default 0 fraction digits)
NumberFormat.getIntegerInstance(Locale.US).format(2.5);                   // "2"  (HALF_EVEN rounding)

NumberFormat compact = NumberFormat.getCompactNumberInstance(Locale.US, NumberFormat.Style.SHORT);
compact.format(1_250_000);                                                // "1M"

Important details:

  • The currency symbol comes from the locale's country. To show naira to a French-speaking customer, set the currency explicitly: nf.setCurrency(Currency.getInstance("NGN")).
  • NumberFormat instances are not thread-safe. Create one per use, or keep one per thread; don't share a static instance across requests. (DateTimeFormatter is immutable and safe.)
  • Fraction digits follow the currency (JPY → 0). Set them deliberately with setMinimumFractionDigits / setMaximumFractionDigits and the RoundingMode you use for money (topic 1.3).
  • Parsing is locale-sensitive: NumberFormat.getNumberInstance(Locale.GERMANY).parse("1.234,5") returns 1234.5. Parse returns Number (often Long or Double); for money use DecimalFormat with setParseBigDecimal(true), or better, accept amounts as JSON numbers or strings in a fixed machine format and only format for display.

String.format and formatted are locale-aware too: "%,.2f".formatted(amount) uses the default locale; pass one explicitly with String.format(Locale.US, "%,.2f", amount) in machine output such as CSV files, so a server with a French default locale doesn't write 1 250 000,50 into a file a partner parses.

3. Dates and times

LocalDate d = LocalDate.of(2026, 4, 3);
DateTimeFormatter.ISO_LOCAL_DATE.format(d);                                        // "2026-04-03"  (APIs and files)
DateTimeFormatter.ofPattern("dd/MM/yyyy").format(d);                               // "03/04/2026"
DateTimeFormatter.ofLocalizedDate(FormatStyle.LONG).withLocale(Locale.UK).format(d);     // "3 April 2026"
DateTimeFormatter.ofLocalizedDate(FormatStyle.LONG).withLocale(Locale.FRANCE).format(d); // "3 avril 2026"
DateTimeFormatter.ofPattern("EEEE d MMMM yyyy", Locale.of("fr")).format(d);        // "vendredi 3 avril 2026"

ZonedDateTime lagos = Instant.parse("2026-10-21T09:15:00Z").atZone(ZoneId.of("Africa/Lagos"));
DateTimeFormatter.ofPattern("dd MMM yyyy HH:mm z", Locale.UK).format(lagos);       // "21 Oct 2026 10:15 WAT"

LocalDate parsed = LocalDate.parse("03/04/2026", DateTimeFormatter.ofPattern("dd/MM/yyyy"));

Pattern letters to know: y year, M month (MM 04, MMM Apr, MMMM April), d day, E day-of-week, H hour 0–23, h 1–12 with a (AM/PM), m minute, s second, S fraction, z/VV zone name/id, X/x offset. A classic bug: YYYY (week-based year) instead of yyyy, which shows the wrong year in the last days of December.

Daylight saving time: Nigeria has none, but your partners in London or New York do. Store Instants, convert with ZoneId at the edge, and use ZonedDateTime arithmetic (plusDays keeps local time across DST changes; plus(Duration.ofHours(24)) doesn't).

4. Messages and resource bundles

Externalise customer-facing text so translators can work without touching code:

src/main/resources/
├── messages.properties          # default (English)
├── messages_fr.properties       # French
└── messages_ha.properties       # Hausa
# messages.properties
transfer.success=Your transfer of {0} to {1} was successful on {2,date,long}.
# messages_fr.properties
transfer.success=Votre virement de {0} à {1} a été effectué le {2,date,long}.
ResourceBundle bundle = ResourceBundle.getBundle("messages", Locale.FRANCE);
String text = MessageFormat.format(bundle.getString("transfer.success"),
        NumberFormat.getCurrencyInstance(Locale.FRANCE).format(amount),
        beneficiaryName,
        Date.from(instant));   // MessageFormat's date formatting works with java.util.Date

Lookup order for getBundle("messages", fr_CA) when the default locale is en_US: messages_fr_CA, messages_fr, then the default locale's candidates messages_en_US, messages_en, then messages (the base bundle). Individual keys missing in a specific bundle are found in its parents (messages_fr → messages). A missing key throws MissingResourceException. Properties files are read as UTF-8 since Java 9.

MessageFormat placeholders: {0}, {1,number,#.##}, {2,date,short}, {3,choice,0#no transfers|1#one transfer|1<{3} transfers}. A single quote is an escape character in MessageFormat patterns, so write '' for an apostrophe ("today''s rate"); this catches people out in French and English text alike.

Spring Boot wraps this as a MessageSource (spring.messages.basename=messages), and resolves the request locale from Accept-Language with a LocaleResolver. You'll use that for localised validation messages and Problem Details titles.

Worked example: a localised transfer receipt

public String receipt(Transfer t, Locale locale) {
    NumberFormat money = NumberFormat.getCurrencyInstance(locale);
    money.setCurrency(Currency.getInstance(t.currency()));          // show the transfer's currency, not the locale's
    DateTimeFormatter when = DateTimeFormatter.ofLocalizedDateTime(FormatStyle.MEDIUM)
            .withLocale(locale).withZone(ZoneId.of("Africa/Lagos"));
    ResourceBundle messages = ResourceBundle.getBundle("messages", locale);
    return MessageFormat.format(messages.getString("receipt.line"),
            money.format(t.amount()), t.beneficiaryName(), when.format(t.postedAt()), t.reference());
}

The amount stays a BigDecimal in the ledger; formatting happens only at the edge, per customer locale, with the transfer's own currency.

Common mistakes

  • Relying on the JVM default locale in servers, or writing locale-formatted numbers into machine-readable files.
  • Sharing a static NumberFormat or SimpleDateFormat between threads.
  • Parsing formatted display strings back into money.
  • YYYY instead of yyyy; mm (minutes) instead of MM (months).
  • Forgetting that ' is special in MessageFormat patterns.
  • Hard-coding customer-facing text in Java code.

Practice

  1. Print ₦1,250,000.50 for en-NG, fr-FR, en-US and de-DE, then print the same amount in NGN for a French customer.
  2. Write a StatementHeader that prints the statement period in long form for English and French customers, in the Africa/Lagos zone.
  3. Create messages.properties and messages_fr.properties with three keys, delete one key from the French file, and observe the parent-bundle fallback. Then request a key that exists nowhere and handle MissingResourceException.
  4. Write a CSV export that uses Locale.ROOT/Locale.US for numbers regardless of the server's default locale, and a test that sets the default locale to Locale.FRANCE to prove it.
