Deployment guide (Phase 2): secured services with an identity provider

Phase 2 services are Phase 1 services plus three things that change how you deploy them: an identity provider that issues the JWTs, outbound integrations (payment providers, registries, partner APIs) with secrets, and sometimes inbound webhooks from those partners. This guide builds on the Phase 1 deployment guide: do its steps for your target first (server hardening, Docker, database, registry, backups), then apply the Phase 2 additions below.

Costs and clean-up. Check each provider's current free tier and pricing before you create anything, set a billing alert, and delete resources when you're done. Keycloak needs about 1 GB of RAM: budget for it.

1. Sizing with an identity provider

Component Minimum Notes
Spring Boot service 0.5 vCPU / 1 GB -XX:MaxRAMPercentage=75 is already set in the image
PostgreSQL 1 vCPU / 1 GB / 10 GB One instance can hold the app database and Keycloak's database (separate databases and users)
Keycloak 26.8 1 vCPU / 1 GB Start-up takes 20–60 s; token validation in your API never calls Keycloak (keys are cached)
One VPS for everything 2 vCPU / 4 GB / 40 GB SSD Comfortable for a capstone with demo traffic

2. Configuration the service needs

The secure starter reads everything from environment variables. Set these on every platform:

Variable Example Purpose
DB_URL, DB_USER, DB_PASSWORD jdbc:postgresql://…/app As in Phase 1
OAUTH_ISSUER_URI https://auth.yourname.dev/realms/itl Must equal the iss claim in tokens exactly (scheme, host, path)
OAUTH_AUDIENCE itl-api Tokens without this audience are rejected
SPRING_SECURITY_OAUTH2_RESOURCESERVER_JWT_JWK_SET_URI http://keycloak:8080/realms/itl/protocol/openid-connect/certs Optional: fetch signing keys over the internal network while still checking the public issuer
Integration secrets (PROVIDER_A_SECRET, COMPANIES_HOUSE_KEY, …) from the secret store Never in the image, the Compose file or Git

The issuer must be reachable when the app first validates a token (for discovery and keys), not at start-up: Spring Boot resolves it lazily.

3. VPS: app, PostgreSQL and Keycloak behind Caddy

Follow sections 3.1–3.3 of the Phase 1 guide (create, secure, install Docker). Point two DNS records at the server: api.yourname.dev and auth.yourname.dev.

~/app/initdb/keycloak.sh (runs once when the database volume is first created):

#!/bin/sh
set -e
psql -v ON_ERROR_STOP=1 -U "$POSTGRES_USER" -d "$POSTGRES_DB" <<SQL
CREATE USER keycloak WITH PASSWORD '${KC_DB_PASSWORD}';
CREATE DATABASE keycloak OWNER keycloak;
SQL

~/app/compose.yaml:

services:
  postgres:
    image: postgres:17-alpine
    restart: unless-stopped
    environment:
      POSTGRES_DB: app
      POSTGRES_USER: app
      POSTGRES_PASSWORD: ${DB_PASSWORD:?missing}
      KC_DB_PASSWORD: ${KC_DB_PASSWORD:?missing}
    volumes:
      - pgdata:/var/lib/postgresql/data
      - ./initdb:/docker-entrypoint-initdb.d:ro
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U app -d app"]
      interval: 10s
      retries: 10

  keycloak:
    image: quay.io/keycloak/keycloak:26.8
    restart: unless-stopped
    command: ["start", "--import-realm"]
    environment:
      KC_DB: postgres
      KC_DB_URL: jdbc:postgresql://postgres:5432/keycloak
      KC_DB_USERNAME: keycloak
      KC_DB_PASSWORD: ${KC_DB_PASSWORD:?missing}
      KC_HOSTNAME: https://auth.yourname.dev
      KC_HOSTNAME_ADMIN: http://localhost:8080   # the admin console is used only through an SSH tunnel (below)
      KC_HTTP_ENABLED: "true"            # TLS ends at Caddy; Keycloak is only on the internal network
      KC_PROXY_HEADERS: xforwarded
      KC_HEALTH_ENABLED: "true"
      KC_BOOTSTRAP_ADMIN_USERNAME: admin
      KC_BOOTSTRAP_ADMIN_PASSWORD: ${KEYCLOAK_ADMIN_PASSWORD:?missing}   # change it after first login
    volumes:
      - ./keycloak:/opt/keycloak/data/import:ro                         # your realm file, without users or secrets
    depends_on:
      postgres:
        condition: service_healthy

  app:
    image: ghcr.io/<owner>/<repo>:<commit-sha>
    restart: unless-stopped
    environment:
      DB_URL: jdbc:postgresql://postgres:5432/app
      DB_USER: app
      DB_PASSWORD: ${DB_PASSWORD:?missing}
      OAUTH_ISSUER_URI: https://auth.yourname.dev/realms/itl
      SPRING_SECURITY_OAUTH2_RESOURCESERVER_JWT_JWK_SET_URI: http://keycloak:8080/realms/itl/protocol/openid-connect/certs
    depends_on:
      postgres:
        condition: service_healthy

  caddy:
    image: caddy:2
    restart: unless-stopped
    ports: ["80:80", "443:443"]
    volumes:
      - ./Caddyfile:/etc/caddy/Caddyfile:ro
      - caddy_data:/data

volumes:
  pgdata:
  caddy_data:

~/app/Caddyfile:

api.yourname.dev {
    encode gzip
    @blockedActuator {
        path /actuator/*
        not path /actuator/health /actuator/health/*
    }
    respond @blockedActuator 404
    reverse_proxy app:8080
}

auth.yourname.dev {
    # Only the realm endpoints are public; the master realm and admin console are not.
    @admin path /admin/* /realms/master/*
    respond @admin 404
    reverse_proxy keycloak:8080
}

Secrets, once, on the server:

cd ~/app && umask 077
{ echo "DB_PASSWORD=$(openssl rand -base64 32 | tr -d '/+=')"
  echo "KC_DB_PASSWORD=$(openssl rand -base64 32 | tr -d '/+=')"
  echo "KEYCLOAK_ADMIN_PASSWORD=$(openssl rand -base64 24 | tr -d '/+=')"; } > .env
chmod +x initdb/keycloak.sh
docker compose up -d && docker compose logs -f keycloak app

To administer Keycloak, use an SSH tunnel instead of exposing the console: ssh -L 8080:localhost:8080 deploy@server after temporarily adding ports: ["127.0.0.1:8080:8080"] to the keycloak service, then open http://localhost:8080/admin. Create real users there (never with the local dev-users.sh passwords) and confidential clients whose secrets you store in your password manager.

Check: curl -s https://auth.yourname.dev/realms/itl/.well-known/openid-configuration | jq .issuer must print exactly your OAUTH_ISSUER_URI; then call the API with a token and without one (401).

Backups: dump both databases (app and keycloak) daily, as in Phase 1 section 3.6.

4. AWS, Azure and GCP

Deploy the app exactly as in Phase 1 (AWS, Azure, GCP) and add the environment variables from section 2. For the identity provider you have two choices:

A. Keycloak in a container (recommended for the capstones). Run the same quay.io/keycloak/keycloak:26.8 image as a second service (ECS service, Container App, Cloud Run service with min instances 1) with KC_DB=postgres pointing at a keycloak database on your managed PostgreSQL, KC_HOSTNAME set to its public HTTPS URL and KC_PROXY_HEADERS=xforwarded. Your realm file, roles and scopes work unchanged.

B. The cloud's managed identity service. Fine for production, but tokens differ from Keycloak's, so adjust the converter in SecurityConfig and test it:

Service Issuer (OAUTH_ISSUER_URI) Differences to handle
Amazon Cognito user pools https://cognito-idp.<region>.amazonaws.com/<user-pool-id> Access tokens carry client_id rather than aud: replace the audience check with a validator on client_id. Groups arrive in cognito:groups; resource-server scopes look like <identifier>/accounts
Microsoft Entra ID https://login.microsoftonline.com/<tenant-id>/v2.0 Audience is your API's application ID; app roles arrive in roles; scopes in scp
Google Identity Platform https://securetoken.google.com/<project-id> Audience is the project id; roles come from custom claims you set

Store integration secrets in AWS Secrets Manager, Azure Key Vault or Google Secret Manager and inject them as environment variables (Phase 1 shows how for the database password).

5. Webhooks, gRPC and outbound integrations

  • Inbound webhooks need a public HTTPS URL. Register https://api.yourname.dev/webhooks/<provider> in the provider's dashboard, keep the endpoint unauthenticated at the JWT layer but verified by signature, and allow it through any WAF rules. Many providers also publish IP ranges you can allow-list as an extra layer.
  • Outbound calls go to the internet: on AWS/Azure/GCP make sure private subnets have NAT (or the platform's egress) and that timeouts are set (the starters do). Never log full request or response bodies from payment providers.
  • gRPC (Capstone 7) needs HTTP/2 end to end: Caddy supports it (reverse_proxy h2c://switch:9090); Cloud Run supports gRPC directly; on AWS use an Application Load Balancer target group with protocol version gRPC; Azure Container Apps supports HTTP/2 ingress (transport: http2). For mTLS between your own services, mount certificates from the secret store, never bake them into images.
