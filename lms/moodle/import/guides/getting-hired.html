Getting hired after Phase 1 (week 14, then ongoing)

Phase 1 doesn't make you a finished backend engineer; Phases 2 and 3 do. But by week 14 you can credibly compete for Java internships, graduate trainee programmes, junior support-engineering roles on Java systems, and some junior backend roles at fintechs and banks, especially if your three capstones are deployed and well documented. Start the visibility work now so it compounds by month 6.

What you can honestly claim after Phase 1

You can say Evidence they'll check
"I write modern Java 21: records, sealed types, streams, virtual threads" Capstone code; topic CBTs; a 20-minute live-coding exercise
"I design relational schemas and write correct, fast SQL" Capstone 1 schema with constraints; a TUNING.md with before/after query plans
"I understand transactions and concurrency in payment systems" Capstone 1's concurrency test, and explaining it out loud
"I build and deploy Spring Boot 4 services with tests and CI" A green GitHub Actions badge and a live /actuator/health URL
"I can read and upgrade legacy Java and Spring Boot 3 code" Project 4.D's UPGRADE.md

Don't claim Kafka, Kubernetes, microservices or Spring Security yet. Interviewers probe what's on your CV, and Phase 2 and 3 will give you those honestly.

Portfolio and visibility

  • One GitHub profile README that works as your portfolio page: a two-line summary ("Java backend engineer in training, building payment and banking systems with Java 21 and Spring Boot 4"), then your three capstones, each with a one-line result, for example "Double-entry ledger: 50 concurrent transfers, zero balance drift, deployed on a VPS with CI/CD."
  • Every capstone README passes the three-minute test from the capstone standards: problem, architecture diagram, how to run it, decisions and trade-offs, live link, data licence.
  • Pin your three capstones and keep commit history honest: small commits, clear messages, no "final final v3".
  • Public writing: one short technical post (LinkedIn article, Hashnode, dev.to or Medium) about something you actually learned, such as "How I made a ledger safe under concurrent transfers" or "Reading my first PostgreSQL query plan". Hiring managers read these.
  • Open source: one small contribution to a library you used (a documentation fix in a Spring guide, a Testcontainers example, a typo in an OpenRewrite recipe). It shows you can work in someone else's codebase.
  • LinkedIn: headline with the stack ("Java · Spring Boot · PostgreSQL · Docker"), the capstones under Projects with links, and the ITLearning certificate when you earn it.

CV for a Phase 1 graduate

  • One page. Contact details, GitHub, LinkedIn and portfolio links at the top.
  • Projects before education if you're changing careers. Each project: what it does, the stack, and one measurable or verifiable result.
  • Skills grouped and honest: Languages (Java 21, Kotlin basics, SQL); Frameworks (Spring Boot 4, Spring Data JPA, JUnit, Testcontainers); Data (PostgreSQL, MySQL, Redis, MongoDB, Flyway); Tools (Git, Maven, Docker, GitHub Actions, GitLab CI, Linux).
  • Previous career counts. A former bank teller who understands reconciliation, a teacher who explains clearly, an accountant who knows double entry: say so, briefly. Domain knowledge is a genuine advantage in fintech hiring.
  • Tailor the top three bullet points to each job ad. Use their words where they're true for you.

Interview loop preparation

Junior Java interviews in Lagos fintechs, banks and international remote teams usually look like this:

Round What it tests How to prepare
Recruiter / HR screen Motivation, communication, availability, salary expectations A 60-second story: where you're coming from, why Java backend, what you've built (lead with Capstone 1)
Online assessment Core Java, SQL, sometimes a HackerRank/Codility coding task Timed practice: 2 easy and 1 medium problem per week in Java; 20 SQL exercises (joins, group by, window functions)
Technical interview: core Java OOP and SOLID, collections and complexity, equals/hashCode, exceptions, immutability, streams, Java 8–21 features, basic concurrency Re-take the topic CBTs from Modules 1–2 without notes; explain each answer aloud
Technical interview: Spring and SQL DI and auto-configuration, REST and status codes, validation, @Transactional, N+1, transactions and isolation, indexes Walk through your capstone's controller → service → repository → SQL path and justify every choice
Take-home or live coding Build a small REST API or fix a bug, with tests Use your starter; practise a 90-minute "build a wallet API with tests" exercise twice
Project deep-dive Depth on one thing you built: trade-offs, failures, numbers Rehearse Capstone 1: why double entry, how locking works, what you'd change at 100× volume
Behavioural Ownership, learning, teamwork, handling mistakes Five STAR stories (below)

Questions you should be able to answer cold

Revise with the Java fundamentals revision sheet and keep up the timed coding-interview practice track.

  1. Why shouldn't you use double for money, and what do you use instead?
  2. What happens if you override equals but not hashCode?
  3. ArrayList vs LinkedList vs HashSet: when and why?
  4. Checked vs unchecked exceptions, and how do you handle InterruptedException?
  5. What does synchronized guarantee? Why doesn't it protect a balance across two service instances?
  6. What are virtual threads good for, and what aren't they good for?
  7. What's the N+1 problem and how do you fix it?
  8. What do the four isolation levels prevent? What does PostgreSQL's default allow?
  9. How would you make a payment API idempotent?
  10. What changed in Spring Boot 4, and how would you upgrade a Boot 3 service?

Five STAR stories to prepare

Use Situation, Task, Action, Result, and keep each under two minutes:

  1. A bug you found and fixed, for example the race condition in the find-and-fix lab or a failing CI build.
  2. Something you learned fast: Kotlin, query plans or Testcontainers, with what you shipped afterwards.
  3. A trade-off you made: pessimistic vs optimistic locking, or caching vs freshness.
  4. Working with others: a code review you gave or received, or helping a cohort peer.
  5. A mistake and what changed afterwards, such as a committed secret you rotated, or a migration you had to redo.

Applications

  1. Shortlist 15–20 roles: Java internships and graduate programmes at banks and fintechs, junior Java developer and application support roles, and remote junior roles that list Java + Spring Boot + SQL.
  2. Map each job ad to evidence before applying: for every requirement, which capstone, project or CBT shows it? Skip roles where fewer than half match; apply where 60%+ match.
  3. Seek referrals: engage with engineers from target companies on LinkedIn by commenting usefully on their technical posts, attend Java and fintech meetups (Lagos Java User Group, Google Developer Groups, fintech events), and ask cohort alumni.
  4. Track everything in a spreadsheet: company, role, date, contact, stage, feedback, next step.
  5. Apply in waves of 4–5 so interviews cluster and you can compare offers. After each rejection, ask for feedback and redo one practice exercise in that area.
  6. Keep building: Phase 2 starts in week 15. Each new module adds a line to your CV.
