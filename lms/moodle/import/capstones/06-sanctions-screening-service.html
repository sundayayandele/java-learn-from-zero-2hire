Architecture and system design (read this first)

Before you write code, study how this system is designed. These five views are the target architecture for a production-grade build; reproduce and adapt them in your own repository, and keep them current as you build. Full explanations, Mermaid, draw.io, SVG and PNG sources and the architecture decision records are in architecture/.

1. Solution architecture

Solution architecture: onboarding and the payments engine call the service synchronously before opening an account or releasing a payment; potential matches create alerts that compliance analysts resolve. Lists refresh daily from official publishers.

Sources: Mermaid · draw.io · SVG · PNG

2. Logical architecture

Logical architecture: list management imports each source into an immutable list version with normalised tokens; matching generates candidates cheaply in the database (trigram index) and scores them precisely in Java; decisioning applies thresholds, allow-lists and records the evidence; case work lets analysts confirm or dismiss alerts with mandatory reasons.

Sources: Mermaid · draw.io · SVG · PNG

3. Technical architecture

Technical architecture shows how the code is organised inside the Spring Boot 4 service: thin controllers that validate and translate errors, services that hold the business rules and transaction boundaries, and a persistence layer (JPA where entity behaviour and locking help, JdbcClient/SQL for reporting and bulk work). Cross-cutting concerns (configuration, health, metrics, scheduling, outbound HTTP) are framework features configured once. Package by feature in code; the layers here are logical.

Sources: Mermaid · draw.io · SVG · PNG

4. Infrastructure architecture

Infrastructure architecture shows where things run on the cheapest production-like target, a single VPS (for example SSDNodes). Only Caddy is reachable from the internet; it terminates TLS and forwards to sanctions-screening-service on Docker's internal network, so the database is never exposed (Docker port publishing bypasses ufw, so nothing else publishes ports). Images are built once by GitHub Actions, stored in GHCR by commit SHA, and pulled onto the server; backups leave the machine daily. Sizing and every command are in the deployment guide.

Sources: Mermaid · draw.io · SVG · PNG

Cloud architecture maps the service onto managed cloud building blocks, drawn for AWS (ECS Express Mode, the AWS-recommended path for new accounts since App Runner closed to new customers in 2026). Key design decisions

  1. One deployable Spring Boot service (modular monolith) on PostgreSQL
  2. Candidate generation in PostgreSQL, scoring in Java
  3. Immutable list versions recorded on every decision
  4. Configurable thresholds owned by compliance
  5. Cache results keyed by normalised input and list version

Weeks 7–12. Modules used: 1, 2, 3, 4.

Business context

Banks and payment companies must not deal with sanctioned people, companies or vessels. Every new customer, beneficiary and cross-border payment is screened against sanctions lists such as the US OFAC SDN list and the UK Sanctions List (and the UN, EU and local lists in production). Screening has to be fast (it sits in the payment path), tolerant of spelling variations and transliteration ("Mohammed / Muhammad / Mohamed"), and auditable: every decision must show which list version and which entry matched, and why.

You'll build a screening service that loads two official lists, normalises names, scores fuzzy matches, and supports an analyst workflow for potential matches.

What you'll build

List management

  • Importers for the OFAC SDN files (SDN.CSV with ALT.CSV aliases and ADD.CSV addresses) and the UK Sanctions List (CSV or XML).
  • Each import creates a list version (source, downloaded at, checksum, entry count). Entries keep their source IDs. Re-importing an unchanged file creates no new version.
  • Normalisation at import time: Unicode normalisation (NFKD) and diacritic removal, upper-casing, punctuation removal, collapsing whitespace, removing common legal suffixes for organisations (LTD, LIMITED, PLC, LLC, INC), and storing tokens. Keep the original name for display.

Screening

  • POST /api/v1/screenings with a name, optional date of birth, country and entity type (individual/organisation).
  • Candidate generation: index tokens (or PostgreSQL pg_trgm trigram index) to find a small candidate set quickly, then score each candidate in Java with a combination of token-set similarity and Jaro-Winkler (implement it yourself, or use Apache Commons Text and explain the algorithm).
  • Configurable thresholds (@ConfigurationProperties): above high → POTENTIAL_MATCH (payment held for review); between low and high → REVIEW; below → CLEAR. Date of birth and country mismatches reduce the score.
  • The response explains the decision: matched entry, list and version, score breakdown, normalised forms.
  • Batch screening: POST /api/v1/screenings/batch for up to 10,000 names, processed concurrently with virtual threads and a bounded number of database connections.
  • Cache recent results (Redis or in-memory) keyed by normalised input and list version; invalidate on new list versions.

Analyst workflow

  • GET /api/v1/alerts?status=OPEN, POST /api/v1/alerts/{id}/decisions (TRUE_MATCH / FALSE_POSITIVE with a mandatory reason). Decisions are audited and immutable.
  • Allow-list: a confirmed false positive for a specific customer and list entry is suppressed in future screenings until the list entry changes.

Acceptance criteria

Infrastructure and deployment

App 1 vCPU / 1–2 GB (matching is CPU-bound in batches); PostgreSQL 1 vCPU / 2 GB / 5 GB with the pg_trgm extension (available on RDS, Azure Flexible Server and Cloud SQL; enable it in a Flyway migration). Optional Redis. Schedule list refreshes daily. CI from the starter; deploy with the deployment guide.

Stretch goals

  • Phonetic matching (Double Metaphone) for transliterated names.
  • A precision/recall report against a labelled set of 200 invented test cases you create.
  • Delta imports that report additions, removals and amendments between list versions.

Interview talking points

  • How you balanced false positives against false negatives, and who should own the thresholds.
  • How you kept screening fast (candidate generation vs scoring) and safe under load.
  • How you made every decision auditable months later.

Step-by-step build guide: Sanctions screening service

Work through the steps in order. Each step ends with a Done when check: don't move on until it passes. Commit after every step with a clear message, so your history tells the story of the build.

Before you start

  • Finish the topics listed under "Skills you'll demonstrate" in the brief, or study them alongside.
  • Read the architecture section and the ADRs. You will update both at the end.
  • Install Java 21 (Temurin), Docker Desktop, Git and IntelliJ IDEA (topic 1.1).

Step 1: Create your repository from the starter

git clone https://github.com/sundayayandele/java-zero-hire.git
mkdir sanctions-screening-service && cp -R java-zero-hire/phases/01-foundations/capstones/06-sanctions-screening-service/starter/. sanctions-screening-service/
cd sanctions-screening-service
git init -b main && git add . && git commit -m "Start from the Sanctions screening service starter"

Create an empty public repository called sanctions-screening-service on GitHub, then:

git remote add origin https://github.com/<your-username>/sanctions-screening-service.git
git push -u origin main

Done when: the Actions tab shows the CI workflow running on your first push.

Step 2: Run it locally

cp .env.example .env          # set DB_PASSWORD to anything local
docker compose up --build
curl http://localhost:8080/actuator/health
./mvnw verify                 # needs Docker running (Testcontainers)

Done when: health returns {"status":"UP"} and ./mvnw verify is green. The base package is ng.itlearning.screening.

Step 3: Get the data

Never commit raw datasets; download them with a script. Add data/ to .gitignore first.

mkdir -p data
curl -L -o data/SDN.CSV https://sanctionslistservice.ofac.treas.gov/api/PublicationPreview/exports/SDN.CSV
curl -L -o data/ALT.CSV https://sanctionslistservice.ofac.treas.gov/api/PublicationPreview/exports/ALT.CSV
# UK Sanctions List: download the CSV from https://www.gov.uk/government/publications/the-uk-sanctions-list

Copy the licence and attribution lines from the brief's Data section into your README now.

Done when: the files are in data/ and git status doesn't show them.

Step 4: Name normalisation

  1. Normaliser.normalise(String): Unicode NFKD, strip diacritics, upper-case, remove punctuation, collapse spaces, drop legal suffixes (LTD, LIMITED, PLC, LLC, INC) for organisations.
  2. Return tokens as well as the normalised string.

Done when: Unit tests: "Société Générale S.A." and "SOCIETE GENERALE SA" normalise identically.

Step 5: Import lists as versions

  1. Migrations: list_version (source, downloaded_at, sha256, entry_count), list_entry, entry_alias.
  2. Import OFAC SDN with aliases, and the UK Sanctions List; skip the import when the checksum matches the latest version.
  3. Enable pg_trgm and add a trigram GIN index on normalised names.

Done when: Importing the same file twice creates one version.

Step 6: Candidate generation and scoring

  1. Find candidates with the trigram index (similarity(name_norm, :q) > 0.3), limit 50.
  2. Score in Java: token-set similarity combined with Jaro-Winkler (implement it or use Apache Commons Text and explain it).
  3. Reduce the score when date of birth or country disagree.

Done when: "Mohamed" and "Muhammad" variants of a test entry score above your low threshold.

Step 7: Screening decisions and explanations

  1. @ConfigurationProperties thresholds: above high → POTENTIAL_MATCH, between → REVIEW, below → CLEAR.
  2. Response shows the matched entry, list and version, score breakdown and normalised forms.
  3. Use only invented test names and public list entries.

Done when: Acceptance tests cover a clear, a review and a potential match.

Step 8: Batch screening

  1. POST /api/v1/screenings/batch for up to 10,000 names on virtual threads, with a Semaphore no larger than the connection pool.

Done when: 10,000 names screen without connection-pool timeouts; report the duration.

Step 9: Analyst workflow and allow-list

  1. Alerts for REVIEW and POTENTIAL_MATCH; decisions TRUE_MATCH / FALSE_POSITIVE with a mandatory reason, append-only.
  2. A false positive for a customer and entry suppresses future alerts until that entry changes.

Done when: A test proves the allow-list suppresses the alert and stops suppressing it after the entry changes.

Step 10: Caching and daily refresh

  1. Cache results keyed by normalised input and list version (Redis or in-memory); new versions invalidate naturally.
  2. Scheduled daily list refresh.

Done when: A repeated screening is served from cache and a new list version bypasses it.

Step 11: Deploy and automate

  1. Make sure ./mvnw verify and the GitHub Actions workflow are green on main.
  2. Optional: mirror the repository to gitlab.com so .gitlab-ci.yml runs too. Other platforms (Azure DevOps, AWS CodeBuild, Jenkins, Argo CD) are covered in the CI/CD guide.
  3. Deploy using the deployment guide: a single VPS (2 vCPU / 4 GB) is cheapest; AWS, Azure and GCP steps are there too.
  4. Put the public health URL (/actuator/health) at the top of your README.

Done when: the health URL returns UP from the internet, and no secret is in Git (git log -p | grep -i password finds nothing real).

Step 12: Update the architecture pack

  1. Copy the architecture/ folder from this capstone into your repository.
  2. Edit the Mermaid (.mmd) or draw.io (.drawio) files so all five diagrams match what you actually built; re-export SVG/PNG (draw.io: File → Export; Mermaid: npx @mermaid-js/mermaid-cli -i x.mmd -o x.svg).
  3. Write at least three ADRs of your own (copy the format in architecture/adr/): one for persistence, one for concurrency or performance, one you chose yourself.

Done when: someone can understand your system from the diagrams and ADRs without reading code.

Step 13: Write the README and record a demo

Your README must cover, in this order: the business problem; the architecture diagram; how to run it; API examples with curl; data sources and licences; design decisions and trade-offs; performance numbers (query plans, timings); what you'd do next. Then record a 3-minute demo video.

Done when: a hiring manager can read the README in three minutes and know what you built and why.

Step 14: Check against the rubric and submit

When you're stuck, go back to the topic in the brief's skills table, or ask in the course forum. For Capstones 1 and 2, your mentor shares the reference solution once your submission has passed, so you can compare approaches.
