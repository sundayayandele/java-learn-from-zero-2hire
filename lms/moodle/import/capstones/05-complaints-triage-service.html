Before you write code, study how this system is designed. 1. Solution architecture

Solution architecture: complaints arrive from bank channels and from the public CFPB dataset (standing in for a regulator feed); agents work queues per team; compliance monitors SLA breaches and regulatory reporting.

Sources: Mermaid · draw.io · SVG · PNG

2. Logical architecture

Logical architecture: ingestion streams the bulk file into staging and upserts complaints; triage applies data-driven routing rules and starts an SLA clock on business days; the workflow enforces legal status transitions with an audit trail; search and reporting use full-text indexes and SQL aggregates. Narratives may live in MongoDB; structured fields stay relational.

Sources: Mermaid · draw.io · SVG · PNG

3. Technical architecture

Technical architecture shows how the code is organised inside the Spring Boot 4 service: thin controllers that validate and translate errors, services that hold the business rules and transaction boundaries, and a persistence layer (JPA where entity behaviour and locking help, JdbcClient/SQL for reporting and bulk work). Cross-cutting concerns (configuration, health, metrics, scheduling, outbound HTTP) are framework features configured once. Package by feature in code; the layers here are logical.

Sources: Mermaid · draw.io · SVG · PNG

4. Infrastructure architecture

Infrastructure architecture shows where things run on the cheapest production-like target, a single VPS (for example SSDNodes). Only Caddy is reachable from the internet; it terminates TLS and forwards to complaints-triage-service on Docker's internal network, so the database is never exposed (Docker port publishing bypasses ufw, so nothing else publishes ports). Images are built once by GitHub Actions, stored in GHCR by commit SHA, and pulled onto the server; backups leave the machine daily. Sizing and every command are in the deployment guide.

Key design decisions

  1. One deployable Spring Boot service (modular monolith) on PostgreSQL
  2. PostgreSQL full-text search first; MongoDB optional for narratives
  3. Business-day SLA clock from a calendar table
  4. Explicit workflow state machine with audit
  5. Streaming, idempotent bulk import

Weeks 8–12. Modules used: 1, 2, 3, 4.

Business context

Banking regulators expect complaints to be acknowledged and resolved within set timelines, tracked by product and issue, and reported regularly. In Nigeria the CBN's consumer protection rules set such timelines and require complaint reporting; in the US the CFPB runs a public complaint database. Banks need internal systems that ingest complaints from many channels, route them to the right team, track deadlines, and give management a live view of where they are breaching.

You'll build that system using the CFPB's public complaint database as a realistic stream of millions of real complaints.

What you'll build

Ingestion

  • A bulk importer for the CFPB CSV that loads a filtered subset (for example the last 12 months, or chosen products) into PostgreSQL with JDBC batching or COPY, idempotent on the complaint ID.
  • Store the structured fields relationally (complaint, company, product, issue), and the free-text consumer narrative plus any extra attributes either in PostgreSQL (TEXT/JSONB) or as documents in MongoDB (topic 3.6). Justify your choice in the README.
  • A POST /api/v1/complaints endpoint for new complaints from the bank's own channels (web, branch, contact centre), validated.

Triage and SLA

  • Routing rules (data-driven): product + issue → team (Cards, Mortgages, Collections, Fraud, Digital) and priority. Keywords in the narrative (e.g. "fraud", "unauthorized", "identity theft") raise the priority.
  • SLA clock: acknowledgement due within 1 business day; resolution due within a configurable number of business days per priority. Use an injected Clock, business-day arithmetic and a holiday table.
  • Status workflow: RECEIVED → ACKNOWLEDGED → IN_PROGRESS → RESOLVED | ESCALATED | CLOSED, with illegal transitions rejected (409) and every change audited.

API (suggested)

Method and path Purpose
GET /api/v1/complaints?product=&state=&status=&q=&page= Search and filter, including full-text search on narratives (PostgreSQL tsvector + GIN index, or a MongoDB text index)
GET /api/v1/complaints/{id} Details, history, SLA status
POST /api/v1/complaints/{id}/transitions Change status (validated workflow)
GET /api/v1/reports/sla-breaches Open complaints past their deadline, grouped by team and priority
GET /api/v1/reports/monthly?product= Volumes, timely-response rate and top issues per month (SQL aggregates and window functions)

Quality bar

  1. The importer handles quoted CSV fields with embedded commas and newlines (use a proper CSV parser such as Apache Commons CSV or Jackson's CSV module, not split(",")).
  2. Every search used by the UI has a supporting index, shown with EXPLAIN ANALYZE in your README.
  3. Narratives are already scrubbed of personal data by the CFPB; still treat them as sensitive: no narratives in logs or metric tags.

Acceptance criteria

Infrastructure and deployment

This capstone handles the most data. During import give PostgreSQL 2 vCPU / 4 GB RAM / 20–50 GB storage (or limit yourself to 6–12 months of data: a few hundred thousand rows fit comfortably on 1 vCPU / 2 GB). MongoDB, if used: a container on the same VPS, or MongoDB Atlas's free tier. CI from the starter; deploy with the deployment guide.

Stretch goals

  • A daily incremental import using the CFPB's API with a date filter.
  • A materialised view for the monthly report, refreshed after each import.
  • Email/SMS notification stubs when an SLA is about to breach.

Interview talking points

  • How you imported millions of messy CSV rows reliably and quickly.
  • Why you chose PostgreSQL full-text search or MongoDB for narratives.
  • How you modelled business days and SLA clocks, and tested them.

Step-by-step build guide: Consumer complaints triage and SLA service

Work through the steps in order. Each step ends with a Done when check: don't move on until it passes. Commit after every step with a clear message, so your history tells the story of the build.

Before you start

  • Finish the topics listed under "Skills you'll demonstrate" in the brief, or study them alongside.
  • Read the architecture section and the ADRs. You will update both at the end.
  • Install Java 21 (Temurin), Docker Desktop, Git and IntelliJ IDEA (topic 1.1).

Step 1: Create your repository from the starter

git clone https://github.com/sundayayandele/java-zero-hire.git
mkdir complaints-triage-service && cp -R java-zero-hire/phases/01-foundations/capstones/05-complaints-triage-service/starter/. complaints-triage-service/
cd complaints-triage-service
git init -b main && git add . && git commit -m "Start from the Consumer complaints triage and SLA service starter"

Create an empty public repository called complaints-triage-service on GitHub, then:

git remote add origin https://github.com/<your-username>/complaints-triage-service.git
git push -u origin main

Done when: the Actions tab shows the CI workflow running on your first push.

Step 2: Run it locally

cp .env.example .env          # set DB_PASSWORD to anything local
docker compose up --build
curl http://localhost:8080/actuator/health
./mvnw verify                 # needs Docker running (Testcontainers)

Done when: health returns {"status":"UP"} and ./mvnw verify is green. The base package is ng.itlearning.complaints.

Step 3: Get the data

Never commit raw datasets; download them with a script. Add data/ to .gitignore first.

mkdir -p data
curl -L -o data/complaints.csv.zip https://files.consumerfinance.gov/ccdb/complaints.csv.zip
# Several GB unzipped: stream it from the zip in Java and keep only the last 12 months

Copy the licence and attribution lines from the brief's Data section into your README now.

Done when: the files are in data/ and git status doesn't show them.

Step 4: Streaming CSV import

  1. Read the CSV straight from the zip with ZipInputStream and Apache Commons CSV (quoted fields contain commas and newlines).
  2. Filter while streaming (for example the last 12 months) so you never hold the file in memory.
  3. Insert with JDBC batches or CopyManager, idempotent on the complaint ID (ON CONFLICT DO NOTHING).

Done when: The filtered import finishes in minutes, and re-running it inserts 0 rows.

Step 5: Relational model and narratives

  1. Tables complaint, company, product, issue; narrative in a TEXT column with a tsvector column (or MongoDB documents; justify the choice in your README).
  2. GIN index on the tsvector; B-tree indexes for the filters the API offers.

Done when: EXPLAIN ANALYZE of a narrative search shows a bitmap index scan on the GIN index.

Step 6: Routing rules

  1. Data-driven rules: product + issue → team and priority, stored in routing_rule.
  2. Keywords in the narrative ("fraud", "unauthorized", "identity theft") raise the priority.

Done when: Unit tests route sample complaints to the right team and priority.

Step 7: SLA clock with business days

  1. Acknowledgement due within 1 business day; resolution within N business days per priority (configuration).
  2. Business-day arithmetic skipping weekends and a holiday table; inject a Clock.

Done when: A complaint received on a Friday before a public holiday gets the correct due dates.

Step 8: Status workflow and audit

  1. Enum state machine RECEIVED → ACKNOWLEDGED → IN_PROGRESS → RESOLVED | ESCALATED | CLOSED; illegal transitions → 409.
  2. Every transition writes an audit row (who, when, from, to, note).

Done when: Tests prove an illegal transition is rejected and nothing changes.

Step 9: Search and reports

  1. GET /api/v1/complaints with filters, paging and full-text q.
  2. /reports/sla-breaches grouped by team and priority; /reports/monthly with window functions for month-on-month change.
  3. Never put narratives in logs or metric tags.

Done when: Each report query has its EXPLAIN ANALYZE in your README.

Step 10: Intake API and metrics

  1. POST /api/v1/complaints for the bank's own channels, validated, routed and SLA-stamped on arrival.
  2. Metrics: complaints.received by channel and complaints.sla.breached gauge.

Done when: A new complaint appears in search with team, priority and due dates set.

Step 11: Deploy and automate

  1. Make sure ./mvnw verify and the GitHub Actions workflow are green on main.
  2. Optional: mirror the repository to gitlab.com so .gitlab-ci.yml runs too. Other platforms (Azure DevOps, AWS CodeBuild, Jenkins, Argo CD) are covered in the CI/CD guide.
  3. Deploy using the deployment guide: a single VPS (2 vCPU / 4 GB) is cheapest; AWS, Azure and GCP steps are there too.
  4. Put the public health URL (/actuator/health) at the top of your README.

Done when: the health URL returns UP from the internet, and no secret is in Git (git log -p | grep -i password finds nothing real).

Step 12: Update the architecture pack

  1. Copy the architecture/ folder from this capstone into your repository.
  2. Edit the Mermaid (.mmd) or draw.io (.drawio) files so all five diagrams match what you actually built; re-export SVG/PNG (draw.io: File → Export; Mermaid: npx @mermaid-js/mermaid-cli -i x.mmd -o x.svg).
  3. Write at least three ADRs of your own (copy the format in architecture/adr/): one for persistence, one for concurrency or performance, one you chose yourself.

Done when: someone can understand your system from the diagrams and ADRs without reading code.

Step 13: Write the README and record a demo

Your README must cover, in this order: the business problem; the architecture diagram; how to run it; API examples with curl; data sources and licences; design decisions and trade-offs; performance numbers (query plans, timings); what you'd do next. Then record a 3-minute demo video.

Done when: a hiring manager can read the README in three minutes and know what you built and why.
