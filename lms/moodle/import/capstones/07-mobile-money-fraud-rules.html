Architecture and system design (read this first)

Before you write code, study how this system is designed. These five views are the target architecture for a production-grade build; reproduce and adapt them in your own repository, and keep them current as you build. Full explanations, Mermaid, draw.io, SVG and PNG sources and the architecture decision records are in architecture/.

1. Solution architecture

Solution architecture: the switch calls the engine inline (sub-50 ms) before authorising a transfer or cash-out; analysts tune rules and review flagged activity; replays against PaySim provide evidence before a rule goes live.

Sources: Mermaid · draw.io · SVG · PNG

2. Logical architecture

Logical architecture: the rule engine combines independent rules into a verdict with reason codes; stateful rules read and update per-account sliding windows; the replay path partitions by account so each account's events stay in order while partitions run in parallel; analytics compute precision and recall per rule against labels.

Sources: Mermaid · draw.io · SVG · PNG

3. Technical architecture

Technical architecture shows how the code is organised inside the Spring Boot 4 service: thin controllers that validate and translate errors, services that hold the business rules and transaction boundaries, and a persistence layer (JPA where entity behaviour and locking help, JdbcClient/SQL for reporting and bulk work). Cross-cutting concerns (configuration, health, metrics, scheduling, outbound HTTP) are framework features configured once. Package by feature in code; the layers here are logical.

Sources: Mermaid · draw.io · SVG · PNG

4. Infrastructure architecture

Infrastructure architecture shows where things run on the cheapest production-like target, a single VPS (for example SSDNodes). Only Caddy is reachable from the internet; it terminates TLS and forwards to mobile-money-fraud-rules on Docker's internal network, so the database is never exposed (Docker port publishing bypasses ufw, so nothing else publishes ports). Images are built once by GitHub Actions, stored in GHCR by commit SHA, and pulled onto the server; backups leave the machine daily. Sizing and every command are in the deployment guide.

Sources: Mermaid · draw.io · SVG · PNG

Cloud architecture maps the service onto managed cloud building blocks, drawn for AWS (ECS Express Mode, the AWS-recommended path for new accounts since App Runner closed to new customers in 2026). Key design decisions

  1. One deployable Spring Boot service (modular monolith) on PostgreSQL
  2. Sealed rule hierarchy with exhaustive evaluation
  3. Partition by account to keep order while running in parallel
  4. Bounded state: in-memory windows with eviction, Redis when multi-instance
  5. Persist only non-Allow verdicts

Weeks 6–12. Modules used: 1, 2, 3, 4.

Business context

Mobile money and agent banking moved millions of Nigerians and Africans into digital payments, and fraud followed: account takeovers that empty a wallet through a rapid series of transfers and cash-outs, mule accounts that receive and immediately withdraw, and amounts structured just under limits. Operators fight this first with rules that run on every transaction in milliseconds, then with machine learning. Rules must be fast, explainable, easy to change, and measured: a rule that blocks 5% of good customers is a business problem too.

You'll build a real-time fraud rules engine and replay 6.3 million synthetic mobile-money transactions through it, measuring each rule's precision and recall against the dataset's fraud labels.

What you'll build

Rules as a sealed hierarchy

public sealed interface FraudRule permits AmountThresholdRule, VelocityRule, DrainRule,
        NewDestinationCashOutRule, BalanceMismatchRule { }

public sealed interface Verdict permits Allow, Review, Block { }

Suggested rules (each configurable and switchable without code changes):

Rule Signal
Amount threshold Single TRANSFER or CASH_OUT above a configured amount
Velocity More than N outgoing transactions from one account within M simulated hours
Account drain Transaction empties ≥ 95% of the origin balance
Transfer-then-cash-out A TRANSFER to an account that performs a CASH_OUT of a similar amount within a short window (a classic mule pattern)
Balance mismatch Origin balance before − amount ≠ balance after (data anomaly worth reviewing)

The engine evaluates every enabled rule (pattern-matching switch over the sealed type), combines them into a verdict with reason codes, and records the decision.

Real-time API and replay

Method and path Purpose
POST /api/v1/evaluations Evaluate one transaction in real time; returns verdict and reasons in < 50 ms p95
POST /api/v1/replays Replay the PaySim file through the engine (async, 202)
GET /api/v1/replays/{id} Progress and results
GET /api/v1/replays/{id}/rule-performance Per rule: alerts, true positives, false positives, precision, recall
GET/PUT /api/v1/rules View and tune rule parameters (audited, versioned)

Engineering requirements

  1. State for velocity and mule rules (recent transactions per account) must be bounded in memory: sliding windows keyed by account in a ConcurrentHashMap with eviction by simulated time, or Redis sorted sets (topic 3.6). Explain your choice.
  2. Replay concurrency: PaySim is ordered by simulated hour (step). Process accounts in parallel but keep each account's transactions in order (for example, partition by origin account hash into N single-threaded workers fed by bounded queues). Prove that the parallel replay produces exactly the same verdicts as a sequential one.
  3. Persist only verdicts that aren't Allow (plus aggregate counts), in JDBC batches, so the database isn't the bottleneck.
  4. Metrics: evaluations per second, verdicts by rule and outcome, evaluation latency timer.

Acceptance criteria

Infrastructure and deployment

App 2 vCPU / 2 GB for full replays (1 vCPU / 1 GB is enough for the API alone); PostgreSQL 1 vCPU / 2 GB / 10 GB. Replays are batch jobs: run them locally or on the VPS, not on scale-to-zero platforms with short request timeouts. CI from the starter; deploy with the deployment guide.

Stretch goals

  • Tune thresholds to maximise recall at a fixed false-positive budget, and chart the trade-off.
  • Hot-reload rule parameters without restart (and without race conditions).
  • Expose decisions as events in an outbox table for a future Kafka pipeline (Module 11).

Interview talking points

  • How you kept per-account order while processing in parallel.
  • Precision vs recall: what you'd tell the business about each rule.
  • How you kept stateful rules memory-bounded.

Step-by-step build guide: Mobile money fraud rules engine

Work through the steps in order. Each step ends with a Done when check: don't move on until it passes. Commit after every step with a clear message, so your history tells the story of the build.

Before you start

  • Finish the topics listed under "Skills you'll demonstrate" in the brief, or study them alongside.
  • Read the architecture section and the ADRs. You will update both at the end.
  • Install Java 21 (Temurin), Docker Desktop, Git and IntelliJ IDEA (topic 1.1).

Step 2: Run it locally

cp .env.example .env          # set DB_PASSWORD to anything local

curl http://localhost:8080/actuator/health

Done when: health returns {"status":"UP"} and ./mvnw verify is green. The base package is ng.itlearning.fraudrules.

Step 4: Transactions and verdicts

  1. record Txn(int step, TxnType type, BigDecimal amount, String origin, BigDecimal oldBalOrig, BigDecimal newBalOrig, String dest, ..., boolean isFraud).
  2. Sealed Verdict permits Allow, Review, Block with reason codes.
  3. Commit a few hundred rows as a test fixture with the CC BY-SA attribution beside it.

Done when: A parser test reads the fixture into Txn records.

Step 5: Rules as a sealed hierarchy

  1. Sealed FraudRule permits AmountThresholdRule, VelocityRule, DrainRule, NewDestinationCashOutRule, BalanceMismatchRule.
  2. Evaluate with a pattern-matching switch (no default), combine results into one verdict.
  3. Rule parameters come from configuration and can be switched off.

Done when: Unit tests for each rule, including boundary values.

Step 6: Bounded per-account state

  1. Sliding windows per account in a ConcurrentHashMap<String, Deque<Txn>>, evicted by simulated time (step).
  2. Or Redis sorted sets; explain your choice.

Done when: Memory stays flat during a replay of 1 million rows (check with JFR or jcmd GC.heap_info).

Step 7: Real-time evaluation API

  1. POST /api/v1/evaluations returns verdict and reasons; measure p95 with a Micrometer Timer.

Done when: p95 below 50 ms in a local load test.

Step 8: Parallel replay that keeps order

  1. Partition by origin.hashCode() % N into N single-threaded workers fed by bounded BlockingQueues.
  2. Persist only non-Allow verdicts in JDBC batches, plus aggregate counts.
  3. POST /api/v1/replays (202) and GET /api/v1/replays/{id} for progress.

Done when: A test proves the parallel replay gives exactly the same verdicts as a sequential one.

Step 9: Measure each rule

  1. Compare verdicts with isFraud: alerts, true positives, false positives, precision and recall per rule.
  2. GET /api/v1/replays/{id}/rule-performance.

Done when: Your README has the table and one tuning change you made because of it.

Step 10: Rule tuning with audit

  1. PUT /api/v1/rules versions parameters and records who changed what.
  2. Metrics: evaluations per second, verdicts by rule and outcome.

Done when: Changing a threshold changes the next replay's results and is in the audit log.

Step 11: Deploy and automate

  1. Make sure ./mvnw verify and the GitHub Actions workflow are green on main.
  2. Optional: mirror the repository to gitlab.com so .gitlab-ci.yml runs too. Other platforms (Azure DevOps, AWS CodeBuild, Jenkins, Argo CD) are covered in the CI/CD guide.
  3. Deploy using the deployment guide: a single VPS (2 vCPU / 4 GB) is cheapest; AWS, Azure and GCP steps are there too.
  4. Put the public health URL (/actuator/health) at the top of your README.

Done when: the health URL returns UP from the internet, and no secret is in Git (git log -p | grep -i password finds nothing real).

  3. Write at least three ADRs of your own (copy the format in architecture/adr/): one for persistence, one for concurrency or performance, one you chose yourself.
