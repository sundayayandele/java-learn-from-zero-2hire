1. Solution architecture

Solution architecture: onboarding officers search and verify legal entities; payment systems validate LEIs on messages in bulk; GLEIF publishes the global reference data several times a day.

Sources: Mermaid · draw.io · SVG · PNG

2. Logical architecture

Logical architecture: ingestion loads the full file into staging and upserts records only when the source is newer, then applies deltas the same way; validation checks ISO 17442 check digits and status; lookup and search serve exact LEI reads and fuzzy name search from indexes; a cache absorbs hot lookups and is invalidated by deltas.

Sources: Mermaid · draw.io · SVG · PNG

3. Technical architecture

Technical architecture shows how the code is organised inside the Spring Boot 4 service: thin controllers that validate and translate errors, services that hold the business rules and transaction boundaries, and a persistence layer (JPA where entity behaviour and locking help, JdbcClient/SQL for reporting and bulk work). Cross-cutting concerns (configuration, health, metrics, scheduling, outbound HTTP) are framework features configured once. Package by feature in code; the layers here are logical.

Sources: Mermaid · draw.io · SVG · PNG

4. Infrastructure architecture

Infrastructure architecture shows where things run on the cheapest production-like target, a single VPS (for example SSDNodes). Only Caddy is reachable from the internet; it terminates TLS and forwards to kyb-lei-lookup-service on Docker's internal network, so the database is never exposed (Docker port publishing bypasses ufw, so nothing else publishes ports). Images are built once by GitHub Actions, stored in GHCR by commit SHA, and pulled onto the server; backups leave the machine daily. Sizing and every command are in the deployment guide.

Key design decisions

  1. One deployable Spring Boot service (modular monolith) on PostgreSQL
  2. Staging and newer-wins upserts
  3. Trigram GIN index for fuzzy name search
  4. Validate check digits before trusting any LEI

Weeks 8–12. Modules used: 1, 2, 3, 4.

Business context

Before a bank opens an account for a company, lends to it or trades with it, it must "know your business" (KYB): confirm the legal entity exists, its registered address and status, and who owns it. In capital markets and cross-border payments, entities are identified by the Legal Entity Identifier (LEI), a 20-character code (ISO 17442) managed by GLEIF, with public reference data and parent relationships. Corporate onboarding teams search this data constantly, and payment systems validate LEIs on messages.

You'll build an internal LEI reference-data service: bulk-load the global LEI dataset (or a large country subset), keep it current with delta files, and serve fast lookups and searches.

What you'll build

Ingestion

  • Bulk load of the GLEIF Golden Copy (Level 1 "who is who" CSV): LEI, legal name, other names, legal and headquarters addresses, jurisdiction, legal form, entity status, registration status, last update date. Optionally Level 2 relationships ("who owns whom": direct and ultimate parents).
  • Use PostgreSQL COPY through the JDBC driver's CopyManager (or batched inserts) into a staging table, then upsert (INSERT ... ON CONFLICT (lei) DO UPDATE ... WHERE excluded.last_update > lei_record.last_update).
  • Delta updates: apply GLEIF delta files (changes in the last 8 hours, 24 hours, etc.) idempotently; record each run.
  • Validate every LEI's check digits (ISO 17442 uses the ISO 7064 MOD 97-10 scheme, like IBANs) and report invalid records instead of loading them.

API (suggested)

Method and path Purpose
GET /api/v1/entities/{lei} Full record, plus parents if loaded
GET /api/v1/entities?name=&country=&status=&page= Search by name (prefix and fuzzy via pg_trgm), country, status
GET /api/v1/entities/{lei}/validation Is the LEI well-formed (check digits), issued, and currently ISSUED (vs LAPSED/RETIRED)?
POST /api/v1/entities/validations Bulk validation of up to 1,000 LEIs (for a payments team)
GET /api/v1/admin/import-runs Import and delta history

Quality bar

  1. Lookups by LEI in < 5 ms server time; name searches in < 100 ms on the loaded dataset, proved with EXPLAIN ANALYZE and an index strategy (B-tree on lei, trigram GIN on normalised names, composite indexes for common filters).
  2. The full load is resumable or repeatable: running it twice yields the same table.
  3. Imports never block reads (load into staging, then upsert in batches, or swap tables in a transaction).
  4. Cache hot lookups with a TTL; invalidate entries touched by a delta.

Data

Dataset GLEIF LEI Golden Copy (Level 1 and optional Level 2): 2.5 million+ entities worldwide
Download GLEIF Golden Copy and delta files; API for small tests: https://api.gleif.org/api/v1/lei-records?filter[entity.legalAddress.country]=NG
Licence CC0 1.0 (GLEIF terms of use): no restrictions, commercial use allowed
Attribution Not required; recommended: "LEI data: GLEIF, CC0."
Smaller option Load only selected countries (e.g. NG, GB, US, DE, ZA) by filtering while streaming the CSV, to keep the database under 2 GB

Skills you'll demonstrate

Streaming large files and check-digit algorithms (1.2, 1.7), bulk loading with COPY and upserts (3.5), indexing and trigram search (3.3), migrations for large tables (3.4), caching with invalidation (3.6), pagination and Problem Details (4.2, 4.3), import metrics (4.5).

Acceptance criteria

Infrastructure and deployment

Full global load: PostgreSQL 2 vCPU / 4 GB / 30–50 GB while loading and indexing. Country subset: 1 vCPU / 2 GB / 10 GB. The app: 0.5–1 vCPU / 1 GB. Enable pg_trgm in a migration (supported on RDS, Azure Flexible Server and Cloud SQL). CI from the starter with a small fixture; deploy with the deployment guide.

Stretch goals

  • Level 2 relationships with an "ultimate parent" endpoint using a recursive CTE.
  • ISIN-to-LEI mapping (GLEIF publishes it) for securities use cases.
  • A change feed: GET /entities/changes?since= for downstream systems.

Interview talking points

  • How you loaded millions of rows fast, safely and repeatably.
  • The index strategy behind sub-100 ms fuzzy search.
  • How the ISO 7064 check digits work and why they catch typos.

Step-by-step build guide: KYB legal entity lookup service

Work through the steps in order. Each step ends with a Done when check: don't move on until it passes. Commit after every step with a clear message, so your history tells the story of the build.

Before you start

  • Finish the topics listed under "Skills you'll demonstrate" in the brief, or study them alongside.
  • Read the architecture section and the ADRs. You will update both at the end.
  • Install Java 21 (Temurin), Docker Desktop, Git and IntelliJ IDEA (topic 1.1).

Step 1: Create your repository from the starter

git clone https://github.com/sundayayandele/java-zero-hire.git
mkdir kyb-lei-lookup-service && cp -R java-zero-hire/phases/01-foundations/capstones/09-kyb-lei-lookup-service/starter/. kyb-lei-lookup-service/
cd kyb-lei-lookup-service
git init -b main && git add . && git commit -m "Start from the KYB legal entity lookup service starter"

Create an empty public repository called kyb-lei-lookup-service on GitHub, then:

git remote add origin https://github.com/<your-username>/kyb-lei-lookup-service.git
git push -u origin main

Done when: the Actions tab shows the CI workflow running on your first push.

Step 2: Run it locally

cp .env.example .env          # set DB_PASSWORD to anything local
docker compose up --build
curl http://localhost:8080/actuator/health
./mvnw verify                 # needs Docker running (Testcontainers)

Done when: health returns {"status":"UP"} and ./mvnw verify is green. The base package is ng.itlearning.lei.

Step 3: Get the data

Never commit raw datasets; download them with a script. Add data/ to .gitignore first.

mkdir -p data
# GLEIF Golden Copy (CC0): download the Level 1 LEI-CDF CSV from https://www.gleif.org/en/lei-data/gleif-golden-copy
curl -g -L -o data/ng-sample.json "https://api.gleif.org/api/v1/lei-records?filter[entity.legalAddress.country]=NG&page[size]=200"

Copy the licence and attribution lines from the brief's Data section into your README now.

Done when: the files are in data/ and git status doesn't show them.

Step 4: LEI check digits

  1. Implement ISO 17442 validation with ISO 7064 MOD 97-10 (as for IBANs): letters → numbers, the whole number mod 97 must equal 1.

Done when: Unit tests accept real LEIs from the sample and reject ones with a changed character.

Step 5: Streaming load into staging

  1. Stream the Golden Copy CSV (optionally filter countries while streaming) into a staging table with CopyManager.
  2. Report invalid LEIs instead of loading them.

Done when: The filtered load finishes and the invalid-record report is produced.

Step 6: Upsert without blocking reads

  1. INSERT ... ON CONFLICT (lei) DO UPDATE ... WHERE excluded.last_update > lei_record.last_update in batches.
  2. Reads keep working during the load.

Done when: Running the full load twice gives an identical table.

Step 7: Delta files

  1. Apply GLEIF delta files idempotently and record each run in import_run.

Done when: Applying the same delta twice changes nothing the second time.

Step 8: Lookup and search

  1. B-tree on lei; pg_trgm GIN on normalised names; composite indexes for country and status filters.
  2. GET /api/v1/entities/{lei} and GET /api/v1/entities?name=&country=&status=.

Done when: LEI lookups under 5 ms and name searches under 100 ms, with plans in your README.

Step 9: Validation endpoints and caching

  1. Single and bulk (up to 1,000) validation: format, check digits, issued, status ISSUED.
  2. Cache hot lookups with a TTL; evict entries touched by a delta.

Done when: Bulk validation of 1,000 LEIs returns per-LEI results with reasons.

Step 10: Deploy and automate

  1. Make sure ./mvnw verify and the GitHub Actions workflow are green on main.
  2. Optional: mirror the repository to gitlab.com so .gitlab-ci.yml runs too. Other platforms (Azure DevOps, AWS CodeBuild, Jenkins, Argo CD) are covered in the CI/CD guide.
  3. Deploy using the deployment guide: a single VPS (2 vCPU / 4 GB) is cheapest; AWS, Azure and GCP steps are there too.
  4. Put the public health URL (/actuator/health) at the top of your README.

Done when: the health URL returns UP from the internet, and no secret is in Git (git log -p | grep -i password finds nothing real).

Step 11: Update the architecture pack

  1. Copy the architecture/ folder from this capstone into your repository.
  2. Edit the Mermaid (.mmd) or draw.io (.drawio) files so all five diagrams match what you actually built; re-export SVG/PNG (draw.io: File → Export; Mermaid: npx @mermaid-js/mermaid-cli -i x.mmd -o x.svg).
  3. Write at least three ADRs of your own (copy the format in architecture/adr/): one for persistence, one for concurrency or performance, one you chose yourself.

Done when: someone can understand your system from the diagrams and ADRs without reading code.

Step 12: Write the README and record a demo

Your README must cover, in this order: the business problem; the architecture diagram; how to run it; API examples with curl; data sources and licences; design decisions and trade-offs; performance numbers (query plans, timings); what you'd do next. Then record a 3-minute demo video.

Done when: a hiring manager can read the README in three minutes and know what you built and why.
