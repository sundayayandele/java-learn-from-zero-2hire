Architecture and system design (read this first)

Before you write code, study how this system is designed. These five views are the target architecture for a production-grade build; reproduce and adapt them in your own repository, and keep them current as you build. Full explanations, Mermaid, draw.io, SVG and PNG sources and the architecture decision records are in architecture/.

1. Solution architecture

Solution architecture: the service is the bank's single source of reference rates for reporting, valuation and display. The ECB is the upstream source; the US Treasury dataset is a stretch source for currencies the ECB doesn't publish (such as NGN). Dealing rates for customer trades are a separate concern.

Sources: Mermaid · draw.io · SVG · PNG

2. Logical architecture

Logical architecture: an ingestion path (download → parse → idempotent load → cache eviction) and a query path (validate → resolve publication date → cross rate → round once). The store holds exactly what the ECB publishes (units per EUR); everything else is derived on read and labelled as such.

Sources: Mermaid · draw.io · SVG · PNG

3. Technical architecture

Technical architecture shows how the code is organised inside the Spring Boot 4 service: thin controllers that validate and translate errors, services that hold the business rules and transaction boundaries, and a persistence layer (JPA where entity behaviour and locking help, JdbcClient/SQL for reporting and bulk work). Cross-cutting concerns (configuration, health, metrics, scheduling, outbound HTTP) are framework features configured once. Package by feature in code; the layers here are logical.

Sources: Mermaid · draw.io · SVG · PNG

4. Infrastructure architecture

Infrastructure architecture shows where things run on the cheapest production-like target, a single VPS (for example SSDNodes). Only Caddy is reachable from the internet; it terminates TLS and forwards to fx-rates-service on Docker's internal network, so the database is never exposed (Docker port publishing bypasses ufw, so nothing else publishes ports). Images are built once by GitHub Actions, stored in GHCR by commit SHA, and pulled onto the server; backups leave the machine daily. Sizing and every command are in the deployment guide.

Sources: Mermaid · draw.io · SVG · PNG

Cloud architecture maps the service onto managed cloud building blocks, drawn for AWS (ECS Express Mode, the AWS-recommended path for new accounts since App Runner closed to new customers in 2026). Key design decisions

  1. One deployable Spring Boot service (modular monolith) on PostgreSQL
  2. Store ECB values per EUR; derive inverse and cross rates on read
  3. Round once, to the target currency's minor units
  4. Idempotent import guarded by a PostgreSQL advisory lock
  5. Platform scheduler on scale-to-zero platforms

Weeks 8–12. Modules used: 1, 2, 3, 4.

Business context

Remittance companies, card issuers, treasury desks and every bank's mobile app need exchange rates: to show customers what a foreign transaction will cost, to convert domiciliary-account balances for reporting, and to value positions at the end of the day. Most use an official reference rate source for reporting and valuation, separate from the dealing rates they quote to customers.

You will build the bank's internal FX reference-rate service: it imports the European Central Bank's daily reference rates, stores their full history, and answers "what was the USD/GBP reference rate on 3 March 2025?" and "convert ₦… to €… at yesterday's rate" with correct business-day handling, cross rates, rounding and attribution.

What you'll build

Import

  • Download the ECB's full history CSV (eurofxref-hist.zip) and daily file, parse them and store each (rate_date, currency, rate_per_eur) in PostgreSQL.
  • Idempotent: re-importing the same file inserts nothing new (ON CONFLICT DO NOTHING on a unique key).
  • Fast: JDBC batching (topic 3.5). The full history (~27 years × up to 41 currencies, about 220,000 values) must import in well under a minute, download included.
  • Record each import run (import_run: started, finished, source, rows read, rows inserted, status, error), exposed via the API.
  • A scheduled job imports the daily file every weekday after 16:30 CET (@Scheduled with a cron expression and time zone), plus an admin endpoint to trigger it manually. Make sure two instances don't import at the same time (a PostgreSQL advisory lock is the simplest option).
  • The parser must cope with the ECB's quirks: empty cells and N/A for currencies that didn't exist yet or were discontinued, and a trailing comma on each line.

Query API (suggested)

Method and path Purpose
GET /api/v1/rates/{base}/{quote}?date=2025-03-03 Rate for a date. EUR-based rates directly; any other pair as a cross rate via EUR
GET /api/v1/rates/{base}/{quote}/history?from=&to= Time series for charts
GET /api/v1/conversions?from=USD&to=GBP&amount=250.00&date= Convert an amount, rounded to the target currency's minor units
GET /api/v1/currencies Currencies available, with first and last dates
POST /api/v1/admin/imports Trigger an import
GET /api/v1/admin/imports Recent import runs

Every rate response includes the date actually used and the attribution "Source: ECB statistics".

Rules

  1. Business-day fallback: the ECB publishes only on TARGET working days. If no rate exists for the requested date (weekend, holiday), use the most recent earlier date and say so in the response (requestedDate, rateDate). Refuse dates more than 7 days after the latest available rate (422) and dates before 1999-01-04.
  2. Cross rates: rate(base→quote) = rate_per_eur(quote) / rate_per_eur(base), computed with BigDecimal at 10 decimal places using HALF_EVEN; EUR itself has a rate of 1.
  3. Conversions: round the converted amount to the target currency's default fraction digits (Currency.getDefaultFractionDigits(), e.g. 2 for USD, 0 for JPY) with HALF_EVEN. Document this rounding policy.
  4. Unknown currency codes → 404 Problem Detail (currency-not-found); currencies that exist but have no rate on or before that date → 404 (rate-not-available).
  5. Caching: cache rate lookups (@Cacheable), and evict the cache when an import inserts new rows. Expose cache hit/miss metrics.

Infrastructure and deployment

  • Sizing: app 0.5 vCPU / 768 MB–1 GB; PostgreSQL 1 vCPU / 1 GB / 5 GB is far more than needed (~200,000 rows).
  • Outbound network: the import job needs HTTPS access to www.ecb.europa.eu. Make the URL configurable, and set connection and read timeouts on the HTTP client.
  • Scheduling across instances: with more than one instance, only one should import (advisory lock or a "leader" flag). On serverless platforms that scale to zero (Cloud Run, Container Apps), trigger the import with the platform's scheduler (Cloud Scheduler, Container Apps jobs, EventBridge Scheduler) calling the admin endpoint instead of relying on @Scheduled.
  • Deploy with the deployment guide.

Stretch goals

  • Add the US Treasury dataset for NGN and other currencies, and choose sources per currency with a priority order.
  • Serve GET /rates/latest as a compact JSON object for a mobile app, with ETag/If-None-Match support.
  • A volatility report: the 30-day rolling standard deviation per currency, computed with a SQL window function.
  • Rewrite the service in Kotlin (topic 4.7) and compare.

Interview talking points

  • Why rates are stored per-EUR and cross rates computed, and where rounding happens.
  • How the import stays idempotent and safe with several instances.
  • The business-day fallback and how you tested time-dependent behaviour (injected Clock).
  • How you'd add a second source and resolve conflicts between sources.

Step-by-step build guide: FX reference rates service

Work through the steps in order. Each step ends with a Done when check: don't move on until it passes. Commit after every step with a clear message, so your history tells the story of the build.

Before you start

  • Finish the topics listed under "Skills you'll demonstrate" in the brief, or study them alongside.
  • Read the architecture section and the ADRs. You will update both at the end.
  • Install Java 21 (Temurin), Docker Desktop, Git and IntelliJ IDEA (topic 1.1).

Step 1: Create your repository from the starter

git clone https://github.com/sundayayandele/java-zero-hire.git
mkdir fx-rates-service && cp -R java-zero-hire/phases/01-foundations/capstones/02-fx-rates-service/starter/. fx-rates-service/
cd fx-rates-service
git init -b main && git add . && git commit -m "Start from the FX reference rates service starter"

Create an empty public repository called fx-rates-service on GitHub, then:

git remote add origin https://github.com/<your-username>/fx-rates-service.git
git push -u origin main

Done when: the Actions tab shows the CI workflow running on your first push.

Step 2: Run it locally

cp .env.example .env          # set DB_PASSWORD to anything local
docker compose up --build
curl http://localhost:8080/actuator/health
./mvnw verify                 # needs Docker running (Testcontainers)

Done when: health returns {"status":"UP"} and ./mvnw verify is green. The base package is ng.itlearning.fxrates.

Step 3: Get the data

Never commit raw datasets; download them with a script. Add data/ to .gitignore first.

mkdir -p data
curl -L -o data/eurofxref-hist.zip https://www.ecb.europa.eu/stats/eurofxref/eurofxref-hist.zip
unzip -o data/eurofxref-hist.zip -d data/

Copy the licence and attribution lines from the brief's Data section into your README now.

Done when: the files are in data/ and git status doesn't show them.

Step 4: Parse the ECB CSV in plain Java

  1. Read eurofxref-hist.csv: the header row lists currencies, then one row per date.
  2. Handle the quirks: empty cells, N/A, and the trailing comma on every line.
  3. Produce record EcbRate(LocalDate date, String currency, BigDecimal ratePerEur).
  4. Commit a tiny unmodified sample (5 dates) under src/test/resources/ecb/ with a README giving the attribution "Source: ECB statistics".

Done when: A parser unit test on the sample returns the exact number of rates and skips N/As.

Step 5: Implement cross rates and conversions

  1. rate(base, quote) = ratePerEur(quote) / ratePerEur(base) with BigDecimal.divide(x, 10, RoundingMode.HALF_EVEN); EUR is 1.
  2. Conversions round to Currency.getInstance(code).getDefaultFractionDigits() with HALF_EVEN (JPY 0 decimals, USD 2).
  3. Write the rounding policy in your README.

Done when: Unit tests cover EUR→USD, USD→GBP (cross), and a JPY conversion with 0 decimals.

Step 6: Schema and idempotent batch import

  1. Migration: fx_rate(rate_date, currency, rate_per_eur, PRIMARY KEY (rate_date, currency)), currency, and import_run.
  2. Insert with JdbcTemplate.batchUpdate in batches of 1,000 using INSERT ... ON CONFLICT DO NOTHING.
  3. Record each run in import_run (started, finished, rows read, rows inserted, status, error).

Done when: Importing the full history takes well under a minute, and importing it again inserts 0 rows.

Step 7: Business-day fallback and validation

  1. Query the latest rate_date <= requested date (an index on (currency, rate_date DESC) makes this instant).
  2. Return both requestedDate and rateDate in the response.
  3. Reject dates before 1999-01-04 and more than 7 days after the latest rate with 422.
  4. Unknown currency → 404 currency-not-found; no rate on or before that date → 404 rate-not-available.

Done when: Asking for a Saturday returns Friday's rate with both dates shown.

Step 8: Query API

  1. Implement the rate, history, conversion and currencies endpoints from the brief with DTO records.
  2. Every response includes "attribution": "Source: ECB statistics" and labels cross rates as derived.
  3. Write @WebMvcTest tests for each Problem Detail.

Done when: All endpoints documented with curl examples in your README.

Step 9: Scheduled daily import with a lock

  1. @Scheduled(cron = "0 45 16 * * MON-FRI", zone = "Europe/Berlin") downloads the daily file.
  2. Wrap the import in pg_try_advisory_lock(...) so only one instance imports at a time.
  3. Add POST /api/v1/admin/imports to trigger it manually and GET to list runs.

Done when: Two app instances started at once produce exactly one import run.

Step 10: Caching and metrics

  1. Add spring-boot-starter-cache and @Cacheable("rates") on the lookup; @CacheEvict(allEntries = true) after an import inserts rows.
  2. Expose cache hits and misses and an fx.import.rows counter.

Done when: A repeated lookup doesn't hit the database (check with SQL logging), and cache metrics appear at /actuator/prometheus.

Step 11: Deploy and automate

  1. Make sure ./mvnw verify and the GitHub Actions workflow are green on main.
  2. Optional: mirror the repository to gitlab.com so .gitlab-ci.yml runs too. Other platforms (Azure DevOps, AWS CodeBuild, Jenkins, Argo CD) are covered in the CI/CD guide.
  3. Deploy using the deployment guide: a single VPS (2 vCPU / 4 GB) is cheapest; AWS, Azure and GCP steps are there too.
  4. Put the public health URL (/actuator/health) at the top of your README.

Done when: the health URL returns UP from the internet, and no secret is in Git (git log -p | grep -i password finds nothing real).

Step 12: Update the architecture pack

  1. Copy the architecture/ folder from this capstone into your repository.
  2. Edit the Mermaid (.mmd) or draw.io (.drawio) files so all five diagrams match what you actually built; re-export SVG/PNG (draw.io: File → Export; Mermaid: npx @mermaid-js/mermaid-cli -i x.mmd -o x.svg).
  3. Write at least three ADRs of your own (copy the format in architecture/adr/): one for persistence, one for concurrency or performance, one you chose yourself.

Done when: someone can understand your system from the diagrams and ADRs without reading code.

Step 13: Write the README and record a demo

Your README must cover, in this order: the business problem; the architecture diagram; how to run it; API examples with curl; data sources and licences; design decisions and trade-offs; performance numbers (query plans, timings); what you'd do next. Then record a 3-minute demo video.

Done when: a hiring manager can read the README in three minutes and know what you built and why.
