Architecture and system design (read this first)

Before you write code, study how this system is designed. These five views are the target architecture for a production-grade build; reproduce and adapt them in your own repository, and keep them current as you build. Full explanations, Mermaid, draw.io, SVG and PNG sources and the architecture decision records are in architecture/.

1. Solution architecture

Solution architecture places the ledger in its business context: channels call it to move money, operations use it for statements and controls, and finance reads the trial balance. In a real bank it sits behind an API gateway and feeds the general ledger and reconciliation (Capstone 10).

Sources: Mermaid · draw.io · SVG · PNG

2. Logical architecture

Logical architecture shows the capabilities and the data they own, independent of technology. Every money movement is a journal of balanced postings; balances are derived from postings and cached on the account in the same transaction. Rules (limits, fees, status) are checked before posting; the database enforces the invariants again (balanced journals, immutable postings, unique references).

Sources: Mermaid · draw.io · SVG · PNG

3. Technical architecture

Technical architecture shows how the code is organised inside the Spring Boot 4 service: thin controllers that validate and translate errors, services that hold the business rules and transaction boundaries, and a persistence layer (JPA where entity behaviour and locking help, JdbcClient/SQL for reporting and bulk work). Cross-cutting concerns (configuration, health, metrics, scheduling, outbound HTTP) are framework features configured once. Package by feature in code; the layers here are logical.

Sources: Mermaid · draw.io · SVG · PNG

4. Infrastructure architecture

Infrastructure architecture shows where things run on the cheapest production-like target, a single VPS (for example SSDNodes). Only Caddy is reachable from the internet; it terminates TLS and forwards to core-banking-ledger on Docker's internal network, so the database is never exposed (Docker port publishing bypasses ufw, so nothing else publishes ports). Images are built once by GitHub Actions, stored in GHCR by commit SHA, and pulled onto the server; backups leave the machine daily. Sizing and every command are in the deployment guide.

Sources: Mermaid · draw.io · SVG · PNG

5. Cloud architecture

Cloud architecture maps the service onto managed cloud building blocks, drawn for AWS (ECS Express Mode, the AWS-recommended path for new accounts since App Runner closed to new customers in 2026). The database sits in private subnets; credentials come from the secret store, never from the image; images are immutable and tagged by commit SHA. The same design on the other clouds:

Key design decisions

  1. One deployable Spring Boot service (modular monolith) on PostgreSQL
  2. Double-entry journals with immutable postings
  3. Pessimistic row locks in a consistent order
  4. Idempotency by client reference plus request fingerprint
  5. JPA for writes, SQL (JdbcClient) for reads

Required for every learner. Weeks 6–13. Modules used: 1, 2, 3, 4.

Business context

Every bank, wallet and payment company sits on a ledger: the record of who owns how much, and every movement that changed it. Tier-1 Nigerian banks, mobile-money operators and fintech wallets all run some version of a double-entry ledger. When it is wrong, customers lose money, regulators fine the institution, and finance teams spend nights reconciling. When it is right, it is invisible.

You will build the ledger service for a small digital bank, ITL Bank: customer wallet accounts, internal general-ledger (GL) accounts, deposits, transfers with fees, reversals, statements and a trial balance, correct under concurrent load and safe against duplicate requests.

What you'll build

A Spring Boot 4 REST service backed by PostgreSQL.

Accounts

  • Customer accounts (type LIABILITY from the bank's point of view): 10-digit account number generated by the service, holder name, currency (NGN by default; must be a valid java.util.Currency), status ACTIVE / FROZEN / CLOSED, daily transfer limit.
  • Internal GL accounts created by a migration: CASH (asset, the source of deposits), FEE_INCOME (income), SUSPENSE (for reversals and unmatched items).

Double-entry journals

Every business event is a journal with two or more postings. Each posting debits or credits one account. The postings of every journal sum to zero per currency. Balances are derived from postings, and also stored on the account row (updated in the same transaction) for fast reads. A consistency check endpoint proves the two agree.

Event Postings
Deposit ₦50,000 into A Debit CASH 50,000; Credit A 50,000
Transfer ₦20,000 from A to B with ₦26.88 fee Debit A 20,026.88; Credit B 20,000; Credit FEE_INCOME 26.88
Reversal of that transfer The exact opposite postings, as a new journal that references the original

Postings are never updated or deleted. Mistakes are corrected with reversing journals, which is how real ledgers stay auditable.

API (suggested)

Method and path Purpose Notes
POST /api/v1/accounts Open an account 201 + Location
GET /api/v1/accounts/{number} Account details and balance 404 Problem Detail if unknown
POST /api/v1/accounts/{number}/freeze and /unfreeze Change status 204
POST /api/v1/deposits Deposit from CASH Requires reference
POST /api/v1/transfers Transfer between customer accounts Requires reference; fee applied
POST /api/v1/transfers/{reference}/reversal Reverse a transfer Once only
GET /api/v1/accounts/{number}/statement?from=&to=&page= Statement with opening balance, running balance and closing balance Paged
GET /api/v1/ledger/trial-balance Every account's balance; total of debits equals total of credits
GET /api/v1/ledger/consistency Compares stored balances with posting sums Should always report zero differences

Business rules

  1. Amounts are positive, at most 2 decimal places (validate with @Digits), in the account's currency.
  2. A customer account can never go below zero (no overdrafts in this capstone).
  3. FROZEN and CLOSED accounts can neither send nor receive.
  4. Transfers to the same account are rejected.
  5. Fees follow tiers configured in application.yaml via @ConfigurationProperties (example: up to ₦5,000 → ₦10.75; up to ₦50,000 → ₦26.88; above → ₦53.75; the fee counts towards the balance check).
  6. Daily limit: the sum of a customer's outgoing transfers (amount + fee) on the current business day (Africa/Lagos time) may not exceed the account's limit.
  7. Idempotency: reference is unique per journal. Repeating a request with the same reference and the same payload returns the original result (HTTP 200) without posting again. The same reference with a different payload is a 409 Conflict.
  8. A transfer can be reversed only once, and only if the receiving account still has the funds (otherwise 422).

Errors

All errors are RFC 9457 Problem Details with stable type URIs: account-not-found (404), validation-failed (400), insufficient-funds (422), daily-limit-exceeded (422), account-not-active (422), duplicate-reference (409), already-reversed (409).

Data

No external dataset: the ledger's data is what your API creates. Write a small load generator (a test helper or a separate main) that opens 1,000 accounts and runs 100,000 random deposits and transfers, so you can test performance and statements at realistic volume. Generated data is yours; publish it under CC0 if you share it. Currency rules come from java.util.Currency.

Infrastructure and deployment

  • Local: docker compose up --build from the starter.
  • Sizing: app 0.5 vCPU / 1 GB RAM (-XX:MaxRAMPercentage=75); PostgreSQL 1 vCPU / 1 GB / 10 GB storage is ample for the load generator. A single 2 vCPU / 4 GB VPS runs both.
  • CI/CD: GitHub Actions (primary) and GitLab CI (secondary) come with the starter.
  • Deploy: follow the deployment guide for a VPS, AWS, Azure or GCP. Use a managed PostgreSQL on the cloud platforms; enable automated backups (a ledger without backups is not a ledger).

Stretch goals

  • Multi-currency accounts with an FX journal using Capstone 2's rates (four postings across two currencies plus an FX position account).
  • GET /accounts/{number}/balance?asOf=2026-10-01T00:00:00Z (historical balance from postings).
  • An outbox table that records TransferCompleted events in the same transaction (the pattern you'll use with Kafka in Module 11).
  • Optimistic locking alternative and a benchmark comparing it with pessimistic locking under contention.

Interview talking points

  • How you prevented double-spending across several service instances, and why synchronized would not have worked.
  • How idempotency works, and what happens if the client times out and retries.
  • The query plan for your statement endpoint before and after indexing.

Step-by-step build guide: Core banking ledger

Work through the steps in order. Each step ends with a Done when check: don't move on until it passes. Commit after every step with a clear message, so your history tells the story of the build.

Before you start

  • Finish the topics listed under "Skills you'll demonstrate" in the brief, or study them alongside.
  • Read the architecture section and the ADRs. You will update both at the end.
  • Install Java 21 (Temurin), Docker Desktop, Git and IntelliJ IDEA (topic 1.1).

Step 1: Create your repository from the starter

git clone https://github.com/sundayayandele/java-zero-hire.git
mkdir core-banking-ledger && cp -R java-zero-hire/phases/01-foundations/capstones/01-core-banking-ledger/starter/. core-banking-ledger/

git remote add origin https://github.com/<your-username>/core-banking-ledger.git

Done when: the Actions tab shows the CI workflow running on your first push.

Step 2: Run it locally

cp .env.example .env          # set DB_PASSWORD to anything local
docker compose up --build
curl http://localhost:8080/actuator/health
./mvnw verify                 # needs Docker running (Testcontainers)

Done when: health returns {"status":"UP"} and ./mvnw verify is green. The base package is ng.itlearning.ledger.

Step 3: Plan your data

This capstone generates its own data (see the brief's Data section). Write the generator as part of the build steps below and release generated data under CC0.

Step 4: Model money and accounts in plain Java

  1. Create a Money record (BigDecimal amount, Currency currency) that rejects nulls, rounds to the currency's minor units with HALF_EVEN and refuses to add different currencies.
  2. Create AccountType (enum: CUSTOMER, FEE_INCOME, SUSPENSE) and AccountStatus (ACTIVE, FROZEN, CLOSED).
  3. Create a sealed JournalType (Deposit, Withdrawal, Transfer, Reversal) and a Posting record (account, debit/credit, Money).
  4. Write Journal so its constructor throws if the postings don't sum to zero: this is the double-entry invariant.
  5. No Spring yet. Put everything in ledger.domain and unit-test it with JUnit 5 and AssertJ.

Done when: Money and Journal unit tests pass, including new Journal(...) failing for unbalanced postings.

Step 5: Write the fee schedule and limits

  1. Implement the tiered transfer fee from the brief as a pure function Money feeFor(Money amount).
  2. Write boundary tests at exactly ₦5,000.00, ₦5,000.01, ₦50,000.00 and ₦50,000.01 (use @ParameterizedTest with @CsvSource).
  3. Add daily-limit checks as a separate pure function taking the amount already sent today.

Done when: All boundary tests are green and the fee code has no double anywhere.

Step 6: Design the schema and Flyway migrations

  1. Replace V1__baseline.sql with V1__ledger_schema.sql: tables account, journal, posting, idempotency_key.
  2. Enforce rules in the database: CHECK (amount > 0) on postings, UNIQUE (reference) on journals, foreign keys everywhere, NOT NULL by default.
  3. Store the current balance on account (updated in the same transaction as postings) and keep postings immutable (no UPDATE/DELETE grants in production).
  4. Add indexes for posting(account_id, created_at) (statements) and journal(reference).
  5. Run docker compose up --build and check the Flyway log shows your migration applied.

Done when: ./mvnw verify passes: the Testcontainers test proves your migration runs on a real PostgreSQL 17.

Step 7: Post journals with row locks

  1. Write PostingService.transfer(from, to, amount, reference) annotated @Transactional.
  2. Lock both accounts with SELECT ... FOR UPDATE, always in ascending account-id order so two opposite transfers can't deadlock.
  3. Inside the lock: check status, check balance (no overdraft), insert the journal and postings, update both balances.
  4. Use JdbcClient or Spring Data JPA with @Lock(PESSIMISTIC_WRITE); either is fine, but be able to explain your choice.

Done when: A test firing 50 parallel transfers between 10 accounts leaves total money unchanged and no balance negative.

Step 8: Make transfers idempotent

  1. Store (reference, request_hash, response) in idempotency_key in the same transaction as the journal.
  2. Same reference and same payload: return the stored response with 200. Same reference with a different payload: 409 Conflict.
  3. Test the client-timeout case: call twice with the same reference and assert only one journal exists.

Done when: The idempotency acceptance tests in the brief pass.

Step 9: Build the REST API

  1. Add DTO records with Bean Validation (@NotNull, @Positive, @Digits(integer = 15, fraction = 2)).
  2. Controllers: open account, deposit, withdraw, transfer, reverse, get account, statement.
  3. Map each domain exception to a Problem Detail (insufficient-funds → 422, account-frozen → 422, duplicate-reference → 409, not found → 404).
  4. Write @WebMvcTest tests for validation errors and each Problem Detail.

Done when: curl examples for every endpoint are in your README and return the documented status codes.

Step 10: Statements, trial balance and consistency check

  1. Statement endpoint: postings for a period with a running balance using SUM(...) OVER (ORDER BY created_at) (topic 3.1).
  2. Trial balance: total debits and credits per account type; they must be equal.
  3. GET /ledger/consistency: compare each account's stored balance with the sum of its postings and report differences.
  4. Run EXPLAIN ANALYZE on the statement query with 100,000 postings before and after your index, and paste both plans in your README.

Done when: Closing balance = opening + credits − debits for any period, and the consistency check reports zero differences after the load test.

Step 11: Load generator and business metrics

  1. Write a load generator (a test helper or a CommandLineRunner behind a profile) that opens 1,000 accounts and runs 100,000 random deposits and transfers.
  2. Add Micrometer metrics ledger.journals (counter tagged by type) and ledger.transfer.amount (distribution summary).
  3. Check them at /actuator/prometheus.

Done when: The generator finishes, the consistency check is clean, and both metrics appear in Prometheus format.

Step 12: Deploy and automate

  1. Make sure ./mvnw verify and the GitHub Actions workflow are green on main.
  2. Optional: mirror the repository to gitlab.com so .gitlab-ci.yml runs too. Other platforms (Azure DevOps, AWS CodeBuild, Jenkins, Argo CD) are covered in the CI/CD guide.
  3. Deploy using the deployment guide: a single VPS (2 vCPU / 4 GB) is cheapest; AWS, Azure and GCP steps are there too.
  4. Put the public health URL (/actuator/health) at the top of your README.

Done when: the health URL returns UP from the internet, and no secret is in Git (git log -p | grep -i password finds nothing real).

  2. Edit the Mermaid (.mmd) or draw.io (.drawio) files so all five diagrams match what you actually built; re-export SVG/PNG (draw.io: File → Export; Mermaid: npx @mermaid-js/mermaid-cli -i x.mmd -o x.svg).
  3. Write at least three ADRs of your own (copy the format in architecture/adr/): one for persistence, one for concurrency or performance, one you chose yourself.
