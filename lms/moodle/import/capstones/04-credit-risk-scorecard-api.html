Architecture and system design (read this first)

Before you write code, study how this system is designed. These five views are the target architecture for a production-grade build; reproduce and adapt them in your own repository, and keep them current as you build. Full explanations, Mermaid, draw.io, SVG and PNG sources and the architecture decision records are in architecture/.

1. Solution architecture

Solution architecture: the risk team owns the rules and reviews performance; card operations act on grades (limit changes, reviews). Scores feed limit-management systems; protected attributes are excluded by design.

Sources: Mermaid · draw.io · SVG · PNG

2. Logical architecture

Logical architecture: rules are data, versioned and audited; the scoring engine is a pure function of (profile, rule-set version) that returns a score, grade, action and reason codes; runs re-score the whole book concurrently; performance analytics compare grades with actual defaults.

Sources: Mermaid · draw.io · SVG · PNG

3. Technical architecture

Technical architecture shows how the code is organised inside the Spring Boot 4 service: thin controllers that validate and translate errors, services that hold the business rules and transaction boundaries, and a persistence layer (JPA where entity behaviour and locking help, JdbcClient/SQL for reporting and bulk work). Cross-cutting concerns (configuration, health, metrics, scheduling, outbound HTTP) are framework features configured once. Package by feature in code; the layers here are logical.

Sources: Mermaid · draw.io · SVG · PNG

4. Infrastructure architecture

Infrastructure architecture shows where things run on the cheapest production-like target, a single VPS (for example SSDNodes). Only Caddy is reachable from the internet; it terminates TLS and forwards to credit-risk-scorecard-api on Docker's internal network, so the database is never exposed (Docker port publishing bypasses ufw, so nothing else publishes ports). Images are built once by GitHub Actions, stored in GHCR by commit SHA, and pulled onto the server; backups leave the machine daily. Sizing and every command are in the deployment guide.

Sources: Mermaid · draw.io · SVG · PNG

Cloud architecture maps the service onto managed cloud building blocks, drawn for AWS (ECS Express Mode, the AWS-recommended path for new accounts since App Runner closed to new customers in 2026). Key design decisions

  1. One deployable Spring Boot service (modular monolith) on PostgreSQL
  2. Rules as versioned data, scores record their version
  3. Pure scoring function
  4. Bulk runs on virtual threads with batched writes
  5. Exclude protected attributes

Weeks 8–13. Modules used: 1, 2, 3, 4.

Business context

Card issuers and lenders score every customer regularly: who is likely to default next month, whose credit limit should be reduced, who deserves an increase. Before (and alongside) machine learning, banks use scorecards: transparent, rule-based points systems that credit-risk teams can explain to regulators and customers. Explainability is not optional: when a limit is cut, the bank must be able to say why.

You'll build a behavioural scorecard service: it loads 30,000 real (anonymised) credit-card customer histories, computes a score for each from configurable rules, explains every score, runs bulk re-scoring concurrently, and lets the risk team measure how well the scorecard separates defaulters from non-defaulters.

What you'll build

Scorecard rules

Model rules as a sealed hierarchy so every rule type is handled exhaustively:

public sealed interface ScoreRule permits RangeRule, RatioRule, CountRule { }

Examples (store rules and their points as data in PostgreSQL, so the risk team can change them without a deployment):

Rule Points
Months (of the last 6) with repayment status ≥ 2 months late 0 → +40, 1 → +10, 2–3 → −30, 4+ → −80
Latest bill amount ÷ credit limit (utilisation) < 30% → +30, 30–70% → +5, 70–100% → −25, > 100% → −60
Payment amount ÷ bill amount, average over 6 months ≥ 100% → +35, 50–99% → +10, < 50% → −20
Credit limit band Configured bands

The score is a base (e.g. 600) plus the sum of rule points, then mapped to a risk grade (A–E) and an action (increase limit, keep, review, reduce, block new spending).

API (suggested)

Method and path Purpose
POST /api/v1/admin/imports Load the dataset (idempotent)
GET /api/v1/customers/{id}/score Score with grade, action and reason codes: each rule's contribution, sorted by impact
POST /api/v1/scores/preview Score an arbitrary profile in the request body (what-if)
POST /api/v1/scoring-runs Re-score all customers asynchronously; returns a run ID (202 Accepted)
GET /api/v1/scoring-runs/{id} Run status, counts per grade, duration
GET /api/v1/scoring-runs/{id}/performance Default rate per grade (from the dataset's label) and a simple Gini/KS statistic
GET/PUT /api/v1/rules View and change rule points (validated; audited)

Rules and quality bar

  1. Scoring is a pure function of the customer profile and rule set: easy to unit test, no database calls inside.
  2. Each score stores the rule-set version it was computed with, so past decisions can be explained after the rules change.
  3. Bulk scoring of 30,000 customers uses virtual threads or a bounded executor, writes results in JDBC batches, and must finish in well under a minute on a laptop. Report the timing.
  4. Rule changes are validated (no overlapping or missing ranges) and recorded in an audit table with who and when.
  5. Fairness: the dataset includes sex, education, marital status and age. Do not use sex or marital status as scoring inputs; document why in your README, and report default rates by grade with and without age as a check.

Acceptance criteria

Infrastructure and deployment

App 1 vCPU / 1 GB (bulk scoring is CPU-light but benefits from a second core); PostgreSQL 1 vCPU / 2 GB / 5 GB. Run scoring runs on demand; on scale-to-zero platforms trigger them with the platform scheduler. CI from the starter; deploy with the deployment guide.

Stretch goals

  • A Population Stability Index (PSI) check between two scoring runs.
  • Stream progress of a scoring run with Server-Sent Events.
  • Compare your scorecard's Gini with a simple logistic regression trained in Python (outside the service), and explain the trade-off between accuracy and explainability.

Interview talking points

Step-by-step build guide: Credit-card default risk scorecard API

Work through the steps in order. Each step ends with a Done when check: don't move on until it passes. Commit after every step with a clear message, so your history tells the story of the build.

Before you start

  • Finish the topics listed under "Skills you'll demonstrate" in the brief, or study them alongside.
  • Read the architecture section and the ADRs. You will update both at the end.
  • Install Java 21 (Temurin), Docker Desktop, Git and IntelliJ IDEA (topic 1.1).

Step 1: Create your repository from the starter

git clone https://github.com/sundayayandele/java-zero-hire.git
mkdir credit-risk-scorecard-api && cp -R java-zero-hire/phases/01-foundations/capstones/04-credit-risk-scorecard-api/starter/. credit-risk-scorecard-api/
cd credit-risk-scorecard-api
git init -b main && git add . && git commit -m "Start from the Credit-card default risk scorecard API starter"

Create an empty public repository called credit-risk-scorecard-api on GitHub, then:

git remote add origin https://github.com/<your-username>/credit-risk-scorecard-api.git
git push -u origin main

Done when: the Actions tab shows the CI workflow running on your first push.

Step 2: Run it locally

cp .env.example .env          # set DB_PASSWORD to anything local
docker compose up --build
curl http://localhost:8080/actuator/health
./mvnw verify                 # needs Docker running (Testcontainers)

Done when: health returns {"status":"UP"} and ./mvnw verify is green. The base package is ng.itlearning.scorecard.

Step 3: Get the data

Never commit raw datasets; download them with a script. Add data/ to .gitignore first.

mkdir -p data
curl -L -o data/default_credit.zip https://archive.ics.uci.edu/static/public/350/default+of+credit+card+clients.zip && unzip -o data/default_credit.zip -d data/
# Convert the .xls to CSV once (LibreOffice: soffice --headless --convert-to csv data/*.xls --outdir data/), or read it with Apache POI

Copy the licence and attribution lines from the brief's Data section into your README now.

Done when: the files are in data/ and git status doesn't show them.

Step 4: Load the dataset

  1. Map the 30,000 rows to CustomerProfile records (limit, age, six months of repayment status, bills and payments, default flag).
  2. Migration for customer_profile; import with JDBC batches, idempotent on the customer ID.
  3. Do not load sex or marital status into scoring inputs (keep them only for the fairness report, or drop them).

Done when: POST /api/v1/admin/imports loads 30,000 rows, and running it again changes nothing.

Step 5: Rules as a sealed hierarchy

  1. Sealed ScoreRule permits RangeRule, RatioRule, CountRule, each returning a RuleResult(ruleId, points, reason).
  2. Store rules and points in score_rule with a rule_set_version.
  3. Validate rule sets: ranges must not overlap or leave gaps.

Done when: A validator unit test rejects an overlapping range set with a clear message.

Step 6: Pure scoring function with reason codes

  1. Score score(CustomerProfile p, RuleSet rules): base + sum of points, mapped to grade A–E and an action.
  2. Return every rule's contribution sorted by absolute impact: these are the reason codes.
  3. No database calls inside the function.

Done when: Unit tests cover each grade boundary and assert the reason codes' order.

Step 7: Score and preview endpoints

  1. GET /api/v1/customers/{id}/score and POST /api/v1/scores/preview (what-if).
  2. Each stored score records the rule-set version it used.

Done when: Changing a rule doesn't change the explanation of an old stored score.

Step 8: Bulk re-scoring with virtual threads

  1. POST /api/v1/scoring-runs returns 202 with a run ID, then scores all customers on Executors.newVirtualThreadPerTaskExecutor() with a Semaphore limiting database work.
  2. Write results with batchUpdate in batches of 1,000.
  3. Track status, counts per grade and duration in scoring_run.

Done when: 30,000 customers re-score in well under a minute; put the timing in your README.

Step 9: Measure the scorecard

  1. /scoring-runs/{id}/performance: default rate per grade, plus KS (the maximum gap between cumulative good and bad distributions) and Gini (2·AUC − 1).
  2. Fairness check: compare default rates by grade with and without age as an input, and write up what you found.

Done when: Default rate rises from grade A to E; KS and Gini are reported with a short interpretation.

Step 10: Audited rule changes and metrics

  1. PUT /api/v1/rules validates, creates a new rule-set version and writes an audit row (who, when, before, after).
  2. Metrics: scorecard.scores by grade and a timer for scoring runs.

Done when: The audit table shows every change, and metrics appear at /actuator/prometheus.

Step 11: Deploy and automate

  1. Make sure ./mvnw verify and the GitHub Actions workflow are green on main.
  2. Optional: mirror the repository to gitlab.com so .gitlab-ci.yml runs too. Other platforms (Azure DevOps, AWS CodeBuild, Jenkins, Argo CD) are covered in the CI/CD guide.
  3. Deploy using the deployment guide: a single VPS (2 vCPU / 4 GB) is cheapest; AWS, Azure and GCP steps are there too.
  4. Put the public health URL (/actuator/health) at the top of your README.

Done when: the health URL returns UP from the internet, and no secret is in Git (git log -p | grep -i password finds nothing real).

Step 12: Update the architecture pack

  1. Copy the architecture/ folder from this capstone into your repository.
  2. Edit the Mermaid (.mmd) or draw.io (.drawio) files so all five diagrams match what you actually built; re-export SVG/PNG (draw.io: File → Export; Mermaid: npx @mermaid-js/mermaid-cli -i x.mmd -o x.svg).
  3. Write at least three ADRs of your own (copy the format in architecture/adr/): one for persistence, one for concurrency or performance, one you chose yourself.

Done when: someone can understand your system from the diagrams and ADRs without reading code.
