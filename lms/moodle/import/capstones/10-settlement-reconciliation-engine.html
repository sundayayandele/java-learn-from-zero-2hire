Architecture and system design (read this first)

Before you write code, study how this system is designed. Full explanations, Mermaid, draw.io, SVG and PNG sources and the architecture decision records are in architecture/.

1. Solution architecture

Solution architecture: every value date, operations reconcile the bank's ledger with each partner's settlement file; breaks are worked to resolution before cut-off and summarised for finance.

Sources: Mermaid · draw.io · SVG · PNG

2. Logical architecture

Logical architecture: intake stores each file once (by checksum) and parses it into staging; matching runs ordered passes over the remaining unmatched items (exact in SQL, then normalised reference, tolerance and date-window passes); break management classifies and resolves exceptions; controls prove that matched plus unmatched value equals each file's total.

Sources: Mermaid · draw.io · SVG · PNG

3. Technical architecture

Technical architecture shows how the code is organised inside the Spring Boot 4 service: thin controllers that validate and translate errors, services that hold the business rules and transaction boundaries, and a persistence layer (JPA where entity behaviour and locking help, JdbcClient/SQL for reporting and bulk work). Cross-cutting concerns (configuration, health, metrics, scheduling, outbound HTTP) are framework features configured once. Package by feature in code; the layers here are logical.

Sources: Mermaid · draw.io · SVG · PNG

4. Infrastructure architecture

Infrastructure architecture shows where things run on the cheapest production-like target, a single VPS (for example SSDNodes). Only Caddy is reachable from the internet; it terminates TLS and forwards to settlement-reconciliation-engine on Docker's internal network, so the database is never exposed (Docker port publishing bypasses ufw, so nothing else publishes ports). Images are built once by GitHub Actions, stored in GHCR by commit SHA, and pulled onto the server; backups leave the machine daily. Sizing and every command are in the deployment guide.

Key design decisions

  1. One deployable Spring Boot service (modular monolith) on PostgreSQL
  2. Ordered matching passes, set-based first
  3. Control totals on every run
  4. Files in object storage, idempotent by checksum

Weeks 9–13. Modules used: 1, 2, 3, 4.

Business context

Every day, a bank's internal ledger must agree with external records: the card scheme's settlement file, the NIP/NIBSS settlement report, the mobile-money partner's statement, the correspondent bank's MT940. Where they disagree, money is at risk: a customer was debited but the partner never received it, or a partner settled a transaction the bank never recorded. Reconciliation teams match millions of records daily, chase exceptions, and must clear them within strict deadlines. Automating the matching, and making exceptions easy to investigate, is classic and valuable backend work.

You'll build a reconciliation engine that ingests an internal ledger extract and an external settlement file, matches them with configurable rules, classifies the breaks, and gives operations a workflow to resolve them.

What you'll build

Inputs

  • Internal ledger extract: one row per transaction (reference, account, amount, currency, direction, value date, channel, status).
  • External settlement file: the partner's view (partner reference, our reference where available, amount, fee, currency, settlement date, status).
  • A generator (part of your project) that produces matching pairs of files from a base dataset, with deliberately injected breaks: missing on either side, amount mismatches, duplicated records, timing differences (settled a day later), reference formatting differences (leading zeros, prefixes, case). Use PaySim rows as the base transactions for realistic amounts and volumes, or generate entirely synthetic data.

Matching

Configurable, ordered match rules (sealed hierarchy), applied in passes:

  1. Exact: same reference, amount and currency.
  2. Normalised reference: after stripping prefixes, leading zeros and case.
  3. Tolerance: same reference, amount within a configured tolerance (for example partner fees), flagged MATCHED_WITH_DIFFERENCE.
  4. Date window: same amount and account within ±1 business day when references are missing.

Each pass works only on records still unmatched. Implement the first pass as a set-based SQL FULL OUTER JOIN (topic 3.1) and the fuzzier passes in Java over bounded batches, or entirely in SQL: justify the split.

Outcomes

MATCHED, MATCHED_WITH_DIFFERENCE, MISSING_IN_LEDGER, MISSING_IN_PARTNER, DUPLICATE, AMOUNT_MISMATCH, each with evidence.

API (suggested)

Method and path Purpose
POST /api/v1/files Upload a ledger or partner file (multipart), validated and loaded into staging with batching; idempotent by file checksum
POST /api/v1/recon-runs Reconcile a ledger file against a partner file for a value date (async)
GET /api/v1/recon-runs/{id} Summary: totals per outcome, matched value, unmatched value, duration
GET /api/v1/recon-runs/{id}/breaks?type=&page= Exceptions to work
POST /api/v1/breaks/{id}/resolutions Resolve with a reason (write-off, manual match, raised with partner); audited
GET /api/v1/recon-runs/{id}/report.csv Exception report for operations

Quality bar

  1. A run over 1 million records per side completes in minutes on a laptop; document timings and where the time goes.
  2. Totals always reconcile: matched value + unmatched value on each side equals that side's file total.
  3. Re-uploading a file is idempotent (checksum); re-running a reconciliation produces the same result.
  4. Manual matches and resolutions are audited and can be reversed with a reason.

Acceptance criteria

Infrastructure and deployment

App 1–2 vCPU / 2 GB for million-row runs; PostgreSQL 2 vCPU / 4 GB / 20 GB. Set spring.servlet.multipart.max-file-size deliberately, and store uploaded files on disk or object storage (S3, Azure Blob, GCS), not in the database. Runs are batch jobs: avoid scale-to-zero platforms' request timeouts by running them asynchronously. CI from the starter with small generated fixtures; deploy with the deployment guide.

Stretch goals

  • Parse a real-world format: SWIFT MT940 or ISO 20022 camt.053 statements (write a small parser and fixtures).
  • Auto-resolution rules for known timing differences that clear the next day.
  • Post write-offs to the Capstone 1 ledger through its API.

Interview talking points

  • How you designed matching passes, and the trade-off between SQL and Java for each.
  • How you proved nothing was lost (control totals).
  • How you made a million-row run fast, and what you'd change for 100 million.

Step-by-step build guide: Settlement reconciliation engine

Work through the steps in order. Each step ends with a Done when check: don't move on until it passes. Commit after every step with a clear message, so your history tells the story of the build.

Before you start

  • Finish the topics listed under "Skills you'll demonstrate" in the brief, or study them alongside.
  • Read the architecture section and the ADRs. You will update both at the end.
  • Install Java 21 (Temurin), Docker Desktop, Git and IntelliJ IDEA (topic 1.1).

Step 1: Create your repository from the starter

git clone https://github.com/sundayayandele/java-zero-hire.git
mkdir settlement-reconciliation-engine && cp -R java-zero-hire/phases/01-foundations/capstones/10-settlement-reconciliation-engine/starter/. settlement-reconciliation-engine/
cd settlement-reconciliation-engine
git init -b main && git add . && git commit -m "Start from the Settlement reconciliation engine starter"

Create an empty public repository called settlement-reconciliation-engine on GitHub, then:

git remote add origin https://github.com/<your-username>/settlement-reconciliation-engine.git
git push -u origin main

Done when: the Actions tab shows the CI workflow running on your first push.

Step 2: Run it locally

cp .env.example .env          # set DB_PASSWORD to anything local
docker compose up --build
curl http://localhost:8080/actuator/health
./mvnw verify                 # needs Docker running (Testcontainers)

Done when: health returns {"status":"UP"} and ./mvnw verify is green. The base package is ng.itlearning.recon.

Step 3: Get the data

Never commit raw datasets; download them with a script. Add data/ to .gitignore first.

mkdir -p data
# Optional base data: PaySim (CC BY-SA 4.0) from https://www.kaggle.com/datasets/ealaxi/paysim1

Copy the licence and attribution lines from the brief's Data section into your README now.

Done when: the files are in data/ and git status doesn't show them.

Step 4: File generator with injected breaks

  1. Generate a ledger extract and a partner file from base transactions.
  2. Inject breaks with known counts: missing on each side, amount mismatches, duplicates, settled a day later, reference formatting (prefixes, leading zeros, case).
  3. Write the expected outcome counts next to the files so tests can check them.

Done when: The generator writes 1 million rows per side plus an expected-results file.

Step 5: Upload and stage files

  1. POST /api/v1/files (multipart) validates and loads into staging with batching or COPY.
  2. Idempotent by SHA-256 checksum.

Done when: Uploading the same file twice returns the original file ID.

Step 6: Match rules as a sealed hierarchy

  1. Sealed MatchRule permits ExactMatch, NormalisedReferenceMatch, ToleranceMatch, DateWindowMatch, applied in order to unmatched records only.
  2. Pass 1 as a set-based SQL FULL OUTER JOIN; later passes in SQL or Java over bounded batches (justify the split).

Done when: On the generated files every injected break is classified correctly.

Step 7: Recon runs and totals

  1. POST /api/v1/recon-runs (async) and GET /api/v1/recon-runs/{id} with totals per outcome and duration.
  2. Matched + unmatched value on each side must equal that side's file total.

Done when: 1 million records per side reconcile in minutes, and the totals check passes.

Step 8: Breaks workflow and report

  1. Break queue with filters; resolutions (write-off, manual match, raised with partner) audited and reversible with a reason.
  2. GET /api/v1/recon-runs/{id}/report.csv streams the exception report.

Done when: A manual match and its reversal both appear in the audit trail.

Step 9: Deploy and automate

  1. Make sure ./mvnw verify and the GitHub Actions workflow are green on main.
  2. Optional: mirror the repository to gitlab.com so .gitlab-ci.yml runs too. Other platforms (Azure DevOps, AWS CodeBuild, Jenkins, Argo CD) are covered in the CI/CD guide.
  3. Deploy using the deployment guide: a single VPS (2 vCPU / 4 GB) is cheapest; AWS, Azure and GCP steps are there too.
  4. Put the public health URL (/actuator/health) at the top of your README.

Done when: the health URL returns UP from the internet, and no secret is in Git (git log -p | grep -i password finds nothing real).

Step 10: Update the architecture pack

  1. Copy the architecture/ folder from this capstone into your repository.
  2. Edit the Mermaid (.mmd) or draw.io (.drawio) files so all five diagrams match what you actually built; re-export SVG/PNG (draw.io: File → Export; Mermaid: npx @mermaid-js/mermaid-cli -i x.mmd -o x.svg).
  3. Write at least three ADRs of your own (copy the format in architecture/adr/): one for persistence, one for concurrency or performance, one you chose yourself.

Done when: someone can understand your system from the diagrams and ADRs without reading code.

Your README must cover, in this order: the business problem; the architecture diagram; how to run it; API examples with curl; data sources and licences; design decisions and trade-offs; performance numbers (query plans, timings); what you'd do next. Then record a 3-minute demo video.

Done when: a hiring manager can read the README in three minutes and know what you built and why.
