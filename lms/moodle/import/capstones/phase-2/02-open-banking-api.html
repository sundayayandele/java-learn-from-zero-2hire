Architecture and system design (read this first)

Before you write code, study how this system is designed. These five views are the target architecture for a production-grade build; reproduce and adapt them in your own repository, and keep them current as you build. Full explanations, Mermaid, draw.io, SVG and PNG sources and the architecture decision records are in architecture/.

1. Solution architecture

Solution architecture: the bank exposes the API; Keycloak authenticates both the TPPs (client credentials) and the customers (authorisation code + PKCE). TPPs never see customer credentials; customers review and revoke consents in the bank's own channels.

Sources: Mermaid · draw.io · SVG · PNG

2. Logical architecture

Logical architecture: the consent is the centre. TPPs create it, customers authorise it for their own accounts, and every data request passes the consent guard (right TPP, authorised, not expired, permission granted, account included) before any account data is read. Every decision, allowed or denied, is written to the access log.

Sources: Mermaid · draw.io · SVG · PNG

3. Technical architecture

Technical architecture shows how the code is organised inside the Spring Boot 4 service: thin controllers that validate and translate errors, services that hold the business rules and transaction boundaries, and a persistence layer (JPA where entity behaviour and locking help, JdbcClient/SQL for reporting and bulk work). Cross-cutting concerns (configuration, health, metrics, scheduling, outbound HTTP) are framework features configured once. Package by feature in code; the layers here are logical.

Sources: Mermaid · draw.io · SVG · PNG

4. Infrastructure architecture

Infrastructure architecture shows where things run on the cheapest production-like target, a single VPS (for example SSDNodes). Only Caddy is reachable from the internet; it terminates TLS and forwards to open-banking-api on Docker's internal network, so the database is never exposed (Docker port publishing bypasses ufw, so nothing else publishes ports). Images are built once by GitHub Actions, stored in GHCR by commit SHA, and pulled onto the server; backups leave the machine daily. Keycloak is published on its own subdomain through Caddy so users and client apps can obtain tokens; the API only fetches its public signing keys (JWKS) and validates tokens locally. Sizing and every command are in the deployment guide.

Sources: Mermaid · draw.io · SVG · PNG

5. Cloud architecture

Cloud architecture maps the service onto managed cloud building blocks, drawn for AWS (ECS Express Mode, the AWS-recommended path for new accounts since App Runner closed to new customers in 2026). The database sits in private subnets; credentials come from the secret store, never from the image; images are immutable and tagged by commit SHA. The same design on the other clouds:

Sources: Mermaid · draw.io · SVG · PNG

Key design decisions

  1. One secured Spring Boot service (modular monolith) with an external identity provider
  2. Contract first: the API description is written and reviewed before the code
  3. Consent as a first-class resource checked on every data request
  4. Deny with 403 and record every decision in an append-only access log

Weeks 18–25. Modules used: 5, 6, 7, 8.

Business context

Open banking lets a customer give a licensed third party (a budgeting app, a lender, an accounting tool) read access to their bank data through APIs, instead of handing over their internet-banking password. The Central Bank of Nigeria's open banking framework and operational guidelines, the UK's Open Banking Standard and the EU's PSD2 all rest on the same ideas: explicit, time-limited consent for specific data, strong customer authentication at the bank, OAuth 2.0 tokens for the third party, and an audit trail of every access.

You will build the Account Information API for ITL Bank: third-party providers (TPPs) create a consent, the customer approves it for chosen accounts, and the TPP can then read only what was approved, until it expires or the customer revokes it.

What you'll build

A Spring Boot 4 resource server on PostgreSQL, secured by Keycloak, modelled on the UK Open Banking Read/Write API account-information flow (simplified; no certificate-bound tokens or request signing).

Actors and tokens

Actor How they authenticate Authorities
TPP (third-party app) Client credentials grant; client id in the token's azp claim SCOPE_accounts
Customer Authorisation code + PKCE at the bank (Keycloak user) ROLE_CUSTOMER
Operations Keycloak user ROLE_OPS

Consent lifecycle

AwaitingAuthorisation ──(customer approves accounts)──▶ Authorised ──(customer revokes)──▶ Revoked
          │                                                  │
          └──(customer rejects)──▶ Rejected                  └──(expirationDateTime passes)──▶ Expired

Permissions (a consent holds one or more): ReadAccountsBasic, ReadAccountsDetail, ReadBalances, ReadTransactionsBasic, ReadTransactionsDetail. Detail permissions add the account number and the transaction's counterparty and narration.

Business rules

  1. A data request succeeds only if all hold: the consent exists, was created by the calling TPP (azp), is Authorised, has not expired, includes the permission the endpoint needs, and includes the account. Otherwise 403 with a specific problem type (the response must not reveal whether an account exists outside the consent).
  2. A customer can authorise a consent only for accounts they own; one account they don't own fails the whole request (403).
  3. expirationDateTime must be in the future and at most 90 days away; the transaction window must not start more than 12 months back.
  4. Transactions are returned within the intersection of the consent's window and the request's window; Basic permissions omit counterpartyName, counterpartyAccount and narration.
  5. Every data access (allowed or denied) writes an access_log row: time, TPP, consent, customer, endpoint, account, outcome. Logs are append-only.
  6. The TPP may make at most 4 unattended calls per account per day for each endpoint (configurable), modelled on the UK standard's limit for unattended access; above it, 429 with Retry-After. Track it in the database.
  7. Money is BigDecimal with the account currency's scale; times are ISO 8601 with offsets.

Errors

Problem Details: validation-failed (400), unauthorized (401), consent-not-found (404, also for another TPP's consent), consent-not-authorised (403), consent-expired (403), permission-not-granted (403), account-not-in-consent (403), not-account-owner (403), invalid-consent-transition (409), rate-limit-exceeded (429).

Data

  • Synthetic, generated by you (CC0). A Flyway seed or generator creates customers, 2–4 accounts each (current, savings, domiciliary USD) and 12 months of transactions (salary, transfers, card payments, bills) with Nigerian-style narrations. Generate at least 200 customers and 100,000 transactions so pagination and indexes matter.
  • Specifications (read, don't copy): UK Open Banking Read/Write API specifications for the consent model and permission names; the Central Bank of Nigeria's open banking framework and operational guidelines (search "CBN open banking operational guidelines" on cbn.gov.ng) for the Nigerian context. Credit the specification in your README; your code and data are your own.
  • Keycloak users and the TPP client are created by your local setup script; never commit real secrets.

Infrastructure and deployment

  • Local: PostgreSQL, Keycloak and the app via docker compose up --build.
  • Sizing: same as Capstone 1 (a 2 vCPU / 4 GB VPS runs all three).
  • Identity: in the cloud use Keycloak in a container with a managed PostgreSQL, or a managed provider (Amazon Cognito, Microsoft Entra ID, Google Identity Platform); the API only needs the issuer URI.
  • Deploy: Phase 2 deployment guide.

Stretch goals

  • A minimal TPP web app that runs the authorisation code + PKCE flow and displays the data.
  • Payment initiation consents (single domestic payment) reusing Phase 1's ledger.
  • Sender-constrained tokens with DPoP (Spring Security supports DPoP-bound access tokens) and a write-up of why FAPI requires sender constraining.
  • A written threat model (STRIDE) for the consent flow in architecture/.

Interview talking points

  • Why scopes in the token are not enough, and how the consent adds per-customer, per-account authorisation.
  • Client credentials vs authorisation code + PKCE: who is authenticated in each, and why the TPP never sees the customer's password.
  • How you prevented broken object level authorisation, and how your tests prove it.
  • What the access log is for, and who reads it.

Step-by-step build guide: Secure open banking accounts API

Work through the steps in order. Each step ends with a Done when check: don't move on until it passes. Commit after every step with a clear message, so your history tells the story of the build.

Before you start

  • Finish the topics listed under "Skills you'll demonstrate" in the brief, or study them alongside.
  • Read the architecture section and the ADRs. You will update both at the end.
  • You need Java 21, Docker Desktop (16 GB RAM recommended: the app, PostgreSQL and Keycloak run together), Git, IntelliJ IDEA and jq.
  • Work in pull requests from the start (topic 8.1): one branch and one PR per step below, merged after CI is green and, ideally, a peer has reviewed it.

Step 1: Create your repository from the secure starter

git clone https://github.com/sundayayandele/java-zero-hire.git
mkdir open-banking-api && cp -R java-zero-hire/phases/02-professional-backend/capstones/02-open-banking-api/starter/. open-banking-api/
cd open-banking-api
git init -b main && git add . && git commit -m "Start from the Secure open banking accounts API starter"

Create an empty public repository called open-banking-api on GitHub, then:

git remote add origin https://github.com/<your-username>/open-banking-api.git
git push -u origin main

In GitHub, protect main (Settings → Branches): require a pull request and the build and scan checks to pass.

Done when: the Actions tab shows the build and scan jobs green on your first push.

Step 2: Run it locally with Keycloak

cp .env.example .env          # set DB_PASSWORD and KEYCLOAK_ADMIN_PASSWORD to local values
docker compose up --build
export DEV_USER_PASSWORD='<pick a local password>' KEYCLOAK_ADMIN_PASSWORD='<same as .env>'
./scripts/dev-users.sh        # creates alice, bob (CUSTOMER), olu (OPS), ada (ADMIN)
TOKEN=$(curl -s -d client_id=itl-cli -d grant_type=password -d username=alice -d password="$DEV_USER_PASSWORD"   -d scope='openid api.read api.write' http://localhost:8081/realms/itl/protocol/openid-connect/token | jq -r .access_token)
curl -i http://localhost:8080/actuator/health
curl -i -H "Authorization: Bearer $TOKEN" http://localhost:8080/api/v1/anything   # 404 with a token, 401 without
./mvnw verify                 # tests + coverage gate; needs Docker running (Testcontainers)

Done when: health returns {"status":"UP"}, a request without a token gets 401, and ./mvnw verify is green. The base package is ng.itlearning.openbanking.

Step 3: Plan your data

This capstone generates its own data (see the brief's Data section). Write the generator as part of the build steps below and release generated data under CC0.

Step 4: Contract and consent model

  1. Write the OpenAPI contract for the TPP, customer and ops endpoints, with the x-consent-id header and every Problem Details type.
  2. Model Consent (permissions as an EnumSet<Permission>, expiry, transaction window, status) and its lifecycle with TDD: legal and illegal transitions, expiry using an injected Clock.

Done when: Contract reviewed in a PR; consent unit tests cover every transition in the brief.

Step 5: Synthetic bank data

  1. Migrations for customer, account, transaction, consent, consent_account, access_log, access_counter.
  2. Write a generator (profile seed) creating 200 customers, 2–4 accounts each and 12 months of transactions with realistic Nigerian narrations; customers' external_subject matches Keycloak user ids.
  3. Index transaction(account_id, booked_at, id) for cursor pagination.

Done when: The seed runs in under a minute and EXPLAIN ANALYZE of a transaction page uses the index.

Step 6: Keycloak: TPP client and customers

  1. Add a confidential client tpp-budgetapp (client credentials only) with an accounts client scope and the itl-api audience mapper to your realm file; its secret comes from the environment, never Git.
  2. Create customer users with scripts/dev-users.sh and record their subject ids for the seed.
  3. Get a TPP token with grant_type=client_credentials and check the azp and scope claims at jwt.io-style decoding (locally, never paste real tokens into websites).

Done when: You can obtain a TPP token and a customer token and the API accepts both.

Step 7: Consent endpoints

  1. TPP endpoints: create (201, AwaitingAuthorisation), get, delete (only the creating TPP, identified by the token's azp).
  2. Customer endpoints: list, authorise for chosen accounts (all must belong to the customer), reject, revoke.
  3. For every endpoint write API tests for: no token (401), wrong scope or role (403), another owner's resource (404 or 403 as the brief says), and the happy path. Use jwt() from spring-security-test with the exact authorities each caller has.

Done when: A customer can't authorise with someone else's account, and a TPP can't see another TPP's consent.

Step 8: Consent guard and data endpoints

  1. Write one ConsentGuard.check(consentId, tppId, permission, accountId) that throws a specific exception per failure; unit-test it exhaustively.
  2. Accounts, balances and transactions endpoints call the guard first; transactions are limited to the intersection of the consent and request windows, and Basic permissions omit counterparty fields.
  3. Write the access_log row for allowed and denied requests (denials in a REQUIRES_NEW transaction so they survive the rollback).

Done when: Each guard failure returns its 403 problem type and leaves a DENIED log row.

Step 9: Unattended access limit

  1. Count calls per (consent, account, endpoint, day) in access_counter with an atomic upsert (INSERT ... ON CONFLICT DO UPDATE ... RETURNING).
  2. Above the configured limit return 429 with Retry-After seconds until midnight Lagos time.

Done when: The fifth call in a day returns 429 and the counter is correct under 20 concurrent calls.

Step 10: Ops access log and hardening

  1. GET /ops/v1/access-log for ROLE_OPS with filters and cursor pagination.
  2. Make sure no token, consent body or account number appears in logs; add the consent id as a log correlation field.
  3. Write a one-page threat model (STRIDE) for the consent flow in architecture/.

Done when: All acceptance criteria pass and the coverage gate is green.

Step 11: Quality gates, pipeline and deployment

  1. Make sure every CI job is green on main: tests, the JaCoCo gate (raise coverage.minimum in pom.xml as your tests grow; 80% is a good target), the Trivy dependency and secret scan, and the image scan.
  2. Optional: mirror to gitlab.com so .gitlab-ci.yml runs too. Azure DevOps, AWS CodeBuild, Jenkins and Argo CD are covered in the CI/CD guide.
  3. Deploy the app with an identity provider using the deployment guide: Keycloak next to the app on a VPS, or Keycloak in a container / a managed provider in the cloud. Set OAUTH_ISSUER_URI to the deployed issuer.
  4. Put the public health URL (/actuator/health) and the Swagger UI URL at the top of your README.

Done when: the health URL returns UP from the internet, protected endpoints return 401 without a token, and no secret is in Git (the Trivy secret scan is green).

Step 12: Update the architecture pack and write a threat model

  1. Copy the architecture/ folder from this capstone into your repository.
  2. Edit the Mermaid (.mmd) or draw.io (.drawio) files so all five diagrams match what you built; re-export SVG/PNG (draw.io: File → Export; Mermaid: npx @mermaid-js/mermaid-cli -i x.mmd -o x.svg).
  3. Write at least three ADRs of your own (copy the format in architecture/adr/): one on security, one on an integration or resilience choice, one you chose yourself.
  4. Write architecture/threat-model.md: the five most important threats (STRIDE is a good checklist), and how your design and tests mitigate each (topic 6.4).

Done when: someone can understand your system, its risks and its defences from the diagrams, ADRs and threat model without reading code.

Step 13: Write the README and record a demo

Your README must cover, in this order: the business problem; the architecture diagram; how to run it including how to get a token; API examples with curl; data sources, sandboxes and licences; security model (roles, scopes, ownership); design decisions and trade-offs; test strategy and coverage; what you'd do next. Then record a 3-minute demo video that includes one failure scenario (a provider outage, a forbidden request, or a retry).

Done when: a hiring manager can read the README in three minutes and know what you built, how it is secured and why.
