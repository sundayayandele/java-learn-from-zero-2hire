Architecture and system design (read this first)

Before you write code, study how this system is designed. These five views are the target architecture for a production-grade build; reproduce and adapt them in your own repository, and keep them current as you build. Full explanations, Mermaid, draw.io, SVG and PNG sources and the architecture decision records are in architecture/.

1. Solution architecture

Solution architecture: officers submit, the engine decides, underwriters handle referrals and overrides, and risk teams backtest rule changes on public data before activating them.

Sources: Mermaid · draw.io · SVG · PNG

2. Logical architecture

Logical architecture: the decision engine reads only financial inputs and the active rule set version, and stores inputs, version and reasons with each decision. Overrides and rule changes follow segregation-of-duties rules. Protected attributes exist only in the HMDA backtest area.

Sources: Mermaid · draw.io · SVG · PNG

3. Technical architecture

Technical architecture shows how the code is organised inside the Spring Boot 4 service: thin controllers that validate and translate errors, services that hold the business rules and transaction boundaries, and a persistence layer (JPA where entity behaviour and locking help, JdbcClient/SQL for reporting and bulk work). Cross-cutting concerns (configuration, health, metrics, scheduling, outbound HTTP) are framework features configured once. Package by feature in code; the layers here are logical.

Sources: Mermaid · draw.io · SVG · PNG

4. Infrastructure architecture

Infrastructure architecture shows where things run on the cheapest production-like target, a single VPS (for example SSDNodes). Only Caddy is reachable from the internet; it terminates TLS and forwards to mortgage-decisions on Docker's internal network, so the database is never exposed (Docker port publishing bypasses ufw, so nothing else publishes ports). Images are built once by GitHub Actions, stored in GHCR by commit SHA, and pulled onto the server; backups leave the machine daily. Keycloak is published on its own subdomain through Caddy so users and client apps can obtain tokens; the API only fetches its public signing keys (JWKS) and validates tokens locally. Sizing and every command are in the deployment guide.

Sources: Mermaid · draw.io · SVG · PNG

5. Cloud architecture

Cloud architecture maps the service onto managed cloud building blocks, drawn for AWS (ECS Express Mode, the AWS-recommended path for new accounts since App Runner closed to new customers in 2026). The database sits in private subnets; credentials come from the secret store, never from the image; images are immutable and tagged by commit SHA. The same design on the other clouds:

Key design decisions

  1. One secured Spring Boot service (modular monolith) with an external identity provider
  2. Versioned rule sets stored with every decision
  3. Protected attributes are unreachable from the decision path

Weeks 17–24. Modules used: 5, 6, 7, 8.

Business context

Lenders decide mortgage applications with rules (affordability, loan-to-value, debt-to-income), and regulators expect those decisions to be explainable, consistent and fair. In the US, every mortgage lender reports each application and its outcome under the Home Mortgage Disclosure Act (HMDA), and the anonymised data is public: millions of real applications with loan amounts, incomes, property values, debt-to-income bands and outcomes. It is a rich, free dataset for building and testing a decision service.

You will build an application decision API: loan officers submit applications, a versioned rule set produces an explained decision, underwriters override with reasons, and a portfolio view compares your rules with real HMDA outcomes.

What you'll build

A Spring Boot 4 service on PostgreSQL with role-based workflows.

API

Method and path Who Purpose
POST /api/v1/applications Loan officer (ROLE_OFFICER or CUSTOMER in your realm mapping) Submit: loan amount, property value, income, monthly debts, loan type, purpose, term
POST /api/v1/applications/{id}/decision System / officer Run the current rule set; returns APPROVE, REFER or DECLINE with every rule's result and reason codes
POST /api/v1/applications/{id}/override ROLE_UNDERWRITER (not the submitting officer) Override with a reason; audited
GET /api/v1/applications/{id} Submitting officer, underwriters, OPS Application, decisions, overrides
GET /api/v1/rulesets and POST /api/v1/rulesets ADMIN Versioned rule thresholds; activating a version needs a second admin
GET /api/v1/analytics/backtest?ruleset=&year=&state= OPS Run a rule set over imported HMDA applications and compare with actual outcomes

Business rules

  1. Loan-to-value (LTV) = loan amount ÷ property value; debt-to-income (DTI) = monthly debts (including the new payment) ÷ monthly income. Calculate the monthly payment with the standard amortisation formula in BigDecimal.
  2. Default rule set v1 (configurable): DTI ≤ 43% and LTV ≤ 80% → APPROVE; DTI ≤ 50% and LTV ≤ 95% → REFER; otherwise DECLINE. Each decision stores the rule set version and the inputs.
  3. Explainability: every decline lists reason codes (DTI_TOO_HIGH, LTV_TOO_HIGH, INCOME_NOT_VERIFIED) in plain language.
  4. Fairness guard: the decision service never reads protected attributes (race, ethnicity, sex, age). They exist in HMDA data only for the backtest's disparity report, which compares approval rates across groups and flags gaps above a threshold for human review.
  5. Segregation of duties: an underwriter can't override their own submission; rule changes need two admins.
  6. Decisions and overrides are append-only and auditable.

Data

  • HMDA public loan-level data, published by the US Consumer Financial Protection Bureau and the FFIEC. Use the Data Browser API, for example curl -L "https://ffiec.cfpb.gov/v2/data-browser-api/view/csv?states=DC&years=2024&actions_taken=1,3" (originated and denied applications in one state; start small).
  • Terms: US federal government work, in the public domain in the US. Attribution recommended: "Source: FFIEC/CFPB Home Mortgage Disclosure Act data." HMDA values are reported in bands and some fields are modified to protect privacy; never try to re-identify applicants, and don't present your backtests as official statistics.
  • Applications submitted through your API are synthetic (CC0).

Step-by-step build guide: Mortgage application decision API

Work through the steps in order. Each step ends with a Done when check: don't move on until it passes. Commit after every step with a clear message, so your history tells the story of the build.

Before you start

  • Finish the topics listed under "Skills you'll demonstrate" in the brief, or study them alongside.
  • Read the architecture section and the ADRs. You will update both at the end.
  • You need Java 21, Docker Desktop (16 GB RAM recommended: the app, PostgreSQL and Keycloak run together), Git, IntelliJ IDEA and jq.
  • Work in pull requests from the start (topic 8.1): one branch and one PR per step below, merged after CI is green and, ideally, a peer has reviewed it.

Step 1: Create your repository from the secure starter

git clone https://github.com/sundayayandele/java-zero-hire.git
mkdir mortgage-decision-api && cp -R java-zero-hire/phases/02-professional-backend/capstones/09-mortgage-decision-api/starter/. mortgage-decision-api/
cd mortgage-decision-api
git init -b main && git add . && git commit -m "Start from the Mortgage application decision API starter"

Create an empty public repository called mortgage-decision-api on GitHub, then:

git remote add origin https://github.com/<your-username>/mortgage-decision-api.git
git push -u origin main

In GitHub, protect main (Settings → Branches): require a pull request and the build and scan checks to pass.

Done when: the Actions tab shows the build and scan jobs green on your first push.

Step 2: Run it locally with Keycloak

cp .env.example .env          # set DB_PASSWORD and KEYCLOAK_ADMIN_PASSWORD to local values
docker compose up --build
export DEV_USER_PASSWORD='<pick a local password>' KEYCLOAK_ADMIN_PASSWORD='<same as .env>'
./scripts/dev-users.sh        # creates alice, bob (CUSTOMER), olu (OPS), ada (ADMIN)
TOKEN=$(curl -s -d client_id=itl-cli -d grant_type=password -d username=alice -d password="$DEV_USER_PASSWORD"   -d scope='openid api.read api.write' http://localhost:8081/realms/itl/protocol/openid-connect/token | jq -r .access_token)
curl -i http://localhost:8080/actuator/health
curl -i -H "Authorization: Bearer $TOKEN" http://localhost:8080/api/v1/anything   # 404 with a token, 401 without
./mvnw verify                 # tests + coverage gate; needs Docker running (Testcontainers)

Done when: health returns {"status":"UP"}, a request without a token gets 401, and ./mvnw verify is green. The base package is ng.itlearning.mortgage.

Step 3: Get the data

Never commit raw datasets; download them with a script. Add data/ to .gitignore first.

mkdir -p data
curl -L -o data/hmda-dc-2024.csv "https://ffiec.cfpb.gov/v2/data-browser-api/view/csv?states=DC&years=2024&actions_taken=1,3"

Copy the licence and attribution lines from the brief's Data section into your README now.

Done when: the files are in data/ and git status doesn't show them.

Step 4: Decision engine with TDD

  1. Monthly payment via the amortisation formula in BigDecimal (MathContext.DECIMAL64, round to kobo/cents at the end).
  2. LTV and DTI with parameterised boundary tests at exactly 43%, 43.01%, 80%, 95%.
  3. Reason codes and plain-language explanations.

Done when: Every boundary test passes.

Step 5: Versioned rule sets

  1. Store thresholds as versioned rows; activation needs a second ADMIN.
  2. Each decision stores inputs, version and reasons.

Done when: Replaying an old decision with its version gives the same result.

Step 6: Roles and segregation of duties

  1. Add OFFICER and UNDERWRITER realm roles; underwriters can't override their own submissions.
  2. For every endpoint write API tests for: no token (401), wrong scope or role (403), another owner's resource (404 or 403 as the brief says), and the happy path. Use jwt() from spring-security-test with the exact authorities each caller has.

Done when: Segregation-of-duties tests pass.

Step 7: HMDA import and backtest

  1. Stream-parse the CSV (it's large); map loan_amount, property_value, income, debt_to_income_ratio bands and action_taken.
  2. Backtest: run a rule set over imported rows and report agreement with actual outcomes, plus approval rates by group with a disparity flag.
  3. An ArchUnit-style test (or a simple package-dependency test) proves the decision package doesn't depend on the HMDA package.

Done when: All acceptance criteria pass and the coverage gate is green.

Step 8: Quality gates, pipeline and deployment

  1. Make sure every CI job is green on main: tests, the JaCoCo gate (raise coverage.minimum in pom.xml as your tests grow; 80% is a good target), the Trivy dependency and secret scan, and the image scan.
  2. Optional: mirror to gitlab.com so .gitlab-ci.yml runs too. Azure DevOps, AWS CodeBuild, Jenkins and Argo CD are covered in the CI/CD guide.
  3. Deploy the app with an identity provider using the deployment guide: Keycloak next to the app on a VPS, or Keycloak in a container / a managed provider in the cloud. Set OAUTH_ISSUER_URI to the deployed issuer.
  4. Put the public health URL (/actuator/health) and the Swagger UI URL at the top of your README.

Done when: the health URL returns UP from the internet, protected endpoints return 401 without a token, and no secret is in Git (the Trivy secret scan is green).

Step 9: Update the architecture pack and write a threat model

  1. Copy the architecture/ folder from this capstone into your repository.
  2. Edit the Mermaid (.mmd) or draw.io (.drawio) files so all five diagrams match what you built; re-export SVG/PNG (draw.io: File → Export; Mermaid: npx @mermaid-js/mermaid-cli -i x.mmd -o x.svg).
  3. Write at least three ADRs of your own (copy the format in architecture/adr/): one on security, one on an integration or resilience choice, one you chose yourself.
  4. Write architecture/threat-model.md: the five most important threats (STRIDE is a good checklist), and how your design and tests mitigate each (topic 6.4).

Done when: someone can understand your system, its risks and its defences from the diagrams, ADRs and threat model without reading code.

Step 10: Write the README and record a demo

Your README must cover, in this order: the business problem; the architecture diagram; how to run it including how to get a token; API examples with curl; data sources, sandboxes and licences; security model (roles, scopes, ownership); design decisions and trade-offs; test strategy and coverage; what you'd do next. Then record a 3-minute demo video that includes one failure scenario (a provider outage, a forbidden request, or a retry).

Done when: a hiring manager can read the README in three minutes and know what you built, how it is secured and why.
