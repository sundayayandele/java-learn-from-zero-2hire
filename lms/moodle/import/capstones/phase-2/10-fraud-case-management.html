Architecture and system design (read this first)

Before you write code, study how this system is designed. These five views are the target architecture for a production-grade build; reproduce and adapt them in your own repository, and keep them current as you build. Full explanations, Mermaid, draw.io, SVG and PNG sources and the architecture decision records are in architecture/.

1. Solution architecture

Solution architecture: fraud rules feed alerts; the fraud team works cases; approved actions call card and account systems; auditors read the trail.

Sources: Mermaid · draw.io · SVG · PNG

2. Logical architecture

Logical architecture: alerts are grouped into cases; analysts work cases they are allowed to see (CasePolicy), propose actions that a different supervisor must approve, and every read of sensitive data and every change is appended to a hash-chained audit log.

Sources: Mermaid · draw.io · SVG · PNG

3. Technical architecture

Technical architecture shows how the code is organised inside the Spring Boot 4 service: thin controllers that validate and translate errors, services that hold the business rules and transaction boundaries, and a persistence layer (JPA where entity behaviour and locking help, JdbcClient/SQL for reporting and bulk work). Cross-cutting concerns (configuration, health, metrics, scheduling, outbound HTTP) are framework features configured once. Package by feature in code; the layers here are logical.

Sources: Mermaid · draw.io · SVG · PNG

4. Infrastructure architecture

Infrastructure architecture shows where things run on the cheapest production-like target, a single VPS (for example SSDNodes). Only Caddy is reachable from the internet; it terminates TLS and forwards to fraud-cases on Docker's internal network, so the database is never exposed (Docker port publishing bypasses ufw, so nothing else publishes ports). Images are built once by GitHub Actions, stored in GHCR by commit SHA, and pulled onto the server; backups leave the machine daily. Keycloak is published on its own subdomain through Caddy so users and client apps can obtain tokens; the API only fetches its public signing keys (JWKS) and validates tokens locally. Sizing and every command are in the deployment guide.

Sources: Mermaid · draw.io · SVG · PNG

5. Cloud architecture

Cloud architecture maps the service onto managed cloud building blocks, drawn for AWS (ECS Express Mode, the AWS-recommended path for new accounts since App Runner closed to new customers in 2026). The database sits in private subnets; credentials come from the secret store, never from the image; images are immutable and tagged by commit SHA. The same design on the other clouds:

Key design decisions

  1. One secured Spring Boot service (modular monolith) with an external identity provider
  2. Object-level authorisation in one policy, enforced with @PreAuthorize
  3. Maker-checker for actions that move money or affect customers
  4. Hash-chained audit log

Weeks 18–25. Modules used: 5, 6, 7, 8.

Business context

Fraud rules (Phase 1, Capstone 7) produce alerts; people turn alerts into cases: investigate, contact the customer, block cards, recover funds, file reports, and close with an outcome. Case management is where security matters most inside a bank: analysts see sensitive data, decisions move money, and every action must be attributable. Regulators and auditors check who saw what, who decided what, and whether one person could act alone.

You will build the case management backend for ITL Bank's fraud team: alert intake, assignment, investigation notes, maker-checker actions, SLAs and a tamper-evident audit trail.

What you'll build

A Spring Boot 4 service on PostgreSQL with fine-grained authorisation.

Roles

Role Can
ANALYST View and work cases assigned to them or their team; propose actions
SUPERVISOR Assign cases, approve or reject proposed actions, close cases
OPS Read-only dashboards and SLA reports
AUDITOR Read the audit trail; nothing else

(Add the extra roles to your Keycloak realm.)

API

Method and path Purpose
POST /api/v1/alerts Ingest alerts (service client, SCOPE_alerts.write); related alerts for the same customer within 48 h join one case
GET /api/v1/cases?status=&assignee=&priority=&cursor= Cases visible to the caller
POST /api/v1/cases/{id}/assign Supervisor assigns
POST /api/v1/cases/{id}/notes Analyst adds a note (notes are immutable; corrections are new notes)
POST /api/v1/cases/{id}/actions Analyst proposes BLOCK_CARD, FREEZE_ACCOUNT, REFUND_CUSTOMER, REPORT_TO_REGULATOR
POST /api/v1/actions/{id}/approve or /reject Supervisor, never the proposer
POST /api/v1/cases/{id}/close Supervisor, with outcome (CONFIRMED_FRAUD, FALSE_POSITIVE, CUSTOMER_ERROR)
GET /api/v1/audit?caseId= Auditor
GET /api/v1/reports/sla OPS: cases breaching SLA by priority

Business rules

  1. Priority from the alert score and amount; SLAs: P1 1 hour to first action, P2 4 hours, P3 24 hours (configurable). A scheduled job flags breaches and escalates.
  2. Object-level authorisation: analysts see only their or their team's cases; any other case returns 404. Implement with a policy class and @PreAuthorize calling it, and test every endpoint for it.
  3. Maker-checker: money- or customer-affecting actions need approval by a different person with SUPERVISOR; approvals are recorded with both identities.
  4. Tamper-evident audit: every read of customer data and every change writes an audit record containing the SHA-256 hash of the previous record (a hash chain). An endpoint verifies the chain.
  5. Customer PII (phone, account number) is masked in list views and shown in full only on the case detail, which is audited.
  6. Closed cases are read-only.

Step-by-step build guide: Fraud case management service

Work through the steps in order. Each step ends with a Done when check: don't move on until it passes. Commit after every step with a clear message, so your history tells the story of the build.

Before you start

  • Finish the topics listed under "Skills you'll demonstrate" in the brief, or study them alongside.
  • Read the architecture section and the ADRs. You will update both at the end.
  • You need Java 21, Docker Desktop (16 GB RAM recommended: the app, PostgreSQL and Keycloak run together), Git, IntelliJ IDEA and jq.
  • Work in pull requests from the start (topic 8.1): one branch and one PR per step below, merged after CI is green and, ideally, a peer has reviewed it.

Step 1: Create your repository from the secure starter

git clone https://github.com/sundayayandele/java-zero-hire.git
mkdir fraud-case-management && cp -R java-zero-hire/phases/02-professional-backend/capstones/10-fraud-case-management/starter/. fraud-case-management/
cd fraud-case-management
git init -b main && git add . && git commit -m "Start from the Fraud case management service starter"

Create an empty public repository called fraud-case-management on GitHub, then:

git remote add origin https://github.com/<your-username>/fraud-case-management.git
git push -u origin main

In GitHub, protect main (Settings → Branches): require a pull request and the build and scan checks to pass.

Done when: the Actions tab shows the build and scan jobs green on your first push.

Step 2: Run it locally with Keycloak

cp .env.example .env          # set DB_PASSWORD and KEYCLOAK_ADMIN_PASSWORD to local values
docker compose up --build
export DEV_USER_PASSWORD='<pick a local password>' KEYCLOAK_ADMIN_PASSWORD='<same as .env>'
./scripts/dev-users.sh        # creates alice, bob (CUSTOMER), olu (OPS), ada (ADMIN)
TOKEN=$(curl -s -d client_id=itl-cli -d grant_type=password -d username=alice -d password="$DEV_USER_PASSWORD"   -d scope='openid api.read api.write' http://localhost:8081/realms/itl/protocol/openid-connect/token | jq -r .access_token)
curl -i http://localhost:8080/actuator/health
curl -i -H "Authorization: Bearer $TOKEN" http://localhost:8080/api/v1/anything   # 404 with a token, 401 without
./mvnw verify                 # tests + coverage gate; needs Docker running (Testcontainers)

Done when: health returns {"status":"UP"}, a request without a token gets 401, and ./mvnw verify is green. The base package is ng.itlearning.cases.

Step 3: Get the data

Never commit raw datasets; download them with a script. Add data/ to .gitignore first.

mkdir -p data
# PaySim is on Kaggle (CC BY-SA 4.0): download with the Kaggle CLI after accepting the dataset terms
kaggle datasets download -d ealaxi/paysim1 -p data --unzip

Copy the licence and attribution lines from the brief's Data section into your README now.

Done when: the files are in data/ and git status doesn't show them.

Step 4: Domain with TDD

  1. Case and action state machines, SLA calculation from priority, alert grouping (same customer within 48 h).
  2. Hash chain: hash = SHA-256(prev_hash || canonical record); verification walks the chain.

Done when: Domain and chain tests pass, including detecting a modified record.

Step 5: Roles and the case policy

  1. Add ANALYST, SUPERVISOR, AUDITOR roles and a team attribute mapped into the token.
  2. CasePolicy.canView(auth, caseId) used from @PreAuthorize("@casePolicy.canView(authentication, #id)"); hidden cases return 404.

Done when: Analysts see only their team's cases.

Step 6: Alert intake from PaySim

  1. A loader turns PaySim fraud rows (or your Phase 1 rules' output) into alerts posted with a client-credentials token.

Done when: Alerts group into cases as the brief describes.

Step 7: Maker-checker, masking and audit

  1. Propose and approve actions with different people; mask PII in lists; audit full-PII views and every change.
  2. An authorisation matrix test: every role × every endpoint with the expected status.
  3. For every endpoint write API tests for: no token (401), wrong scope or role (403), another owner's resource (404 or 403 as the brief says), and the happy path. Use jwt() from spring-security-test with the exact authorities each caller has.

Done when: The matrix test passes.

Step 8: SLAs and reports

  1. Scheduled breach detection with a Clock; GET /api/v1/reports/sla for OPS.

Done when: All acceptance criteria pass and the coverage gate is green.

Step 9: Quality gates, pipeline and deployment

  1. Make sure every CI job is green on main: tests, the JaCoCo gate (raise coverage.minimum in pom.xml as your tests grow; 80% is a good target), the Trivy dependency and secret scan, and the image scan.
  2. Optional: mirror to gitlab.com so .gitlab-ci.yml runs too. Azure DevOps, AWS CodeBuild, Jenkins and Argo CD are covered in the CI/CD guide.
  3. Deploy the app with an identity provider using the deployment guide: Keycloak next to the app on a VPS, or Keycloak in a container / a managed provider in the cloud. Set OAUTH_ISSUER_URI to the deployed issuer.
  4. Put the public health URL (/actuator/health) and the Swagger UI URL at the top of your README.

Done when: the health URL returns UP from the internet, protected endpoints return 401 without a token, and no secret is in Git (the Trivy secret scan is green).

Step 10: Update the architecture pack and write a threat model

  1. Copy the architecture/ folder from this capstone into your repository.
  2. Edit the Mermaid (.mmd) or draw.io (.drawio) files so all five diagrams match what you built; re-export SVG/PNG (draw.io: File → Export; Mermaid: npx @mermaid-js/mermaid-cli -i x.mmd -o x.svg).
  3. Write at least three ADRs of your own (copy the format in architecture/adr/): one on security, one on an integration or resilience choice, one you chose yourself.
  4. Write architecture/threat-model.md: the five most important threats (STRIDE is a good checklist), and how your design and tests mitigate each (topic 6.4).

Done when: someone can understand your system, its risks and its defences from the diagrams, ADRs and threat model without reading code.

Step 11: Write the README and record a demo

Your README must cover, in this order: the business problem; the architecture diagram; how to run it including how to get a token; API examples with curl; data sources, sandboxes and licences; security model (roles, scopes, ownership); design decisions and trade-offs; test strategy and coverage; what you'd do next. Then record a 3-minute demo video that includes one failure scenario (a provider outage, a forbidden request, or a retry).

Done when: a hiring manager can read the README in three minutes and know what you built, how it is secured and why.
