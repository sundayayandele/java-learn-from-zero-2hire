Architecture and system design (read this first)

Before you write code, study how this system is designed. These five views are the target architecture for a production-grade build; reproduce and adapt them in your own repository, and keep them current as you build. Full explanations, Mermaid, draw.io, SVG and PNG sources and the architecture decision records are in architecture/.

1. Solution architecture

Solution architecture: the developer platform of a payments company: businesses sign up, are verified against the company registry, and integrate with API keys.

Sources: Mermaid · draw.io · SVG · PNG

2. Logical architecture

Logical architecture: two front doors. Dashboard users authenticate with Keycloak JWTs to register merchants and manage keys; merchant servers authenticate with API keys (optionally HMAC-signed requests) and are rate limited per key. Keys are stored only as hashes.

Sources: Mermaid · draw.io · SVG · PNG

3. Technical architecture

Technical architecture shows how the code is organised inside the Spring Boot 4 service: thin controllers that validate and translate errors, services that hold the business rules and transaction boundaries, and a persistence layer (JPA where entity behaviour and locking help, JdbcClient/SQL for reporting and bulk work). Cross-cutting concerns (configuration, health, metrics, scheduling, outbound HTTP) are framework features configured once. Package by feature in code; the layers here are logical.

Sources: Mermaid · draw.io · SVG · PNG

4. Infrastructure architecture

Infrastructure architecture shows where things run on the cheapest production-like target, a single VPS (for example SSDNodes). Only Caddy is reachable from the internet; it terminates TLS and forwards to merchant-platform on Docker's internal network, so the database is never exposed (Docker port publishing bypasses ufw, so nothing else publishes ports). Images are built once by GitHub Actions, stored in GHCR by commit SHA, and pulled onto the server; backups leave the machine daily. Keycloak is published on its own subdomain through Caddy so users and client apps can obtain tokens; the API only fetches its public signing keys (JWKS) and validates tokens locally. Sizing and every command are in the deployment guide.

Sources: Mermaid · draw.io · SVG · PNG

5. Cloud architecture

Cloud architecture maps the service onto managed cloud building blocks, drawn for AWS (ECS Express Mode, the AWS-recommended path for new accounts since App Runner closed to new customers in 2026). The database sits in private subnets; credentials come from the secret store, never from the image; images are immutable and tagged by commit SHA. The same design on the other clouds:

Key design decisions

  1. One secured Spring Boot service (modular monolith) with an external identity provider
  2. Two security filter chains: JWT for people, API keys for servers
  3. Store API key hashes, show the secret once
  4. Token-bucket rate limits per key in a shared store

Weeks 17–24. Modules used: 5, 6, 7, 8.

Business context

Payment companies earn money when merchants integrate their API. That needs a developer platform: businesses sign up, are checked against the company registry (know your business), get test and live API keys, sign requests, stay within rate limits, and receive webhooks. Stripe, Paystack and Flutterwave all run such a platform. Getting API-key security wrong (storing keys in plain text, never rotating them, no scoping) is one of the most common causes of fintech breaches.

What you'll build

A Spring Boot 4 service on PostgreSQL with two security models side by side: Keycloak JWTs for the merchant dashboard users, and API keys with HMAC request signing for merchants' servers.

API

Method and path Who Purpose
POST /api/v1/merchants Signed-in user (ROLE_CUSTOMER) Register a business with its UK Companies House company number (or a manual registration number)
POST /api/v1/merchants/{id}/verify OPS Run the company lookup and record the result; activate or reject
POST /api/v1/merchants/{id}/keys Merchant owner Create a key pair: pk_test_…/sk_test_… or (only when active) pk_live_…/sk_live_…. The secret is shown once
GET /api/v1/merchants/{id}/keys Merchant owner Key ids, prefixes, scopes, created/last-used dates; never secrets
POST /api/v1/merchants/{id}/keys/{keyId}/roll Merchant owner Rotate with an overlap window (old key valid for 24 h)
DELETE /api/v1/merchants/{id}/keys/{keyId} Merchant owner Revoke immediately
GET /api/v1/echo and POST /api/v1/charges-preview Merchant server with an API key Sample protected endpoints to prove authentication, scopes and limits

Business rules

  1. Key storage: store only a hash of each secret (SHA-256 of a high-entropy random secret is acceptable because the secret is not guessable; explain why this differs from passwords) and the first 8 characters for display. Compare in constant time.
  2. Request signing: merchant servers send Authorization: Bearer sk_… or (stretch-required for live keys) X-Signature: t=<unix>,v1=<hex HMAC-SHA256 of t.method.path.body>; reject timestamps older than 5 minutes (replay protection).
  3. Test keys only reach test-mode data; live keys require an ACTIVE, verified merchant.
  4. Key scopes (charges:read, charges:write) restrict endpoints.
  5. Rate limits per key: e.g. 100 requests/minute for test, 500 for live (configurable), token-bucket (Bucket4j or your own with PostgreSQL/Redis). Exceeding returns 429 with Retry-After and RateLimit-* headers.
  6. Company verification: the company must exist and be active; record the name and registered office returned by the registry, and flag mismatches with the submitted name.
  7. Every key creation, roll and revocation is audited with the acting user.

Errors

validation-failed (400), invalid-api-key (401), signature-expired (401), insufficient-scope (403), merchant-not-active (409), company-not-found (422), rate-limit-exceeded (429).

Data

  • UK Companies House Public Data API: free; register for an API key at the Companies House developer hub. Company data is available under the Open Government Licence v3.0. Attribution: "Contains public sector information licensed under the Open Government Licence v3.0." Respect the published rate limit (600 requests per 5 minutes) and keep the key out of Git.
  • Tests use WireMock stubs of the company profile endpoint, so CI never calls the real API.
  • Merchants and keys are created through your API (synthetic, CC0).

Step-by-step build guide: Merchant onboarding and API key platform

Work through the steps in order. Each step ends with a Done when check: don't move on until it passes. Commit after every step with a clear message, so your history tells the story of the build.

Before you start

  • Finish the topics listed under "Skills you'll demonstrate" in the brief, or study them alongside.
  • Read the architecture section and the ADRs. You will update both at the end.
  • You need Java 21, Docker Desktop (16 GB RAM recommended: the app, PostgreSQL and Keycloak run together), Git, IntelliJ IDEA and jq.
  • Work in pull requests from the start (topic 8.1): one branch and one PR per step below, merged after CI is green and, ideally, a peer has reviewed it.

Step 1: Create your repository from the secure starter

git clone https://github.com/sundayayandele/java-zero-hire.git
mkdir merchant-api-platform && cp -R java-zero-hire/phases/02-professional-backend/capstones/05-merchant-api-platform/starter/. merchant-api-platform/
cd merchant-api-platform
git init -b main && git add . && git commit -m "Start from the Merchant onboarding and API key platform starter"

Create an empty public repository called merchant-api-platform on GitHub, then:

git remote add origin https://github.com/<your-username>/merchant-api-platform.git
git push -u origin main

In GitHub, protect main (Settings → Branches): require a pull request and the build and scan checks to pass.

Done when: the Actions tab shows the build and scan jobs green on your first push.

Step 2: Run it locally with Keycloak

cp .env.example .env          # set DB_PASSWORD and KEYCLOAK_ADMIN_PASSWORD to local values
docker compose up --build
export DEV_USER_PASSWORD='<pick a local password>' KEYCLOAK_ADMIN_PASSWORD='<same as .env>'
./scripts/dev-users.sh        # creates alice, bob (CUSTOMER), olu (OPS), ada (ADMIN)
TOKEN=$(curl -s -d client_id=itl-cli -d grant_type=password -d username=alice -d password="$DEV_USER_PASSWORD"   -d scope='openid api.read api.write' http://localhost:8081/realms/itl/protocol/openid-connect/token | jq -r .access_token)
curl -i http://localhost:8080/actuator/health
curl -i -H "Authorization: Bearer $TOKEN" http://localhost:8080/api/v1/anything   # 404 with a token, 401 without
./mvnw verify                 # tests + coverage gate; needs Docker running (Testcontainers)

Done when: health returns {"status":"UP"}, a request without a token gets 401, and ./mvnw verify is green. The base package is ng.itlearning.merchants.

Step 3: Plan your data

This capstone generates its own data (see the brief's Data section). Write the generator as part of the build steps below and release generated data under CC0.

Step 4: Keys and signatures in plain Java

  1. Generate secrets with SecureRandom (32 bytes, base62), prefix sk_test_/sk_live_; hash with SHA-256; compare with MessageDigest.isEqual.
  2. Signature: HMAC-SHA256(secret, t + "." + method + "." + path + "." + body); reject timestamps older than 5 minutes.

Done when: Unit tests cover valid, tampered, expired and replayed requests.

Step 5: Two security filter chains

  1. Chain 1 (/api/v1/merchants/**): JWT resource server. Chain 2 (/api/v1/echo, /api/v1/charges-preview): a custom ApiKeyAuthenticationFilter producing an authentication with key scopes as authorities.
  2. Order the chains with securityMatcher and @Order; test that each rejects the other's credentials.

Done when: JWTs fail on API-key endpoints and API keys fail on dashboard endpoints.

Step 6: Merchant registration and Companies House

  1. Get a free Companies House API key and keep it in .env; the client uses HTTP Basic with the key as username, timeouts and a circuit breaker.
  2. WireMock stubs for active, dissolved and unknown companies; OPS verification activates or rejects.

Done when: Verification tests pass against WireMock; CI never calls the real API.

Step 7: Key lifecycle

  1. Create (secret shown once), list (prefix only), roll (overlap 24 h), revoke; audit every change with the acting user.
  2. For every endpoint write API tests for: no token (401), wrong scope or role (403), another owner's resource (404 or 403 as the brief says), and the happy path. Use jwt() from spring-security-test with the exact authorities each caller has.

Done when: No secret is stored in plain text and the roll overlap test passes.

Step 8: Rate limiting

  1. Token bucket per key (Bucket4j with Redis, or a PostgreSQL row with atomic updates for one instance).
  2. Return 429 with Retry-After and RateLimit-Limit/RateLimit-Remaining headers.

Done when: All acceptance criteria pass and the coverage gate is green.

Step 9: Quality gates, pipeline and deployment

  1. Make sure every CI job is green on main: tests, the JaCoCo gate (raise coverage.minimum in pom.xml as your tests grow; 80% is a good target), the Trivy dependency and secret scan, and the image scan.
  2. Optional: mirror to gitlab.com so .gitlab-ci.yml runs too. Azure DevOps, AWS CodeBuild, Jenkins and Argo CD are covered in the CI/CD guide.
  3. Deploy the app with an identity provider using the deployment guide: Keycloak next to the app on a VPS, or Keycloak in a container / a managed provider in the cloud. Set OAUTH_ISSUER_URI to the deployed issuer.
  4. Put the public health URL (/actuator/health) and the Swagger UI URL at the top of your README.

Done when: the health URL returns UP from the internet, protected endpoints return 401 without a token, and no secret is in Git (the Trivy secret scan is green).

Step 10: Update the architecture pack and write a threat model

  1. Copy the architecture/ folder from this capstone into your repository.
  2. Edit the Mermaid (.mmd) or draw.io (.drawio) files so all five diagrams match what you built; re-export SVG/PNG (draw.io: File → Export; Mermaid: npx @mermaid-js/mermaid-cli -i x.mmd -o x.svg).
  3. Write at least three ADRs of your own (copy the format in architecture/adr/): one on security, one on an integration or resilience choice, one you chose yourself.
  4. Write architecture/threat-model.md: the five most important threats (STRIDE is a good checklist), and how your design and tests mitigate each (topic 6.4).

Done when: someone can understand your system, its risks and its defences from the diagrams, ADRs and threat model without reading code.

Step 11: Write the README and record a demo

Your README must cover, in this order: the business problem; the architecture diagram; how to run it including how to get a token; API examples with curl; data sources, sandboxes and licences; security model (roles, scopes, ownership); design decisions and trade-offs; test strategy and coverage; what you'd do next. Then record a 3-minute demo video that includes one failure scenario (a provider outage, a forbidden request, or a retry).

Done when: a hiring manager can read the README in three minutes and know what you built, how it is secured and why.
