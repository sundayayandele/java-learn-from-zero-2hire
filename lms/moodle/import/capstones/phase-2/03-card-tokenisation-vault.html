Architecture and system design (read this first)

Before you write code, study how this system is designed. These five views are the target architecture for a production-grade build; reproduce and adapt them in your own repository, and keep them current as you build. Full explanations, Mermaid, draw.io, SVG and PNG sources and the architecture decision records are in architecture/.

1. Solution architecture

Solution architecture: only the vault and the processor path see card numbers, which keeps every other system out of PCI DSS scope. Merchants and checkout work with tokens.

Sources: Mermaid · draw.io · SVG · PNG

2. Logical architecture

Logical architecture: tokenisation validates the card, looks it up by keyed HMAC (same card, same token per merchant), encrypts it with a fresh data key, and wraps that key with the current key-encryption key (KEK). Detokenisation is a separate, narrowly scoped and audited path. Rotation re-wraps data keys in batches.

Sources: Mermaid · draw.io · SVG · PNG

3. Technical architecture

Technical architecture shows how the code is organised inside the Spring Boot 4 service: thin controllers that validate and translate errors, services that hold the business rules and transaction boundaries, and a persistence layer (JPA where entity behaviour and locking help, JdbcClient/SQL for reporting and bulk work). Cross-cutting concerns (configuration, health, metrics, scheduling, outbound HTTP) are framework features configured once. Package by feature in code; the layers here are logical.

Sources: Mermaid · draw.io · SVG · PNG

4. Infrastructure architecture

Infrastructure architecture shows where things run on the cheapest production-like target, a single VPS (for example SSDNodes). Only Caddy is reachable from the internet; it terminates TLS and forwards to card-vault on Docker's internal network, so the database is never exposed (Docker port publishing bypasses ufw, so nothing else publishes ports). Images are built once by GitHub Actions, stored in GHCR by commit SHA, and pulled onto the server; backups leave the machine daily. Keycloak is published on its own subdomain through Caddy so users and client apps can obtain tokens; the API only fetches its public signing keys (JWKS) and validates tokens locally. Sizing and every command are in the deployment guide.

Sources: Mermaid · draw.io · SVG · PNG

5. Cloud architecture

Cloud architecture maps the service onto managed cloud building blocks, drawn for AWS (ECS Express Mode, the AWS-recommended path for new accounts since App Runner closed to new customers in 2026). The database sits in private subnets; credentials come from the secret store, never from the image; images are immutable and tagged by commit SHA. The same design on the other clouds:

Key design decisions

  1. One secured Spring Boot service (modular monolith) with an external identity provider
  2. Envelope encryption with versioned key-encryption keys
  3. Keyed HMAC for card lookup, random tokens
  4. Separate scope and audit for detokenisation

Weeks 17–24. Modules used: 5, 6, 7, 8.

Business context

Any company that stores card numbers falls under PCI DSS, the card industry's security standard, and every system that touches a primary account number (PAN) is "in scope" for audits. Payment companies shrink that scope with a token vault: one small, heavily protected service stores encrypted PANs and hands everyone else a meaningless token. Checkout, subscriptions and refunds then work with tokens; only the vault, and the narrow path to the card network, ever see the real number.

You will build that vault for ITL Pay: tokenise, detokenise under strict authorisation, rotate encryption keys without downtime, and prove with tests and logs that PANs never leak.

What you'll build

A Spring Boot 4 service on PostgreSQL, secured by Keycloak.

API

Method and path Who Purpose
POST /api/v1/tokens Checkout service (SCOPE_vault.tokenise) Body: pan, expiryMonth, expiryYear, cardholderName. Returns token, last4, brand, expiry. Same PAN for the same merchant returns the same token
GET /api/v1/tokens/{token} Merchant (SCOPE_api.read, owner only) Metadata only: last4, brand, expiry, status. Never the PAN
POST /api/v1/tokens/{token}/detokenise Payment processor client only (SCOPE_vault.detokenise) Returns the PAN. Requires a purpose (AUTHORISATION, REFUND, CHARGEBACK); every call is audited
DELETE /api/v1/tokens/{token} Owner merchant Deactivate (crypto-shred: destroy the data key)
POST /api/v1/admin/keys/rotate ADMIN with a second ADMIN approval (maker-checker) Start rotation to a new key-encryption key
GET /api/v1/admin/audit?token=&from=&to= OPS Detokenisation audit trail

Business rules

  1. Validate PANs with the Luhn check, 13–19 digits, and detect the brand from the IIN prefix (Visa 4, Mastercard 51–55 and 2221–2720, Verve 5060/5061/6500, Amex 34/37). Expired cards are rejected.
  2. Envelope encryption: each PAN is encrypted with AES-256-GCM using a random per-record data key; the data key is encrypted ("wrapped") with the current key-encryption key (KEK). Store ciphertext, IV, wrapped key and KEK version, never the PAN or the plain data key.
  3. Deterministic lookup for "same PAN → same token" uses an HMAC-SHA256 of the PAN with a separate secret, never a plain hash (PANs are guessable, so unkeyed hashes can be brute-forced).
  4. Tokens are random (at least 128 bits), URL-safe, prefixed tok_, and not derived from the PAN. A format-preserving token (16 digits, passing Luhn, keeping the last four) is a stretch goal.
  5. Key rotation: new tokens use the new KEK immediately; a background job re-wraps old data keys in batches; both versions decrypt during rotation; the old KEK is retired when no record uses it.
  6. PANs, CVVs and full tokens never appear in logs, exceptions, metrics tags or Problem Details. CVV is never accepted or stored (a request containing cvv is rejected with 400).
  7. Detokenisation is rate limited per client and alerts (a metric and a log event) above a threshold.

Errors

validation-failed (400), invalid-pan (422), card-expired (422), token-not-found (404, also for other merchants' tokens), forbidden (403), approval-required (409), rate-limit-exceeded (429).

Data

  • Test card numbers only. Use the published test PANs from payment providers' documentation (for example Stripe's testing page) and Luhn-valid numbers you generate with test prefixes. Never use or store a real card number, even your own.
  • Keys: locally the KEK comes from an environment variable or a file outside Git; in the cloud from AWS KMS, Azure Key Vault or Google Cloud KMS (stretch).
  • Standards to read: PCI Security Standards Council document library (PCI DSS v4.0.1 summary and tokenisation guidelines), and the OWASP Cryptographic Storage Cheat Sheet.
  • Generated data is yours (CC0).

Infrastructure and deployment

  • Sizing: small (0.5 vCPU / 1 GB app, 1 GB PostgreSQL). The database must not be reachable from the internet; enable encryption at rest on managed databases.
  • Network: in production the vault sits in its own subnet, reachable only from the checkout and processor services (security groups / network policies).
  • Deploy: Phase 2 deployment guide. Use the cloud's key management service for the KEK.

Stretch goals

  • KEK in AWS KMS / Azure Key Vault / Google Cloud KMS via their Java SDKs, with the local implementation behind the same interface.
  • Format-preserving tokens.
  • Network tokens: model a scheme token alongside your vault token.

Interview talking points

  • What envelope encryption buys you, and how key rotation works without decrypting everything at once.
  • Why an unkeyed SHA-256 of a PAN is not safe for lookups.
  • How you kept PANs out of logs, and how your tests prove it.
  • How tokenisation reduces PCI DSS scope for the rest of the platform.

Step-by-step build guide: Card tokenisation vault

Work through the steps in order. Each step ends with a Done when check: don't move on until it passes. Commit after every step with a clear message, so your history tells the story of the build.

Before you start

  • Finish the topics listed under "Skills you'll demonstrate" in the brief, or study them alongside.
  • Read the architecture section and the ADRs. You will update both at the end.
  • You need Java 21, Docker Desktop (16 GB RAM recommended: the app, PostgreSQL and Keycloak run together), Git, IntelliJ IDEA and jq.
  • Work in pull requests from the start (topic 8.1): one branch and one PR per step below, merged after CI is green and, ideally, a peer has reviewed it.

Step 1: Create your repository from the secure starter

git clone https://github.com/sundayayandele/java-zero-hire.git
mkdir card-tokenisation-vault && cp -R java-zero-hire/phases/02-professional-backend/capstones/03-card-tokenisation-vault/starter/. card-tokenisation-vault/
cd card-tokenisation-vault
git init -b main && git add . && git commit -m "Start from the Card tokenisation vault starter"

Create an empty public repository called card-tokenisation-vault on GitHub, then:

git remote add origin https://github.com/<your-username>/card-tokenisation-vault.git
git push -u origin main

In GitHub, protect main (Settings → Branches): require a pull request and the build and scan checks to pass.

Done when: the Actions tab shows the build and scan jobs green on your first push.

Step 2: Run it locally with Keycloak

cp .env.example .env          # set DB_PASSWORD and KEYCLOAK_ADMIN_PASSWORD to local values
docker compose up --build
export DEV_USER_PASSWORD='<pick a local password>' KEYCLOAK_ADMIN_PASSWORD='<same as .env>'
./scripts/dev-users.sh        # creates alice, bob (CUSTOMER), olu (OPS), ada (ADMIN)
TOKEN=$(curl -s -d client_id=itl-cli -d grant_type=password -d username=alice -d password="$DEV_USER_PASSWORD"   -d scope='openid api.read api.write' http://localhost:8081/realms/itl/protocol/openid-connect/token | jq -r .access_token)
curl -i http://localhost:8080/actuator/health
curl -i -H "Authorization: Bearer $TOKEN" http://localhost:8080/api/v1/anything   # 404 with a token, 401 without
./mvnw verify                 # tests + coverage gate; needs Docker running (Testcontainers)

Done when: health returns {"status":"UP"}, a request without a token gets 401, and ./mvnw verify is green. The base package is ng.itlearning.vault.

Step 3: Plan your data

This capstone generates its own data (see the brief's Data section). Write the generator as part of the build steps below and release generated data under CC0.

Step 4: Card validation in plain Java

  1. Implement Luhn, length checks and brand detection from IIN ranges with @ParameterizedTest tables, using only test card numbers.
  2. Reject expired cards using an injected Clock.

Done when: Validation tests pass for valid, invalid and boundary cases (expiry this month).

Step 5: Envelope encryption

  1. EnvelopeCrypto: generate a 256-bit data key (KeyGenerator), encrypt with AES/GCM/NoPadding, 12-byte random IV, 128-bit tag; wrap the data key with the KEK (AES key wrap or GCM) and record the KEK version.
  2. A KeyEncryptionKeys interface with a local implementation reading versioned keys from environment variables (base64), never from Git.
  3. Tests: round trip, tampered ciphertext fails, wrong KEK version fails.

Done when: Crypto tests pass and no key material appears in test output.

Step 6: Tokenise and look up

  1. Schema card_token (token, merchant, HMAC, ciphertext, iv, wrapped key, KEK version, last4, brand, expiry, status) with a unique (merchant_id, pan_hmac).
  2. POST /api/v1/tokens with SCOPE_vault.tokenise: reject any cvv field (configure Jackson to fail on unknown properties for this DTO), validate, HMAC lookup, else encrypt and insert.

Done when: Same card and merchant gives the same token; a SQL search for the PAN digits finds nothing.

Step 7: Detokenise with audit

  1. POST /api/v1/tokens/{token}/detokenise with SCOPE_vault.detokenise and a purpose; write an audit row for every attempt.
  2. Rate-limit detokenisation per client and count it in a metric.
  3. For every endpoint write API tests for: no token (401), wrong scope or role (403), another owner's resource (404 or 403 as the brief says), and the happy path. Use jwt() from spring-security-test with the exact authorities each caller has.

Done when: Only the processor client can detokenise; every attempt is audited.

Step 8: Key rotation with maker-checker

  1. POST /admin/keys/rotate creates a pending rotation; a different ADMIN approves it; then new tokens use the new KEK.
  2. A batch job re-wraps data keys (1,000 rows per transaction, FOR UPDATE SKIP LOCKED) and reports progress.

Done when: After rotation and re-wrap every token still detokenises and no row uses the old version.

Step 9: Prove PANs never leak

  1. Add a logback appender in tests that captures all output; after the suite, assert no test PAN appears.
  2. Mask PANs in toString() of every DTO (records override it) and in Problem Details.

Done when: The leak test passes and the coverage gate is green.

Step 10: Quality gates, pipeline and deployment

  1. Make sure every CI job is green on main: tests, the JaCoCo gate (raise coverage.minimum in pom.xml as your tests grow; 80% is a good target), the Trivy dependency and secret scan, and the image scan.
  2. Optional: mirror to gitlab.com so .gitlab-ci.yml runs too. Azure DevOps, AWS CodeBuild, Jenkins and Argo CD are covered in the CI/CD guide.
  3. Deploy the app with an identity provider using the deployment guide: Keycloak next to the app on a VPS, or Keycloak in a container / a managed provider in the cloud. Set OAUTH_ISSUER_URI to the deployed issuer.
  4. Put the public health URL (/actuator/health) and the Swagger UI URL at the top of your README.

Done when: the health URL returns UP from the internet, protected endpoints return 401 without a token, and no secret is in Git (the Trivy secret scan is green).

Step 11: Update the architecture pack and write a threat model

  1. Copy the architecture/ folder from this capstone into your repository.
  2. Edit the Mermaid (.mmd) or draw.io (.drawio) files so all five diagrams match what you built; re-export SVG/PNG (draw.io: File → Export; Mermaid: npx @mermaid-js/mermaid-cli -i x.mmd -o x.svg).
  3. Write at least three ADRs of your own (copy the format in architecture/adr/): one on security, one on an integration or resilience choice, one you chose yourself.
  4. Write architecture/threat-model.md: the five most important threats (STRIDE is a good checklist), and how your design and tests mitigate each (topic 6.4).

Done when: someone can understand your system, its risks and its defences from the diagrams, ADRs and threat model without reading code.

Step 12: Write the README and record a demo

Your README must cover, in this order: the business problem; the architecture diagram; how to run it including how to get a token; API examples with curl; data sources, sandboxes and licences; security model (roles, scopes, ownership); design decisions and trade-offs; test strategy and coverage; what you'd do next. Then record a 3-minute demo video that includes one failure scenario (a provider outage, a forbidden request, or a retry).

Done when: a hiring manager can read the README in three minutes and know what you built, how it is secured and why.
