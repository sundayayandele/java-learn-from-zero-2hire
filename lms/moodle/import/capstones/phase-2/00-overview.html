Phase 2 capstones

← Phase 2 · Data sources and licences · Deployment guide · CI/CD guide

Ten integration- and security-heavy fintech capstones: the work Lagos fintechs, banks and global consultancies hire junior and mid-level Java engineers to do. Each uses public data or simulators that are free for commercial and non-commercial use (licences recorded in each brief and in docs/data-sources.md), or synthetic data generated by your own code. Where a brief mentions a real provider sandbox, it is optional: tests always run against WireMock simulators, so CI never needs a third-party key.

Every capstone starts with its architecture and system design: five views (solution, logical, technical, infrastructure and cloud) as Mermaid, draw.io, SVG and PNG, plus architecture decision records, in its architecture/ folder.

Every capstone has a step-by-step build guide (GUIDE.md): setup from the secure starter, Keycloak, data, build steps that each end with a "done when" check, then the quality-gated pipeline, deployment, architecture pack, README and submission.

Every starter is generated from the Spring Boot secure service starter: OAuth2 resource server with Keycloak, method security, OpenAPI, JaCoCo coverage gate, SBOM, Trivy scans and CI/CD for six platforms.

Complete at least two by the end of week 24: Capstone 1 plus any one other, then defend them in a 20-minute capstone defence (demo, code questions and a live change). A third capstone is welcome but optional: depth beats breadth in interviews. Capstones 1 and 2 come with complete, tested reference solutions; look at them only after you have built your own version.

What every capstone must have

These are the same standards hiring managers look for. They are also the rubric.

  1. A public GitHub repository created from the capstone's starter/ folder, with a meaningful history built through pull requests (topic 8.1): small PRs with descriptions, reviewed by a peer where possible.
  2. An OpenAPI (or GraphQL / proto) contract written and reviewed before the implementation (topic 5.2), published by the running service.
  3. Security: every endpoint authenticated except health and docs; roles and scopes as in the brief; ownership checks; secrets only from the environment; no sensitive data in logs or errors.
  4. Integrations behind interfaces, with timeouts, retries only where safe, and circuit breakers; tested with WireMock.
  5. Tests: unit tests for every business rule (TDD where it helps), Testcontainers integration tests of the main flows, API tests for every 401, 403 and 404 path. The JaCoCo gate at 70% or higher must pass.
  6. Quality-gated CI on GitHub Actions (primary): tests, coverage, Trivy dependency and secret scan, image scan before publishing. The GitLab pipeline should also pass if you mirror the repository.
  7. Operability: health and readiness, Prometheus metrics with at least two business metrics, Problem Details errors, structured logs with a correlation id.
  8. Deployment with the identity provider, on at least one target from the deployment guide, with the health URL in your README. Tear down cloud resources when done.
  9. Architecture pack: the five diagrams updated to match what you built, at least three ADRs of your own, and a short threat model (top five threats and mitigations).
  10. README that a hiring manager can read in three minutes: problem, architecture, how to run it (including getting a token), API examples, data and licence attribution, decisions and trade-offs, what you'd do next.

Rubric

Each criterion is scored 1–4. A capstone passes at 17/24 with no criterion below 2.

Criterion 1: Not yet 2: Developing 3: Hireable 4: Standout
Correctness and domain rules Core flows broken Main flows work; some rules or edge cases missing All rules implemented and tested, including failures and retries Invariants enforced at several layers and proven under concurrency
API design and integration Ad-hoc endpoints, no contract Contract exists; inconsistent errors or no resilience Contract-first, consistent Problem Details, timeouts, safe retries, circuit breakers, idempotency Failure modes documented and demonstrated; graceful degradation
Security Endpoints open or secrets committed Authentication works; authorisation gaps Roles, scopes and ownership enforced and tested; no secrets or sensitive data leaked Threat model, defence in depth, security tests in CI
Testing and quality Few or failing tests Unit tests only; gate not enforced Test pyramid, WireMock and Testcontainers, coverage gate green, code reviewed Mutation testing or contract tests; tests read like the specification
Delivery and operations Not deployed Runs in Docker locally Quality-gated pipeline, deployed with identity provider, metrics and health Automated deployment from CI, dashboards, runbook
Communication Code only README describes what README explains why, trade-offs, licences; ADRs Threat model, ADRs and a 3-minute demo video
