Architecture and system design (read this first)

Before you write code, study how this system is designed. Full explanations, Mermaid, draw.io, SVG and PNG sources and the architecture decision records are in architecture/.

1. Solution architecture

Solution architecture: customers start transfers in their bank's app; banks exchange messages through the switch over gRPC with mutual TLS.

Sources: Mermaid · draw.io · SVG · PNG

2. Logical architecture

Logical architecture: the sending bank runs name enquiry, debits locally, sends the transfer through the switch with a deadline, and treats a timeout as pending, resolving it by status queries. Session ids make every step idempotent; failures reverse the debit.

Sources: Mermaid · draw.io · SVG · PNG

3. Technical architecture

Technical architecture shows how the code is organised inside the Spring Boot 4 service: thin controllers that validate and translate errors, services that hold the business rules and transaction boundaries, and a persistence layer (JPA where entity behaviour and locking help, JdbcClient/SQL for reporting and bulk work). Cross-cutting concerns (configuration, health, metrics, scheduling, outbound HTTP) are framework features configured once. Package by feature in code; the layers here are logical.

Sources: Mermaid · draw.io · SVG · PNG

4. Infrastructure architecture

Infrastructure architecture shows where things run on the cheapest production-like target, a single VPS (for example SSDNodes). Only Caddy is reachable from the internet; it terminates TLS and forwards to interbank-switch on Docker's internal network, so the database is never exposed (Docker port publishing bypasses ufw, so nothing else publishes ports). Images are built once by GitHub Actions, stored in GHCR by commit SHA, and pulled onto the server; backups leave the machine daily. Keycloak is published on its own subdomain through Caddy so users and client apps can obtain tokens; the API only fetches its public signing keys (JWKS) and validates tokens locally. Sizing and every command are in the deployment guide.

Sources: Mermaid · draw.io · SVG · PNG

Cloud architecture maps the service onto managed cloud building blocks, drawn for AWS (ECS Express Mode, the AWS-recommended path for new accounts since App Runner closed to new customers in 2026). Key design decisions

  1. gRPC with Protocol Buffers between banks and switch, REST at the customer edge
  2. A timeout is PENDING, resolved by status queries
  3. Mutual TLS between services

Weeks 17–25. Modules used: 5, 6, 7, 8.

Business context

When you send money from one Nigerian bank to another, your bank first runs a name enquiry (who owns this account at the other bank?) and then a funds transfer, both through NIBSS Instant Payment (NIP), followed by a transaction status query if the response is late. Internally, banks and switches use fast binary protocols between services; gRPC with Protocol Buffers is the modern choice: strongly typed contracts, HTTP/2, deadlines and streaming.

You will build a simplified switch and two participant bank services that talk gRPC, with deadlines, retries on status queries, idempotent transfers and mutual TLS.

What you'll build

Two Spring Boot 4 applications using Spring gRPC (or one application started twice with different profiles), each with its own PostgreSQL schema:

  • Switch: routes requests by the destination bank code, records every message, and settles net positions at the end of the day.
  • Participant bank (run two instances, for example bank code 999001 and 999002): holds accounts and balances, answers name enquiries, credits incoming transfers.

Contract (interbank.proto)

service Interbank {
  rpc NameEnquiry(NameEnquiryRequest) returns (NameEnquiryResponse);
  rpc FundsTransfer(FundsTransferRequest) returns (FundsTransferResponse);
  rpc TransactionStatus(TransactionStatusRequest) returns (FundsTransferResponse);
  rpc StreamSettlementReport(SettlementRequest) returns (stream SettlementLine);
}

Messages carry a session id (unique, 30 characters: sender bank code + timestamp + random), amounts in kobo (int64), and NIP-style response codes (00 success, 07 invalid account, 51 insufficient funds, 25 unable to locate record, 91 beneficiary bank not available, 94 duplicate transaction, 96 system malfunction).

A small REST API on the sending bank (POST /api/v1/transfers, secured with JWT) lets a mobile app start a transfer.

Business rules

  1. Every gRPC call sets a deadline (name enquiry 3 s, transfer 10 s). Deadline exceeded on a transfer is not a failure: the sender marks it PENDING and queries TransactionStatus with backoff until a final answer (max 5 attempts, then REQUIRES_REVIEW).
  2. Idempotency: a repeated session id returns the original result (94 only if the payload differs).
  3. The debit at the sending bank and the credit at the receiving bank are separate local transactions; the sender reverses its debit when the final status is a failure.
  4. Name enquiry results are cached for 10 minutes and must be quoted in the transfer (the name enquiry reference).
  5. Services authenticate each other with mutual TLS (certificates generated by a script, never committed for production); gRPC errors map to proper Status codes, not exceptions with stack traces.
  6. The switch streams the end-of-day settlement report (net position per bank) with server streaming.

Data

  • Synthetic accounts and transfers (CC0) generated by a seed script: 1,000 accounts per bank with Nigerian-style names and 10-digit account numbers (NUBAN check-digit algorithm from the CBN's published NUBAN standard is a good exercise).
  • Background reading: NIBSS's public description of NIP and ISO 20022 concepts (pacs.008 credit transfer, pacs.002 status report) at iso20022.org. Codes here are simplified for learning.

Infrastructure and deployment

Three small containers (switch + two banks) and PostgreSQL (one database per service). gRPC needs HTTP/2 end to end: on cloud load balancers use an HTTP/2-capable target (Cloud Run supports gRPC; on AWS use an ALB with gRPC target groups; Azure Container Apps supports HTTP/2). Phase 2 deployment guide.

Stretch goals

  • gRPC health checking and server reflection for grpcurl.
  • A REST/JSON gateway generated from the proto (transcoding) and a comparison of payload sizes.
  • Fraud hooks: call Phase 1's fraud rules before debiting.

Interview talking points

  • Why a timeout on a transfer must not be treated as a failure.
  • How idempotent session ids and status queries give exactly-once effects over an unreliable network.
  • gRPC vs REST for internal service calls.

Step-by-step build guide: Interbank transfer gRPC service

Work through the steps in order. Each step ends with a Done when check: don't move on until it passes. Commit after every step with a clear message, so your history tells the story of the build.

Before you start

  • Finish the topics listed under "Skills you'll demonstrate" in the brief, or study them alongside.
  • Read the architecture section and the ADRs. You will update both at the end.
  • You need Java 21, Docker Desktop (16 GB RAM recommended: the app, PostgreSQL and Keycloak run together), Git, IntelliJ IDEA and jq.
  • Work in pull requests from the start (topic 8.1): one branch and one PR per step below, merged after CI is green and, ideally, a peer has reviewed it.

Step 1: Create your repository from the secure starter

git clone https://github.com/sundayayandele/java-zero-hire.git
mkdir interbank-transfer-grpc && cp -R java-zero-hire/phases/02-professional-backend/capstones/07-interbank-transfer-grpc/starter/. interbank-transfer-grpc/
cd interbank-transfer-grpc
git init -b main && git add . && git commit -m "Start from the Interbank transfer gRPC service starter"

Create an empty public repository called interbank-transfer-grpc on GitHub, then:

git remote add origin https://github.com/<your-username>/interbank-transfer-grpc.git
git push -u origin main

In GitHub, protect main (Settings → Branches): require a pull request and the build and scan checks to pass.

Done when: the Actions tab shows the build and scan jobs green on your first push.

Step 2: Run it locally with Keycloak

cp .env.example .env          # set DB_PASSWORD and KEYCLOAK_ADMIN_PASSWORD to local values
docker compose up --build
export DEV_USER_PASSWORD='<pick a local password>' KEYCLOAK_ADMIN_PASSWORD='<same as .env>'
./scripts/dev-users.sh        # creates alice, bob (CUSTOMER), olu (OPS), ada (ADMIN)
TOKEN=$(curl -s -d client_id=itl-cli -d grant_type=password -d username=alice -d password="$DEV_USER_PASSWORD"   -d scope='openid api.read api.write' http://localhost:8081/realms/itl/protocol/openid-connect/token | jq -r .access_token)
curl -i http://localhost:8080/actuator/health
curl -i -H "Authorization: Bearer $TOKEN" http://localhost:8080/api/v1/anything   # 404 with a token, 401 without
./mvnw verify                 # tests + coverage gate; needs Docker running (Testcontainers)

Done when: health returns {"status":"UP"}, a request without a token gets 401, and ./mvnw verify is green. The base package is ng.itlearning.interbank.

Step 3: Plan your data

This capstone generates its own data (see the brief's Data section). Write the generator as part of the build steps below and release generated data under CC0.

Step 4: Proto contract and codes

  1. Write src/main/proto/interbank.proto from the brief and generate Java with the protobuf Maven plugin (see the Spring gRPC getting-started guide).
  2. Implement NUBAN check digits and the response-code enum in plain Java with tests.

Done when: Generated classes compile and NUBAN tests pass.

Step 5: Bank service

  1. Implement NameEnquiry and the credit side of FundsTransfer with idempotency by session id.
  2. Test with an in-process gRPC server and a blocking stub.

Done when: Repeating a session id never credits twice.

Step 6: Switch and sending bank

  1. Switch routes by destination bank code and logs every message; sending bank debits locally then calls the switch with withDeadlineAfter(10, SECONDS).
  2. Deadline exceeded → PENDING; a resolver calls TransactionStatus with backoff (max 5) then reverses or completes.

Done when: The slow-receiver test ends with a completed transfer and no reversal.

Step 7: mTLS and the REST edge

  1. Generate a private CA and service certificates with a script (openssl), mounted from outside Git; require client certificates on servers.
  2. Add POST /api/v1/transfers (JWT, SCOPE_api.write, ownership of the source account).
  3. For every endpoint write API tests for: no token (401), wrong scope or role (403), another owner's resource (404 or 403 as the brief says), and the happy path. Use jwt() from spring-security-test with the exact authorities each caller has.

Done when: A client without a certificate is refused; REST authorisation tests pass.

Step 8: Settlement streaming and Compose

  1. Server-streaming StreamSettlementReport with net positions per bank; test that they sum to zero.
  2. compose.yaml runs the switch, two banks, PostgreSQL and Keycloak.

Done when: All acceptance criteria pass and the coverage gate is green.

Step 9: Quality gates, pipeline and deployment

  1. Make sure every CI job is green on main: tests, the JaCoCo gate (raise coverage.minimum in pom.xml as your tests grow; 80% is a good target), the Trivy dependency and secret scan, and the image scan.
  2. Optional: mirror to gitlab.com so .gitlab-ci.yml runs too. Azure DevOps, AWS CodeBuild, Jenkins and Argo CD are covered in the CI/CD guide.
  3. Deploy the app with an identity provider using the deployment guide: Keycloak next to the app on a VPS, or Keycloak in a container / a managed provider in the cloud. Set OAUTH_ISSUER_URI to the deployed issuer.
  4. Put the public health URL (/actuator/health) and the Swagger UI URL at the top of your README.

Done when: the health URL returns UP from the internet, protected endpoints return 401 without a token, and no secret is in Git (the Trivy secret scan is green).

Step 10: Update the architecture pack and write a threat model

  1. Copy the architecture/ folder from this capstone into your repository.
  2. Edit the Mermaid (.mmd) or draw.io (.drawio) files so all five diagrams match what you built; re-export SVG/PNG (draw.io: File → Export; Mermaid: npx @mermaid-js/mermaid-cli -i x.mmd -o x.svg).
  3. Write at least three ADRs of your own (copy the format in architecture/adr/): one on security, one on an integration or resilience choice, one you chose yourself.
  4. Write architecture/threat-model.md: the five most important threats (STRIDE is a good checklist), and how your design and tests mitigate each (topic 6.4).

Done when: someone can understand your system, its risks and its defences from the diagrams, ADRs and threat model without reading code.

Step 11: Write the README and record a demo

Your README must cover, in this order: the business problem; the architecture diagram; how to run it including how to get a token; API examples with curl; data sources, sandboxes and licences; security model (roles, scopes, ownership); design decisions and trade-offs; test strategy and coverage; what you'd do next. Then record a 3-minute demo video that includes one failure scenario (a provider outage, a forbidden request, or a retry).

Done when: a hiring manager can read the README in three minutes and know what you built, how it is secured and why.
