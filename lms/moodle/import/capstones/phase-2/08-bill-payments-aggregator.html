Architecture and system design (read this first)

Before you write code, study how this system is designed. These five views are the target architecture for a production-grade build; reproduce and adapt them in your own repository, and keep them current as you build. Full explanations, Mermaid, draw.io, SVG and PNG sources and the architecture decision records are in architecture/.

1. Solution architecture

Solution architecture: the banking app integrates once; the aggregator handles each biller's protocol, outages and settlement.

Sources: Mermaid · draw.io · SVG · PNG

2. Logical architecture

Logical architecture: each payment debits the wallet, then vends through the biller's adapter. Timeouts become UNKNOWN and are resolved by status queries before any refund. Daily settlement files are reconciled against payments.

Sources: Mermaid · draw.io · SVG · PNG

3. Technical architecture

Technical architecture shows how the code is organised inside the Spring Boot 4 service: thin controllers that validate and translate errors, services that hold the business rules and transaction boundaries, and a persistence layer (JPA where entity behaviour and locking help, JdbcClient/SQL for reporting and bulk work). Cross-cutting concerns (configuration, health, metrics, scheduling, outbound HTTP) are framework features configured once. Package by feature in code; the layers here are logical.

Sources: Mermaid · draw.io · SVG · PNG

4. Infrastructure architecture

Infrastructure architecture shows where things run on the cheapest production-like target, a single VPS (for example SSDNodes). Only Caddy is reachable from the internet; it terminates TLS and forwards to bill-payments on Docker's internal network, so the database is never exposed (Docker port publishing bypasses ufw, so nothing else publishes ports). Images are built once by GitHub Actions, stored in GHCR by commit SHA, and pulled onto the server; backups leave the machine daily. Keycloak is published on its own subdomain through Caddy so users and client apps can obtain tokens; the API only fetches its public signing keys (JWKS) and validates tokens locally. Sizing and every command are in the deployment guide.

Sources: Mermaid · draw.io · SVG · PNG

5. Cloud architecture

Cloud architecture maps the service onto managed cloud building blocks, drawn for AWS (ECS Express Mode, the AWS-recommended path for new accounts since App Runner closed to new customers in 2026). The database sits in private subnets; credentials come from the secret store, never from the image; images are immutable and tagged by commit SHA. The same design on the other clouds:

Key design decisions

  1. One secured Spring Boot service (modular monolith) with an external identity provider
  2. Adapter per biller with its own bulkhead, timeouts and circuit breaker
  3. UNKNOWN is a status, resolved before refunding

Weeks 17–25. Modules used: 5, 6, 7, 8.

Business context

Airtime, data bundles, electricity tokens, cable TV and government levies are among the most frequent transactions in Nigerian banking apps. Behind the "Pay bill" button, an aggregator talks to dozens of billers, each with its own API quirks, outages and reconciliation files. The hard problems are the classic integration problems: validate the customer (meter number, smartcard), take the customer's money exactly once, deliver the value (a token, a top-up) or refund, and reconcile with each biller daily.

What you'll build

A Spring Boot 4 service on PostgreSQL integrating three simulated billers (WireMock), each with a different protocol style:

Biller Style Quirks to handle
PowerCo (prepaid electricity) REST/JSON, synchronous token vend Slow (2–8 s), sometimes times out after vending
TelcoX (airtime and data) REST/JSON, asynchronous: accepts then sends a callback Duplicate callbacks
CableTV (subscriptions) XML over HTTP Validation returns customer name and plan; vend is idempotent by your reference

API

Method and path Who Purpose
GET /api/v1/billers and /billers/{id}/products Customer Catalogue (cached)
POST /api/v1/billers/{id}/validate Customer Validate meter / phone / smartcard; returns customer name
POST /api/v1/bill-payments Customer (SCOPE_api.write) Pay; requires Idempotency-Key; debits the customer's wallet (a local table) then vends
GET /api/v1/bill-payments/{id} Owner or OPS Status and token/receipt
POST /callbacks/telcox TelcoX (signed) Async result
POST /api/v1/ops/reconciliation/{biller} OPS Upload the biller's daily settlement CSV and reconcile

Business rules

  1. Status flow: CREATED → DEBITED → VENDING → SUCCEEDED | FAILED → REFUNDED, or VENDING → UNKNOWN on timeout. Never refund an UNKNOWN: query the biller's status endpoint with backoff first, because the token may already have been delivered.
  2. Per-biller resilience: timeouts sized to each biller, retries only for idempotent calls, a circuit breaker and a bulkhead (limit concurrent calls) so a slow biller can't exhaust threads for the others.
  3. When a biller's circuit is open, the catalogue marks it unavailable and new payments are refused before debiting.
  4. Electricity tokens are shown to the owner only and masked in logs.
  5. Reconciliation matches by your reference: missing on your side, missing on the biller's side, and amount mismatches go to an exception report.
  6. Wallet debits and refunds are double-entry postings (reuse your Phase 1 ledger thinking).

Data

  • Synthetic (CC0): customers, wallets, meter numbers and smartcards generated by your seed; biller simulators written as WireMock stubs, including failure scenarios; settlement CSVs generated by your script with injected breaks.
  • No real biller API is required. If you use a real aggregator sandbox for a stretch goal, read and follow its terms and never commit keys.

Step-by-step build guide: Bill payments aggregator

Work through the steps in order. Each step ends with a Done when check: don't move on until it passes. Commit after every step with a clear message, so your history tells the story of the build.

Before you start

  • Finish the topics listed under "Skills you'll demonstrate" in the brief, or study them alongside.
  • Read the architecture section and the ADRs. You will update both at the end.
  • You need Java 21, Docker Desktop (16 GB RAM recommended: the app, PostgreSQL and Keycloak run together), Git, IntelliJ IDEA and jq.
  • Work in pull requests from the start (topic 8.1): one branch and one PR per step below, merged after CI is green and, ideally, a peer has reviewed it.

Step 1: Create your repository from the secure starter

git clone https://github.com/sundayayandele/java-zero-hire.git
mkdir bill-payments-aggregator && cp -R java-zero-hire/phases/02-professional-backend/capstones/08-bill-payments-aggregator/starter/. bill-payments-aggregator/
cd bill-payments-aggregator
git init -b main && git add . && git commit -m "Start from the Bill payments aggregator starter"

Create an empty public repository called bill-payments-aggregator on GitHub, then:

git remote add origin https://github.com/<your-username>/bill-payments-aggregator.git
git push -u origin main

In GitHub, protect main (Settings → Branches): require a pull request and the build and scan checks to pass.

Done when: the Actions tab shows the build and scan jobs green on your first push.

Step 2: Run it locally with Keycloak

cp .env.example .env          # set DB_PASSWORD and KEYCLOAK_ADMIN_PASSWORD to local values
docker compose up --build
export DEV_USER_PASSWORD='<pick a local password>' KEYCLOAK_ADMIN_PASSWORD='<same as .env>'
./scripts/dev-users.sh        # creates alice, bob (CUSTOMER), olu (OPS), ada (ADMIN)
TOKEN=$(curl -s -d client_id=itl-cli -d grant_type=password -d username=alice -d password="$DEV_USER_PASSWORD"   -d scope='openid api.read api.write' http://localhost:8081/realms/itl/protocol/openid-connect/token | jq -r .access_token)
curl -i http://localhost:8080/actuator/health
curl -i -H "Authorization: Bearer $TOKEN" http://localhost:8080/api/v1/anything   # 404 with a token, 401 without
./mvnw verify                 # tests + coverage gate; needs Docker running (Testcontainers)

Done when: health returns {"status":"UP"}, a request without a token gets 401, and ./mvnw verify is green. The base package is ng.itlearning.bills.

Step 3: Plan your data

This capstone generates its own data (see the brief's Data section). Write the generator as part of the build steps below and release generated data under CC0.

Step 4: State machine and wallet postings

  1. TDD the status flow including UNKNOWN; wallet debits and refunds as balanced postings.

Done when: State and posting tests pass.

Step 5: Three biller adapters

  1. REST/JSON PowerCo with a long read timeout; TelcoX accepts then calls back (signed); CableTV over XML (Jackson XML).
  2. Stateful WireMock scenarios: timeout-after-vend then status SUCCESS; duplicate callbacks.

Done when: Each adapter's tests pass against its stubs.

Step 6: Payment flow with idempotency

  1. Validate, debit (locked wallet row), vend, record; Idempotency-Key required.
  2. Timeouts → UNKNOWN; the resolver job queries status before any refund.
  3. For every endpoint write API tests for: no token (401), wrong scope or role (403), another owner's resource (404 or 403 as the brief says), and the happy path. Use jwt() from spring-security-test with the exact authorities each caller has.

Done when: No double debit on retry and no refund for a vend that succeeded.

Step 7: Bulkheads and breakers

  1. A concurrency limit per biller (Spring Framework 7 @ConcurrencyLimit or a Resilience4j Bulkhead) plus a breaker per biller.
  2. Test: PowerCo hangs while TelcoX payments complete normally.

Done when: The isolation test passes.

Step 8: Reconciliation

  1. Upload a settlement CSV (multipart, size-limited), match by reference, report the three break types.

Done when: All acceptance criteria pass and the coverage gate is green.

Step 9: Quality gates, pipeline and deployment

  1. Make sure every CI job is green on main: tests, the JaCoCo gate (raise coverage.minimum in pom.xml as your tests grow; 80% is a good target), the Trivy dependency and secret scan, and the image scan.
  2. Optional: mirror to gitlab.com so .gitlab-ci.yml runs too. Azure DevOps, AWS CodeBuild, Jenkins and Argo CD are covered in the CI/CD guide.
  3. Deploy the app with an identity provider using the deployment guide: Keycloak next to the app on a VPS, or Keycloak in a container / a managed provider in the cloud. Set OAUTH_ISSUER_URI to the deployed issuer.
  4. Put the public health URL (/actuator/health) and the Swagger UI URL at the top of your README.

Done when: the health URL returns UP from the internet, protected endpoints return 401 without a token, and no secret is in Git (the Trivy secret scan is green).

Step 10: Update the architecture pack and write a threat model

  1. Copy the architecture/ folder from this capstone into your repository.
  2. Edit the Mermaid (.mmd) or draw.io (.drawio) files so all five diagrams match what you built; re-export SVG/PNG (draw.io: File → Export; Mermaid: npx @mermaid-js/mermaid-cli -i x.mmd -o x.svg).
  3. Write at least three ADRs of your own (copy the format in architecture/adr/): one on security, one on an integration or resilience choice, one you chose yourself.
  4. Write architecture/threat-model.md: the five most important threats (STRIDE is a good checklist), and how your design and tests mitigate each (topic 6.4).

Done when: someone can understand your system, its risks and its defences from the diagrams, ADRs and threat model without reading code.

Step 11: Write the README and record a demo

Your README must cover, in this order: the business problem; the architecture diagram; how to run it including how to get a token; API examples with curl; data sources, sandboxes and licences; security model (roles, scopes, ownership); design decisions and trade-offs; test strategy and coverage; what you'd do next. Then record a 3-minute demo video that includes one failure scenario (a provider outage, a forbidden request, or a retry).

Done when: a hiring manager can read the README in three minutes and know what you built, how it is secured and why.
