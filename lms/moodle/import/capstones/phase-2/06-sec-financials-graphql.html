Architecture and system design (read this first)

Before you write code, study how this system is designed. These five views are the target architecture for a production-grade build; reproduce and adapt them in your own repository, and keep them current as you build. Full explanations, Mermaid, draw.io, SVG and PNG sources and the architecture decision records are in architecture/.

1. Solution architecture

Solution architecture: client apps ask for exactly the fields they need from one GraphQL endpoint; the service keeps its own copy of SEC data so clients never hit the SEC directly.

Sources: Mermaid · draw.io · SVG · PNG

2. Logical architecture

Logical architecture: an import path maps XBRL concepts to metrics and keeps every filed value (restatements included); a query path resolves GraphQL fields in batches and calculates ratios on read.

Sources: Mermaid · draw.io · SVG · PNG

3. Technical architecture

Technical architecture shows how the code is organised inside the Spring Boot 4 service: thin controllers that validate and translate errors, services that hold the business rules and transaction boundaries, and a persistence layer (JPA where entity behaviour and locking help, JdbcClient/SQL for reporting and bulk work). Cross-cutting concerns (configuration, health, metrics, scheduling, outbound HTTP) are framework features configured once. Package by feature in code; the layers here are logical.

Sources: Mermaid · draw.io · SVG · PNG

4. Infrastructure architecture

Infrastructure architecture shows where things run on the cheapest production-like target, a single VPS (for example SSDNodes). Only Caddy is reachable from the internet; it terminates TLS and forwards to financials-graphql on Docker's internal network, so the database is never exposed (Docker port publishing bypasses ufw, so nothing else publishes ports). Images are built once by GitHub Actions, stored in GHCR by commit SHA, and pulled onto the server; backups leave the machine daily. Keycloak is published on its own subdomain through Caddy so users and client apps can obtain tokens; the API only fetches its public signing keys (JWKS) and validates tokens locally. Sizing and every command are in the deployment guide.

Sources: Mermaid · draw.io · SVG · PNG

Cloud architecture maps the service onto managed cloud building blocks, drawn for AWS (ECS Express Mode, the AWS-recommended path for new accounts since App Runner closed to new customers in 2026). Key design decisions

  1. One secured Spring Boot service (modular monolith) with an external identity provider
  2. Schema-first GraphQL with batch mapping
  3. Limit depth, page size and complexity; disable introspection in production
  4. Keep all filed values and select the latest on read

Weeks 16–24. Modules used: 5, 6, 7, 8.

Business context

Investment platforms, equity research teams and credit analysts need company fundamentals: revenue, net income, assets, liabilities and cash flow, per company and period. Clients want very different slices (a mobile app needs three numbers, an analyst's spreadsheet needs ten years of twenty metrics), which is where GraphQL shines: one endpoint, and each client asks for exactly the fields it needs. The US SEC publishes every listed company's XBRL financial data free of charge.

You will build a GraphQL API over SEC EDGAR "company facts" data, with a REST import pipeline, sensible query limits and caching.

What you'll build

A Spring Boot 4 service with Spring for GraphQL on PostgreSQL.

Schema (core)

type Query {
  company(ticker: String, cik: ID): Company
  companies(first: Int = 20, after: String, sector: String): CompanyConnection!
  compare(tickers: [String!]!, metric: Metric!, fiscalYear: Int!): [MetricValue!]!
}
type Company { cik: ID!  ticker: String  name: String!  facts(metric: Metric!, period: PeriodType = ANNUAL, last: Int = 5): [MetricValue!]!  ratios(fiscalYear: Int!): Ratios }
type MetricValue { metric: Metric!  value: BigDecimal!  unit: String!  fiscalYear: Int!  fiscalPeriod: String!  periodEnd: Date!  form: String!  filed: Date! }
type Ratios { netMargin: BigDecimal  debtToEquity: BigDecimal  currentRatio: BigDecimal  returnOnEquity: BigDecimal }
enum Metric { REVENUE NET_INCOME TOTAL_ASSETS TOTAL_LIABILITIES STOCKHOLDERS_EQUITY CURRENT_ASSETS CURRENT_LIABILITIES OPERATING_CASH_FLOW }
enum PeriodType { ANNUAL QUARTERLY }

Plus type Mutation { importCompany(cik: ID!): ImportResult! } for ADMIN.

Business rules

  1. Map each Metric to one or more XBRL US-GAAP concepts in configuration (for example REVENUE → Revenues, RevenueFromContractWithCustomerExcludingAssessedTax, SalesRevenueNet), using the first one the company reports.
  2. Annual values come from 10-K filings with fp = FY; when a fact was restated, use the latest filed value for that period and keep the history.
  3. Ratios are calculated with BigDecimal (scale 4, HALF_EVEN) and are null, not an error, when a component is missing or a denominator is zero.
  4. Solve the N+1 problem with @BatchMapping (or DataLoader) so companies { facts(...) } makes a constant number of SQL queries.
  5. Protect the server: maximum query depth 6, maximum first 100, a query complexity limit, and a timeout. Introspection is disabled in production profiles.
  6. Queries need SCOPE_api.read; importCompany needs ROLE_ADMIN.
  7. The importer calls the SEC with a descriptive User-Agent including a contact email (SEC fair-access policy), stays under 10 requests per second, and is idempotent.

Data

  • SEC EDGAR APIs (documentation): https://data.sec.gov/api/xbrl/companyfacts/CIK##########.json per company, the bulk companyfacts.zip, and the ticker list https://www.sec.gov/files/company_tickers.json.
  • Terms: information on SEC.gov is public information that may be copied or distributed without the SEC's permission (SEC privacy and website information); follow the fair-access rules: declare your User-Agent, max 10 requests per second. Attribution: "Source: U.S. Securities and Exchange Commission, EDGAR."
  • For development, import 50–100 companies (for example the 30 Dow Jones constituents plus a few banks); the full bulk file is over 1 GB.

Step-by-step build guide: Company financials GraphQL API

Work through the steps in order. Each step ends with a Done when check: don't move on until it passes. Commit after every step with a clear message, so your history tells the story of the build.

Before you start

  • Finish the topics listed under "Skills you'll demonstrate" in the brief, or study them alongside.
  • Read the architecture section and the ADRs. You will update both at the end.
  • You need Java 21, Docker Desktop (16 GB RAM recommended: the app, PostgreSQL and Keycloak run together), Git, IntelliJ IDEA and jq.
  • Work in pull requests from the start (topic 8.1): one branch and one PR per step below, merged after CI is green and, ideally, a peer has reviewed it.

Step 1: Create your repository from the secure starter

git clone https://github.com/sundayayandele/java-zero-hire.git
mkdir sec-financials-graphql && cp -R java-zero-hire/phases/02-professional-backend/capstones/06-sec-financials-graphql/starter/. sec-financials-graphql/
cd sec-financials-graphql
git init -b main && git add . && git commit -m "Start from the Company financials GraphQL API starter"

Create an empty public repository called sec-financials-graphql on GitHub, then:

git remote add origin https://github.com/<your-username>/sec-financials-graphql.git
git push -u origin main

In GitHub, protect main (Settings → Branches): require a pull request and the build and scan checks to pass.

Done when: the Actions tab shows the build and scan jobs green on your first push.

Step 2: Run it locally with Keycloak

cp .env.example .env          # set DB_PASSWORD and KEYCLOAK_ADMIN_PASSWORD to local values
docker compose up --build
export DEV_USER_PASSWORD='<pick a local password>' KEYCLOAK_ADMIN_PASSWORD='<same as .env>'
./scripts/dev-users.sh        # creates alice, bob (CUSTOMER), olu (OPS), ada (ADMIN)
TOKEN=$(curl -s -d client_id=itl-cli -d grant_type=password -d username=alice -d password="$DEV_USER_PASSWORD"   -d scope='openid api.read api.write' http://localhost:8081/realms/itl/protocol/openid-connect/token | jq -r .access_token)
curl -i http://localhost:8080/actuator/health
curl -i -H "Authorization: Bearer $TOKEN" http://localhost:8080/api/v1/anything   # 404 with a token, 401 without
./mvnw verify                 # tests + coverage gate; needs Docker running (Testcontainers)

Done when: health returns {"status":"UP"}, a request without a token gets 401, and ./mvnw verify is green. The base package is ng.itlearning.financials.

Step 3: Get the data

Never commit raw datasets; download them with a script. Add data/ to .gitignore first.

mkdir -p data
# The SEC requires a descriptive User-Agent with a contact email
UA='YourName yourname@example.com'
curl -A "$UA" -o data/company_tickers.json https://www.sec.gov/files/company_tickers.json
curl -A "$UA" -o data/CIK0000320193.json https://data.sec.gov/api/xbrl/companyfacts/CIK0000320193.json

Copy the licence and attribution lines from the brief's Data section into your README now.

Done when: the files are in data/ and git status doesn't show them.

Step 4: Schema first

  1. Write src/main/resources/graphql/schema.graphqls from the brief; add BigDecimal and Date scalars (graphql-java extended scalars or your own).
  2. Review the schema in a PR before writing resolvers.

Done when: The schema loads at startup and the PR is merged.

Step 5: Importer with recorded data

  1. Parse a recorded companyfacts JSON (Jackson streaming or tree model) and map concepts to metrics from configuration.
  2. Store every (metric, period, filed) value; select the latest filed on read.
  3. The live importer sends the User-Agent, waits ≥ 100 ms between requests and is idempotent.

Done when: Importer tests on the recorded file give the expected annual revenue for three years.

Step 6: Resolvers with batching

  1. @QueryMapping for company, companies (connection with cursors) and compare; @BatchMapping for Company.facts and Company.ratios.
  2. Count SQL statements in a test (a datasource proxy or Hibernate statistics) to prove no N+1.

Done when: The batching test shows a constant number of queries for 20 companies.

Step 7: Security and limits

  1. Secure /graphql with SCOPE_api.read; @PreAuthorize("hasRole('ADMIN')") on importCompany.
  2. Add MaxQueryDepthInstrumentation(6) and a complexity limit; cap first at 100; disable introspection in the prod profile.
  3. Test with HttpGraphQlTester (or GraphQlTester) including rejected deep queries.

Done when: All acceptance criteria pass and the coverage gate is green.

Step 8: Quality gates, pipeline and deployment

  1. Make sure every CI job is green on main: tests, the JaCoCo gate (raise coverage.minimum in pom.xml as your tests grow; 80% is a good target), the Trivy dependency and secret scan, and the image scan.
  2. Optional: mirror to gitlab.com so .gitlab-ci.yml runs too. Azure DevOps, AWS CodeBuild, Jenkins and Argo CD are covered in the CI/CD guide.
  3. Deploy the app with an identity provider using the deployment guide: Keycloak next to the app on a VPS, or Keycloak in a container / a managed provider in the cloud. Set OAUTH_ISSUER_URI to the deployed issuer.
  4. Put the public health URL (/actuator/health) and the Swagger UI URL at the top of your README.

Done when: the health URL returns UP from the internet, protected endpoints return 401 without a token, and no secret is in Git (the Trivy secret scan is green).

Step 9: Update the architecture pack and write a threat model

  1. Copy the architecture/ folder from this capstone into your repository.
  2. Edit the Mermaid (.mmd) or draw.io (.drawio) files so all five diagrams match what you built; re-export SVG/PNG (draw.io: File → Export; Mermaid: npx @mermaid-js/mermaid-cli -i x.mmd -o x.svg).
  3. Write at least three ADRs of your own (copy the format in architecture/adr/): one on security, one on an integration or resilience choice, one you chose yourself.
  4. Write architecture/threat-model.md: the five most important threats (STRIDE is a good checklist), and how your design and tests mitigate each (topic 6.4).

Done when: someone can understand your system, its risks and its defences from the diagrams, ADRs and threat model without reading code.

Step 10: Write the README and record a demo

Your README must cover, in this order: the business problem; the architecture diagram; how to run it including how to get a token; API examples with curl; data sources, sandboxes and licences; security model (roles, scopes, ownership); design decisions and trade-offs; test strategy and coverage; what you'd do next. Then record a 3-minute demo video that includes one failure scenario (a provider outage, a forbidden request, or a retry).

Done when: a hiring manager can read the README in three minutes and know what you built, how it is secured and why.
