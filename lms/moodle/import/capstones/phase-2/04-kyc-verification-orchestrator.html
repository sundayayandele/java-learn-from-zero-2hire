1. Solution architecture

Solution architecture: the onboarding app submits once; the orchestrator calls four external providers and returns a tier the account-opening system can act on.

Sources: Mermaid · draw.io · SVG · PNG

2. Logical architecture

Logical architecture: the orchestrator runs the cheap, decisive identity check first, then face match and watchlist screening in parallel, then waits for the asynchronous address result. The tier policy turns results into Tier 1–3 or REFER; compliance decides referrals. Stored data is minimised.

Sources: Mermaid · draw.io · SVG · PNG

3. Technical architecture

Technical architecture shows how the code is organised inside the Spring Boot 4 service: thin controllers that validate and translate errors, services that hold the business rules and transaction boundaries, and a persistence layer (JPA where entity behaviour and locking help, JdbcClient/SQL for reporting and bulk work). Cross-cutting concerns (configuration, health, metrics, scheduling, outbound HTTP) are framework features configured once. Package by feature in code; the layers here are logical.

Sources: Mermaid · draw.io · SVG · PNG

4. Infrastructure architecture

Infrastructure architecture shows where things run on the cheapest production-like target, a single VPS (for example SSDNodes). Only Caddy is reachable from the internet; it terminates TLS and forwards to kyc-orchestrator on Docker's internal network, so the database is never exposed (Docker port publishing bypasses ufw, so nothing else publishes ports). Images are built once by GitHub Actions, stored in GHCR by commit SHA, and pulled onto the server; backups leave the machine daily. Keycloak is published on its own subdomain through Caddy so users and client apps can obtain tokens; the API only fetches its public signing keys (JWKS) and validates tokens locally. Sizing and every command are in the deployment guide.

Sources: Mermaid · draw.io · SVG · PNG

Cloud architecture maps the service onto managed cloud building blocks, drawn for AWS (ECS Express Mode, the AWS-recommended path for new accounts since App Runner closed to new customers in 2026). Key design decisions

  1. One secured Spring Boot service (modular monolith) with an external identity provider
  2. Sequence the decisive check first, then run independent checks in parallel
  3. Provider outage leads to PENDING_RETRY, not rejection
  4. Store masked identifiers plus HMAC, purge raw responses

Weeks 18–25. Modules used: 5, 6, 7, 8.

Business context

Before a Nigerian bank or fintech opens an account it must know its customer (KYC): verify identity numbers such as the BVN and NIN, match the customer's name and date of birth, check a selfie against the ID photo, and screen against watchlists. Each check is a call to a different external provider, each with its own latency, outages, pricing and response format. Onboarding teams therefore build an orchestrator that runs the checks in the right order (some in parallel), tolerates provider failures, decides a tier (CBN's tiered KYC: Tier 1, 2, 3 with different limits) and leaves a complete audit trail for compliance.

What you'll build

A Spring Boot 4 service on PostgreSQL that orchestrates four simulated providers (WireMock in tests and locally): identity number lookup (BVN/NIN style), address verification, face match and watchlist screening.

API

Method and path Who Purpose
POST /api/v1/verifications Onboarding app (SCOPE_kyc.write) Start a verification: name, date of birth, phone, identity number and type, address, selfie reference. 202 + Location
GET /api/v1/verifications/{id} Onboarding app (owner) or OPS Status, each check's result, decided tier, reasons
POST /api/v1/verifications/{id}/checks/{check}/retry OPS Retry one failed check
POST /api/v1/verifications/{id}/review ADMIN (compliance) Manual decision with a reason, for REFER outcomes
POST /webhooks/address-provider Provider (signed) Asynchronous address verification result

Business rules

  1. Run identity lookup first; if it fails to match, stop (don't pay for the other checks). Run face match and watchlist screening in parallel (virtual threads or CompletableFuture), then wait for the asynchronous address result.
  2. Name matching tolerates order, case, diacritics and common Nigerian name variants (normalisation plus a similarity threshold from configuration); date of birth must match exactly.
  3. Tier decision: identity match only → Tier 1; plus face match ≥ threshold → Tier 2; plus verified address → Tier 3. Any watchlist hit → REFER for manual review, never automatic approval.
  4. Each provider call has timeouts, at most 2 retries with backoff for transient errors, and a circuit breaker; an open circuit marks the check UNAVAILABLE and the verification PENDING_RETRY, not failed.
  5. Store only what you need: identity numbers are stored masked (*******1234) plus an HMAC for lookups; provider raw responses are encrypted or dropped after 30 days (a scheduled purge job).
  6. Every check result and decision is recorded in an append-only verification_event table with the provider's request id.

Errors

validation-failed (400), verification-not-found (404), check-not-retryable (409), forbidden (403), provider-unavailable (503 on synchronous retry).

Data

  • Synthetic identities only (CC0), generated by your script: names drawn from common Nigerian first and family names, random dates of birth, fake 11-digit numbers. Never use real BVNs, NINs or photos of real people.
  • Provider simulators: WireMock stubs you write from the contract in your OpenAPI file; include slow, failing and mismatching scenarios.
  • Context to read: the CBN's three-tiered KYC requirements (search "CBN three-tiered KYC" on cbn.gov.ng) and the Nigeria Data Protection Act 2023 principles of data minimisation (summarised on ndpc.gov.ng).

Step-by-step build guide: KYC identity verification orchestrator

Work through the steps in order. Each step ends with a Done when check: don't move on until it passes. Commit after every step with a clear message, so your history tells the story of the build.

Before you start

  • Finish the topics listed under "Skills you'll demonstrate" in the brief, or study them alongside.
  • Read the architecture section and the ADRs. You will update both at the end.
  • You need Java 21, Docker Desktop (16 GB RAM recommended: the app, PostgreSQL and Keycloak run together), Git, IntelliJ IDEA and jq.
  • Work in pull requests from the start (topic 8.1): one branch and one PR per step below, merged after CI is green and, ideally, a peer has reviewed it.

Step 1: Create your repository from the secure starter

git clone https://github.com/sundayayandele/java-learn-from-zero-2hire.git
mkdir kyc-verification-orchestrator && cp -R java-learn-from-zero-2hire/phases/02-professional-backend/capstones/04-kyc-verification-orchestrator/starter/. kyc-verification-orchestrator/
cd kyc-verification-orchestrator
git init -b main && git add . && git commit -m "Start from the KYC identity verification orchestrator starter"

Create an empty public repository called kyc-verification-orchestrator on GitHub, then:

git remote add origin https://github.com/<your-username>/kyc-verification-orchestrator.git
git push -u origin main

In GitHub, protect main (Settings → Branches): require a pull request and the build and scan checks to pass.

Done when: the Actions tab shows the build and scan jobs green on your first push.

Step 2: Run it locally with Keycloak

cp .env.example .env          # set DB_PASSWORD and KEYCLOAK_ADMIN_PASSWORD to local values
docker compose up --build
export DEV_USER_PASSWORD='<pick a local password>' KEYCLOAK_ADMIN_PASSWORD='<same as .env>'
./scripts/dev-users.sh        # creates alice, bob (CUSTOMER), olu (OPS), ada (ADMIN)
TOKEN=$(curl -s -d client_id=itl-cli -d grant_type=password -d username=alice -d password="$DEV_USER_PASSWORD"   -d scope='openid api.read api.write' http://localhost:8081/realms/itl/protocol/openid-connect/token | jq -r .access_token)
curl -i http://localhost:8080/actuator/health
curl -i -H "Authorization: Bearer $TOKEN" http://localhost:8080/api/v1/anything   # 404 with a token, 401 without
./mvnw verify                 # tests + coverage gate; needs Docker running (Testcontainers)

Done when: health returns {"status":"UP"}, a request without a token gets 401, and ./mvnw verify is green. The base package is ng.itlearning.kyc.

Step 3: Plan your data

This capstone generates its own data (see the brief's Data section). Write the generator as part of the build steps below and release generated data under CC0.

Step 4: Matching and tier rules with TDD

  1. NameMatcher: normalise case, accents, whitespace and order; similarity with a configurable threshold (Jaro-Winkler or token-set ratio).
  2. TierPolicy: results → Tier 1/2/3 or REFER; watchlist hit always REFER.

Done when: Matching and tier tests pass, including name order swaps and diacritics.

Step 5: Provider clients and simulators

  1. One client per provider with timeouts; WireMock stubs for match, mismatch, slow, 500 and malformed responses.
  2. Synthetic identity generator (CC0) for tests and the seed.

Done when: Each client has tests for every stub scenario.

Step 6: Orchestration

  1. POST /api/v1/verifications returns 202 + Location; work runs asynchronously (virtual threads).
  2. Identity first; on match run face match and watchlist in parallel; then wait for the address webhook (signed).
  3. Append a verification_event per step; store masked id + HMAC only.

Done when: Identity mismatch makes no further provider calls; the parallel test shows overlap in timing.

Step 7: Resilience and retries

  1. Circuit breaker per provider; open circuit → check UNAVAILABLE, verification PENDING_RETRY.
  2. OPS retry endpoint and ADMIN review endpoint for REFER.
  3. For every endpoint write API tests for: no token (401), wrong scope or role (403), another owner's resource (404 or 403 as the brief says), and the happy path. Use jwt() from spring-security-test with the exact authorities each caller has.

Done when: Outage and retry acceptance tests pass.

Step 8: Data minimisation

  1. A scheduled purge removes raw provider payloads older than 30 days.
  2. Check logs and Problem Details never include identity numbers.

Done when: All acceptance criteria pass and the coverage gate is green.

Step 9: Quality gates, pipeline and deployment

  1. Make sure every CI job is green on main: tests, the JaCoCo gate (raise coverage.minimum in pom.xml as your tests grow; 80% is a good target), the Trivy dependency and secret scan, and the image scan.
  2. Optional: mirror to gitlab.com so .gitlab-ci.yml runs too. Azure DevOps, AWS CodeBuild, Jenkins and Argo CD are covered in the CI/CD guide.
  3. Deploy the app with an identity provider using the deployment guide: Keycloak next to the app on a VPS, or Keycloak in a container / a managed provider in the cloud. Set OAUTH_ISSUER_URI to the deployed issuer.
  4. Put the public health URL (/actuator/health) and the Swagger UI URL at the top of your README.

Done when: the health URL returns UP from the internet, protected endpoints return 401 without a token, and no secret is in Git (the Trivy secret scan is green).

Step 10: Update the architecture pack and write a threat model

  1. Copy the architecture/ folder from this capstone into your repository.
  2. Edit the Mermaid (.mmd) or draw.io (.drawio) files so all five diagrams match what you built; re-export SVG/PNG (draw.io: File → Export; Mermaid: npx @mermaid-js/mermaid-cli -i x.mmd -o x.svg).
  3. Write at least three ADRs of your own (copy the format in architecture/adr/): one on security, one on an integration or resilience choice, one you chose yourself.
  4. Write architecture/threat-model.md: the five most important threats (STRIDE is a good checklist), and how your design and tests mitigate each (topic 6.4).

Done when: someone can understand your system, its risks and its defences from the diagrams, ADRs and threat model without reading code.

Step 11: Write the README and record a demo

Your README must cover, in this order: the business problem; the architecture diagram; how to run it including how to get a token; API examples with curl; data sources, sandboxes and licences; security model (roles, scopes, ownership); design decisions and trade-offs; test strategy and coverage; what you'd do next. Then record a 3-minute demo video that includes one failure scenario (a provider outage, a forbidden request, or a retry).

Done when: a hiring manager can read the README in three minutes and know what you built, how it is secured and why.
