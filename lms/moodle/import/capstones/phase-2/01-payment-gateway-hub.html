Architecture and system design (read this first)

Before you write code, study how this system is designed. These five views are the target architecture for a production-grade build; reproduce and adapt them in your own repository, and keep them current as you build. Full explanations, Mermaid, draw.io, SVG and PNG sources and the architecture decision records are in architecture/.

1. Solution architecture

Solution architecture: merchant applications integrate once with the hub; the hub integrates with each payment provider. Providers call back with signed webhooks. Keycloak issues the merchants' tokens; operations watch provider health and payments.

Sources: Mermaid · draw.io · SVG · PNG

2. Logical architecture

Logical architecture: three flows share one payment record. Initialise checks the idempotency key, picks a provider through the router and stores the payment as PENDING. Webhooks are verified (HMAC over the raw body), de-duplicated by provider event id and applied through the state machine. Reconciliation verifies stale pending payments. Every transition appends an immutable payment event.

Sources: Mermaid · draw.io · SVG · PNG

3. Technical architecture

Technical architecture shows how the code is organised inside the Spring Boot 4 service: thin controllers that validate and translate errors, services that hold the business rules and transaction boundaries, and a persistence layer (JPA where entity behaviour and locking help, JdbcClient/SQL for reporting and bulk work). Cross-cutting concerns (configuration, health, metrics, scheduling, outbound HTTP) are framework features configured once. Package by feature in code; the layers here are logical.

Sources: Mermaid · draw.io · SVG · PNG

4. Infrastructure architecture

Infrastructure architecture shows where things run on the cheapest production-like target, a single VPS (for example SSDNodes). Only Caddy is reachable from the internet; it terminates TLS and forwards to payment-gateway-hub on Docker's internal network, so the database is never exposed (Docker port publishing bypasses ufw, so nothing else publishes ports). Images are built once by GitHub Actions, stored in GHCR by commit SHA, and pulled onto the server; backups leave the machine daily. Keycloak is published on its own subdomain through Caddy so users and client apps can obtain tokens; the API only fetches its public signing keys (JWKS) and validates tokens locally. Sizing and every command are in the deployment guide.

Sources: Mermaid · draw.io · SVG · PNG

5. Cloud architecture

Cloud architecture maps the service onto managed cloud building blocks, drawn for AWS (ECS Express Mode, the AWS-recommended path for new accounts since App Runner closed to new customers in 2026). The database sits in private subnets; credentials come from the secret store, never from the image; images are immutable and tagged by commit SHA. The same design on the other clouds:

Key design decisions

  1. One secured Spring Boot service (modular monolith) with an external identity provider
  2. Contract first: the API description is written and reviewed before the code
  3. Explicit payment state machine with an append-only event history
  4. Idempotency keys for merchants, event-id deduplication for providers
  5. Circuit breaker per provider with priority failover for initialisation only

Required for every learner. Weeks 16–25. Modules used: 5, 6, 7, 8.

Business context

Nigerian fintechs, e-commerce platforms and banks rarely talk to card schemes directly: they integrate payment service providers (PSPs) such as Paystack, Flutterwave, Interswitch or Stripe. Every integration has the same hard parts: initialising a payment, sending the customer to the provider, receiving webhooks that may arrive late, twice or out of order, verifying the result, coping when the provider is slow or down, and never charging or crediting twice. Teams that do this well keep a single internal payment hub in front of all providers, so product teams integrate once.

You will build that hub for ITL Commerce: merchant applications call one clean API; the hub routes each payment to a provider, verifies signed webhooks, drives each payment through a strict state machine, fails over when a provider's circuit is open, and reconciles anything left pending.

What you'll build

A secured Spring Boot 4 REST service backed by PostgreSQL, integrating two payment providers through one PaymentProvider interface.

Providers

  • Provider A ("paystack-like") and Provider B ("flutterwave-like"): in development and tests they are simulated with WireMock using the request/response shapes in the brief's provider contract. Optionally, point Provider A at Paystack's test mode with your own test secret key (never commit it).
  • Each provider has a base URL, a secret key (for API calls and webhook signatures) and a priority, all from @ConfigurationProperties and environment variables.

Payment state machine

INITIATED ──▶ PENDING ──▶ SUCCEEDED ──▶ REFUNDED (full) / PARTIALLY_REFUNDED
     │            │
     └──▶ FAILED ◀┘            (ABANDONED after 24 h pending with no provider result)

Only the transitions drawn are legal. A late pending event never moves a SUCCEEDED payment backwards; a success webhook for an ABANDONED payment is recorded and flagged for operations, not silently applied.

API

Method and path Who Purpose
POST /api/v1/payments Merchant app (SCOPE_api.write) Initialise a payment. Requires an Idempotency-Key header. Returns 201 with reference, provider, authorizationUrl, status
GET /api/v1/payments/{reference} The owning merchant (SCOPE_api.read) or OPS Payment details and status history
GET /api/v1/payments?status=&from=&to=&cursor= Owning merchant or OPS Cursor-paginated list, newest first
POST /api/v1/payments/{reference}/verify Owning merchant Ask the provider for the latest status and apply it
POST /api/v1/payments/{reference}/refunds Owning merchant (SCOPE_api.write) Full or partial refund; total refunds may not exceed the amount
POST /webhooks/{provider} The provider (no JWT) Signed webhook. Verify the HMAC signature over the raw body before parsing
GET /api/v1/ops/providers OPS Each provider's circuit-breaker state and recent error rate

The merchant is the token's sub (or azp for client-credentials tokens). Never accept a merchant id from the request body.

Business rules

  1. Amounts are integers in minor units (kobo, cents, pesewas) with an ISO 4217 currency: NGN, GHS, KES, USD. Minimum 100 minor units; maximum configurable per currency.
  2. Idempotency: the same Idempotency-Key from the same merchant with the same payload returns the original response (status 201 replayed) and calls no provider. The same key with a different payload returns 422 idempotency-key-reused. Keys expire after 24 hours.
  3. Routing: use the highest-priority provider that supports the currency and whose circuit breaker is not open. If none is available, return 503 no-provider-available with Retry-After.
  4. Webhooks: reject an invalid or missing signature with 401 and store nothing. Process each provider event id once (store it with a unique constraint); duplicates return 200 so the provider stops retrying. Respond within 2 seconds: persist, then process.
  5. Outbound calls have connect and read timeouts (2 s / 5 s). verify is retried up to 3 times with exponential backoff and jitter on timeouts and 5xx; initialise is not retried blindly (it is not idempotent at the provider unless you pass your reference).
  6. Reconciliation: a scheduled job verifies payments PENDING for more than 15 minutes, and marks those older than 24 hours ABANDONED.
  7. Refunds: only SUCCEEDED or PARTIALLY_REFUNDED payments; the sum of refunds never exceeds the original amount (enforce in the database too).
  8. Every state change is appended to payment_event (who/what caused it, old and new status, provider event id) and is never updated or deleted.

Errors

RFC 9457 Problem Details with stable type URIs: validation-failed (400), unauthorized (401), forbidden (403), payment-not-found (404, also returned for other merchants' payments so references can't be probed), idempotency-key-missing (400), idempotency-key-reused (422), invalid-state-transition (409), refund-exceeds-amount (422), provider-unavailable (502), no-provider-available (503).

Provider contract

The simulator (and the WireMock stubs in your tests) follow this simplified contract, modelled on Paystack's public API:

Call Request Response
POST {base}/transaction/initialize {"reference","amount","currency","email","callback_url"} with Authorization: Bearer {secret} {"status":true,"data":{"authorization_url","access_code","reference"}}
GET {base}/transaction/verify/{reference} Authorization: Bearer {secret} {"status":true,"data":{"reference","status":"success"|"failed"|"abandoned"|"ongoing","amount","currency","id"}}
POST {base}/refund {"transaction","amount"} {"status":true,"data":{"id","status":"pending"|"processed"}}
Webhook to you {"event":"charge.success"|"charge.failed"|"refund.processed","data":{"id","reference","amount","currency","status"}} Header x-provider-signature: hex HMAC-SHA512 of the raw body with the provider secret

Data

  • No external dataset. Payments are created through your API; write a load script that creates 10,000 payments across both providers and fires their webhooks (including duplicates and out-of-order events). Generated data is yours; publish it under CC0 if you share it.
  • Optional sandbox: Paystack test mode. Free with a Paystack account; test keys start with sk_test_ and move no real money. Read Paystack's test payments and webhooks documentation, and follow Paystack's terms of service. Never commit keys, never use live keys, and note that Paystack signs webhooks with header x-paystack-signature.
  • Currency metadata (minor units) comes from java.util.Currency.

Infrastructure and deployment

  • Local: docker compose up --build runs PostgreSQL, Keycloak and the app; WireMock runs inside the tests (add a WireMock container to Compose for manual testing).
  • Sizing: app 0.5 vCPU / 1 GB; PostgreSQL 1 vCPU / 1 GB; Keycloak 1 vCPU / 1 GB (or a managed identity provider). A 2 vCPU / 4 GB VPS runs all three.
  • Public webhooks: providers must reach /webhooks/{provider} over HTTPS. On a VPS, Caddy gives you TLS; locally use the provider's test webhook tool or a tunnel only for testing.
  • Deploy: follow the Phase 2 deployment guide.

Stretch goals

  • A transactional outbox that publishes PaymentSucceeded events (the pattern you'll use with Kafka in Phase 3).
  • Per-merchant rate limiting on POST /payments (Bucket4j) returning 429 with Retry-After.
  • Replace WireMock in a dedicated test profile with Paystack test mode and record the differences you found.
  • A small dashboard of payment success rate by provider (Micrometer + Grafana).

Interview talking points

  • Why the hub verifies the webhook signature over the raw bytes, and why the comparison must be constant-time.
  • How idempotency keys differ from webhook event deduplication, and why you need both.
  • What happens if your service crashes after the provider charged the card but before you saved the result.
  • How the circuit breaker, retries and timeouts interact, and why initialise is not retried blindly.

Step-by-step build guide: Payment gateway integration hub

Work through the steps in order. Each step ends with a Done when check: don't move on until it passes. Commit after every step with a clear message, so your history tells the story of the build.

Before you start

  • Finish the topics listed under "Skills you'll demonstrate" in the brief, or study them alongside.
  • Read the architecture section and the ADRs. You will update both at the end.
  • You need Java 21, Docker Desktop (16 GB RAM recommended: the app, PostgreSQL and Keycloak run together), Git, IntelliJ IDEA and jq.
  • Work in pull requests from the start (topic 8.1): one branch and one PR per step below, merged after CI is green and, ideally, a peer has reviewed it.

Step 2: Run it locally with Keycloak

cp .env.example .env          # set DB_PASSWORD and KEYCLOAK_ADMIN_PASSWORD to local values

Done when: health returns {"status":"UP"}, a request without a token gets 401, and ./mvnw verify is green. The base package is ng.itlearning.gateway.

Step 3: Plan your data

This capstone generates its own data (see the brief's Data section). Write the generator as part of the build steps below and release generated data under CC0.

Step 4: Write and review the OpenAPI contract

  1. Create src/main/resources/static/openapi.yaml (or docs/openapi.yaml) describing every endpoint in the brief, the Idempotency-Key header, the payment schema and every Problem Details type.
  2. Open a pull request containing only the contract and ask a peer (or your mentor) to review it (topic 7.5).
  3. Add a test that fetches /v3/api-docs and checks the paths in the contract exist once you implement them.

Done when: The contract PR is merged and every status code in the brief appears in it.

Step 5: Model the payment state machine with TDD

  1. Write PaymentStatus (enum) and a PaymentStateMachine with boolean canMove(from, to) and PaymentStatus apply(current, ProviderResult).
  2. Write the tests first: every legal transition, every illegal one, and the out-of-order cases (ongoing after SUCCEEDED keeps SUCCEEDED).
  3. Money as long minor units plus Currency; validate minimum and maximum amounts in a Money record.

Done when: State machine tests cover every arrow in the brief's diagram and all pass.

Step 6: Schema and migrations

  1. V1__payments.sql: payment (unique reference, merchant_id, amount_minor, currency, status, provider, version), payment_event (append-only), idempotency_key (unique (merchant_id, idem_key)), webhook_event (unique (provider, event_id)), refund.
  2. Add CHECK constraints for positive amounts and allowed statuses, and a trigger or check that keeps total refunds ≤ amount.
  3. Index payment(merchant_id, created_at desc, id) for cursor pagination and payment(status, updated_at) for reconciliation.

Done when: ./mvnw verify passes and the Flyway history shows your migration on Testcontainers PostgreSQL.

Step 7: Provider client with WireMock

  1. Define PaymentProvider (initialise, verify, refund, supports(currency)) and implement it once for the brief's provider contract, configured per provider (base URL, secret, priority).
  2. Build the RestClient with ClientHttpRequestFactoryBuilder.jdk() and HttpClientSettings.defaults().withConnectTimeout(2s).withReadTimeout(5s) (topic 5.4).
  3. Test it against WireMock (wiremock-standalone): success, 4xx, 5xx, slow responses that exceed the read timeout.

Done when: Provider client tests pass, including one that proves the read timeout fires.

Step 8: Initialise payments with idempotency keys

  1. POST /api/v1/payments: require Idempotency-Key (400 if missing); hash the request body (SHA-256 of a canonical JSON) and look up (merchant, key).
  2. Same key + same hash → replay the stored response; same key + different hash → 422 idempotency-key-reused.
  3. Insert the key row and the payment in one transaction, call the provider, then store the response. Handle the race where two identical requests arrive together (unique constraint violation → wait and replay).

Done when: WireMock verifies exactly one provider call when the same request is sent twice, including concurrently.

Step 9: Signed webhooks, deduplicated

  1. POST /webhooks/{provider} reads the raw body (@RequestBody byte[]), computes HMAC-SHA512 with the provider secret and compares with MessageDigest.isEqual (constant time).
  2. Permit the webhook path in the security chain without a JWT; the signature is its authentication.
  3. Insert into webhook_event; a unique violation means a duplicate: return 200 without reprocessing. Then lock the payment (SELECT ... FOR UPDATE) and apply the state machine, appending a payment_event.

Done when: Bad signature → 401 and nothing stored; the same event sent twice concurrently produces one payment_event.

Step 10: Routing, circuit breakers and retries

  1. Wrap each provider in its own Resilience4j CircuitBreaker (count-based window, 50% failure threshold, 30 s open).
  2. ProviderRouter picks the highest-priority provider that supports the currency and whose breaker allows calls; none → 503 no-provider-available with Retry-After.
  3. Retry verify up to 3 attempts with exponential backoff and jitter on timeouts and 5xx (Spring Framework 7 @Retryable or Resilience4j Retry). Never retry initialise blindly.
  4. Expose breaker states at GET /api/v1/ops/providers (OPS only).

Done when: With Provider A stubbed to time out, new payments go to Provider B; with both down the API returns 503.

Step 11: Security and ownership

  1. Scopes: api.write to create and refund, api.read to read; ROLE_OPS may read any payment.
  2. The merchant id is the JWT subject (CurrentUser.subject()); queries always filter by it, and another merchant's reference returns 404.
  3. For every endpoint write API tests for: no token (401), wrong scope or role (403), another owner's resource (404 or 403 as the brief says), and the happy path. Use jwt() from spring-security-test with the exact authorities each caller has.

Done when: The authorisation tests for every endpoint pass.

Step 12: Refunds, reconciliation and metrics

  1. Refunds: only SUCCEEDED/PARTIALLY_REFUNDED; lock the payment, check the running total, call the provider, record the refund.
  2. A @Scheduled job verifies payments pending > 15 minutes and marks those pending > 24 hours ABANDONED (use a Clock bean so tests can move time).
  3. Metrics: payments.initialised{provider,currency}, payments.completed{provider,status}, webhooks.rejected{reason}.

Done when: Every acceptance criterion in the brief has a passing test, and the coverage gate passes.

Step 13: Quality gates, pipeline and deployment

  1. Make sure every CI job is green on main: tests, the JaCoCo gate (raise coverage.minimum in pom.xml as your tests grow; 80% is a good target), the Trivy dependency and secret scan, and the image scan.
  2. Optional: mirror to gitlab.com so .gitlab-ci.yml runs too. Azure DevOps, AWS CodeBuild, Jenkins and Argo CD are covered in the CI/CD guide.
  3. Deploy the app with an identity provider using the deployment guide: Keycloak next to the app on a VPS, or Keycloak in a container / a managed provider in the cloud. Set OAUTH_ISSUER_URI to the deployed issuer.
  4. Put the public health URL (/actuator/health) and the Swagger UI URL at the top of your README.

Done when: the health URL returns UP from the internet, protected endpoints return 401 without a token, and no secret is in Git (the Trivy secret scan is green).
