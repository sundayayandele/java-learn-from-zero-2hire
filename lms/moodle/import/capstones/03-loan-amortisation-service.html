Architecture and system design (read this first)

Before you write code, study how this system is designed. These five views are the target architecture for a production-grade build; reproduce and adapt them in your own repository, and keep them current as you build. Full explanations, Mermaid, draw.io, SVG and PNG sources and the architecture decision records are in architecture/.

1. Solution architecture

Solution architecture: officers and the customer app quote and book loans; collections works from the arrears portfolio; disbursements and repayments would post to the core ledger (Capstone 1). Market lending rates from the World Bank inform product configuration.

Sources: Mermaid · draw.io · SVG · PNG

2. Logical architecture

Logical architecture: a pure schedule engine (no I/O, exhaustively tested) used by quoting and booking; servicing allocates repayments in a configurable order; a nightly arrears job ages loans and posts penalties; portfolio reporting buckets loans by days past due.

Sources: Mermaid · draw.io · SVG · PNG

3. Technical architecture

Technical architecture shows how the code is organised inside the Spring Boot 4 service: thin controllers that validate and translate errors, services that hold the business rules and transaction boundaries, and a persistence layer (JPA where entity behaviour and locking help, JdbcClient/SQL for reporting and bulk work). Cross-cutting concerns (configuration, health, metrics, scheduling, outbound HTTP) are framework features configured once. Package by feature in code; the layers here are logical.

Sources: Mermaid · draw.io · SVG · PNG

4. Infrastructure architecture

Infrastructure architecture shows where things run on the cheapest production-like target, a single VPS (for example SSDNodes). Only Caddy is reachable from the internet; it terminates TLS and forwards to loan-amortisation-service on Docker's internal network, so the database is never exposed (Docker port publishing bypasses ufw, so nothing else publishes ports). Images are built once by GitHub Actions, stored in GHCR by commit SHA, and pulled onto the server; backups leave the machine daily. Sizing and every command are in the deployment guide.

Sources: Mermaid · draw.io · SVG · PNG

Key design decisions

  1. One deployable Spring Boot service (modular monolith) on PostgreSQL
  2. Sealed RepaymentMethod with a pure schedule engine
  3. Final instalment absorbs rounding
  4. Injected Clock and business-date arithmetic
  5. Nightly arrears job with a single-runner lock

Weeks 7–13. Modules used: 1, 3, 4.

Business context

Microfinance banks, digital lenders, salary-advance and buy-now-pay-later products all need the same engine: given a principal, a rate, a tenor and a product type, produce a repayment schedule that is exactly right to the kobo, then track repayments against it, compute arrears and penalties, and allow early settlement. Errors here are customer complaints and regulatory findings (wrong interest, rounding drift, hidden charges).

You'll build the loan-servicing engine for ITL Microfinance: product configuration, schedule generation for several amortisation methods, repayment allocation, arrears and early payoff.

What you'll build

Loan products (a sealed hierarchy)

public sealed interface RepaymentMethod permits ReducingBalance, FlatRate, InterestOnlyBullet { }
Method Behaviour
Reducing balance (annuity) Equal instalments; interest on the outstanding balance each period
Flat rate Interest computed on the original principal for the whole tenor, spread evenly (common in microfinance; you'll also compute its effective annual rate, which is much higher than the headline rate)
Interest-only with bullet Interest each period, principal repaid at the end

Products (configured in the database by a migration): name, method, annual rate range, tenor range in months, management fee %, late-payment penalty rule, grace days.

API (suggested)

Method and path Purpose
GET /api/v1/products List loan products
POST /api/v1/quotes Quote: schedule, total interest, total cost, effective annual rate, without creating a loan
POST /api/v1/loans Book a loan (stores the schedule)
GET /api/v1/loans/{id} Loan details, outstanding balance, next due date, days past due
GET /api/v1/loans/{id}/schedule Full schedule with paid/unpaid status per instalment
POST /api/v1/loans/{id}/repayments Record a repayment (idempotent by reference) and allocate it
GET /api/v1/loans/{id}/payoff?date= Early settlement amount on a date
GET /api/v1/portfolio/arrears Loans past due, bucketed 1–30, 31–60, 61–90, 90+ days (a standard "portfolio at risk" view)

Rules

  1. Exactness: every instalment is rounded to kobo with HALF_EVEN; the final instalment absorbs rounding so the principal repaid equals the principal lent exactly. Total interest equals the sum of the schedule's interest column.
  2. Repayment allocation order: penalties → interest due → principal due → (if extra) future principal (reducing the outstanding balance). Configurable per product.
  3. Penalties: after the grace days, a daily penalty on overdue principal at the product's rate, capped (configure it; document the policy).
  4. Early payoff: outstanding principal + interest accrued to the payoff date (daily accrual, actual/365) + any penalties, minus nothing else. Flat-rate products may charge a configurable early-termination fee.
  5. Validation: amount and tenor within the product's ranges; rate within the range; positive amounts with at most 2 decimals.
  6. All dates use an injected Clock and Africa/Lagos business dates, so tests can travel in time.

Step-by-step build guide: Loan amortisation and repayment service

Work through the steps in order. Each step ends with a Done when check: don't move on until it passes. Commit after every step with a clear message, so your history tells the story of the build.

Before you start

  • Finish the topics listed under "Skills you'll demonstrate" in the brief, or study them alongside.
  • Read the architecture section and the ADRs. You will update both at the end.
  • Install Java 21 (Temurin), Docker Desktop, Git and IntelliJ IDEA (topic 1.1).

git remote add origin https://github.com/<your-username>/loan-amortisation-service.git

Step 2: Run it locally

cp .env.example .env          # set DB_PASSWORD to anything local

Step 3: Get the data

Never commit raw datasets; download them with a script. Add data/ to .gitignore first.

mkdir -p data
curl -L -o data/fr_inr_lend_nga.json "https://api.worldbank.org/v2/country/NGA/indicator/FR.INR.LEND?format=json&per_page=100"

Copy the licence and attribution lines from the brief's Data section into your README now.

Done when: the files are in data/ and git status doesn't show them.

Step 4: Model products and repayment methods

  1. Sealed RepaymentMethod permits ReducingBalance, FlatRate, InterestOnlyBullet (records).
  2. LoanProduct record: name, method, rate range, tenor range, management fee %, penalty rule, grace days.
  3. Inject a Clock everywhere you need "today"; business dates are Africa/Lagos.

Done when: Domain compiles with no Spring imports and a switch over RepaymentMethod has no default branch.

Step 5: Generate exact schedules

  1. Reducing balance: instalment = P·r / (1 − (1 + r)^−n) with monthly rate r; compute with BigDecimal and MathContext.DECIMAL128, then round each instalment to kobo with HALF_EVEN.
  2. Flat rate: interest = P × annual rate × years, spread evenly; also compute the effective annual rate.
  3. Interest-only bullet: interest every period, principal in the last.
  4. The last instalment absorbs rounding so principal repaid equals principal lent exactly.

Done when: Property test: for 1,000 random loans, the principal column sums exactly to the principal and total interest equals the interest column.

Step 6: Test with real loan sizes

  1. Parse the UCI German Credit file (duration and credit amount columns) into test inputs.
  2. Generate a quote for all 1,000 applications and assert every schedule sums exactly.
  3. Use the World Bank lending rate for Nigeria to set realistic product rate ranges, with the attribution in your README.

Done when: All 1,000 schedules pass the exactness checks.

Step 7: Schema, products and quotes

  1. Migrations: loan_product (seeded with 3 products), loan, instalment, repayment, allocation.
  2. POST /api/v1/quotes returns the schedule, total interest, total cost and effective rate without saving anything.
  3. Validate amount, tenor and rate against the product ranges (422 Problem Detail when out of range).

Done when: A quote request outside the product's tenor range returns a clear 422.

Step 8: Book loans and record repayments

  1. POST /api/v1/loans stores the loan and schedule in one transaction.
  2. POST /api/v1/loans/{id}/repayments is idempotent by reference and allocates: penalties → interest → principal → future principal.
  3. Store each allocation row so you can explain where every kobo went.

Done when: A test pays the first three instalments plus an extra amount and checks the outstanding balance drops by the right principal.

Step 9: Arrears, penalties and early payoff

  1. Days past due from the oldest unpaid instalment; buckets 1–30, 31–60, 61–90, 90+ with a SQL CASE and GROUP BY for /portfolio/arrears.
  2. Daily penalty on overdue principal after the grace days, capped as documented.
  3. Payoff = outstanding principal + interest accrued to the date (actual/365) + penalties (+ early-termination fee for flat-rate products).

Done when: Time-travel tests (fixed Clock) cover on-time, 45 days late and early payoff cases.

Step 10: API polish and metrics

  1. Problem Details for every domain exception; @WebMvcTest tests for them.
  2. Metrics: loans.booked (counter by product) and loans.arrears.balance (gauge).

Done when: All endpoints have curl examples and the metrics show at /actuator/prometheus.

Step 11: Deploy and automate

  1. Make sure ./mvnw verify and the GitHub Actions workflow are green on main.
  2. Optional: mirror the repository to gitlab.com so .gitlab-ci.yml runs too. Other platforms (Azure DevOps, AWS CodeBuild, Jenkins, Argo CD) are covered in the CI/CD guide.
  3. Deploy using the deployment guide: a single VPS (2 vCPU / 4 GB) is cheapest; AWS, Azure and GCP steps are there too.
  4. Put the public health URL (/actuator/health) at the top of your README.

Done when: the health URL returns UP from the internet, and no secret is in Git (git log -p | grep -i password finds nothing real).

  1. Copy the architecture/ folder from this capstone into your repository.
  2. Edit the Mermaid (.mmd) or draw.io (.drawio) files so all five diagrams match what you actually built; re-export SVG/PNG (draw.io: File → Export; Mermaid: npx @mermaid-js/mermaid-cli -i x.mmd -o x.svg).
  3. Write at least three ADRs of your own (copy the format in architecture/adr/): one for persistence, one for concurrency or performance, one you chose yourself.
